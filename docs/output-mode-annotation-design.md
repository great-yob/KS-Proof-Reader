# 결과물 축 확장 설계 — 한/글 메모 삽입 · PDF 주석

작성 2026-08-07 · 형제 문서: [proofreading-architecture.md](proofreading-architecture.md)

> 현행 결과물 축은 두 값이다: **교정본 + 정오표** / **정오표만**(`options["errata_only"]`).
> 여기에 두 값을 더 붙일 수 있는지 실측으로 검토한다.
> ③ 한/글 본문은 그대로 두고 **메모**로 "원문→교정문 + 사유" 달기
> ④ **PDF로 변환한 뒤 PDF 주석**으로 같은 내용 달기

**결론 먼저**

| 옵션 | 판정 | 근거 |
|---|---|---|
| ③ 한/글 메모 | **가능 · 권장** | 한/글 2010에서 `type="MEMO"` 필드 삽입 성공(0.08초/건, 20건 저장·재오픈 보존). **단 본문 스토리에서만** |
| ③′ 표시본(부수 확인) | 가능 | 치환 없이 글자색/음영만 적용 성공, 본문 35,989자 **글자 불변** |
| ④ PDF 주석 | **가능 · 권장** | 2010에서 PDF 저장 성공(17쪽/745KB/4.7초), 한글 텍스트 검색·좌표 추출·주석 삽입·렌더까지 전 구간 통과 |

측정 환경: 한/글 2010 `8, 5, 8, 1677`(`C:\Program Files (x86)\Hnc\Hwp80`, CLSID 점유 확인) · 표본 `교정샘플/05.hwp`(17쪽·35,989자·표 10·그림 5).

> ⚠ **이 문서의 §1은 2026-08-07 같은 날 한 번 뒤집혔다.** 초판은 ③을 "불가"로 적었는데,
> 그 근거였던 `InsertFieldMemo → False`는 **테스트가 머리말 스토리에서 시도한 탓**이었다.
> 왜 그렇게 잘못 읽혔는지를 §1.2에 남겨 둔다 — 같은 함정을 다시 밟지 않기 위해서다.

## 1. 옵션 ③ 한/글 메모 — 된다

### 1.1 실측: 본문 스토리에서 `type="MEMO"` 필드가 정상 삽입된다

```
find("항공유") 매치 1 → GetPos (0, 4, 172)          ← list 0 = 본문 스토리
hwp.HAction.Run("InsertFieldMemo")  → True
GetPos (0, 4, 172) → (22, 0, 0)                     ← 메모 서브스토리 진입
HAction.Execute("InsertText", …)    → True          ← 메모 안에 사유 문장
hwp.HAction.Run("CloseEx")          → True
GetPos → (0, 4, 169)                                ← 본문 복귀
```

hwpx(OWPML)로 저장해 직접 확인한 결과가 결정적이다.

```xml
<hp:ctrl><hp:fieldBegin id="…" type="MEMO" editable="1" zorder="2" fieldid="…">
  <hp:parameters><hp:stringParam name="Command">MEMO/65535/2/…/user9/\;;</hp:stringParam></hp:parameters>
  <hp:subList><hp:p><hp:run><hp:t>‘연료’ → ‘연료(燃料)’ · [표기] 한자 병기 · 메모#1</hp:t></hp:run></hp:p></hp:subList>
</hp:fieldBegin></hp:ctrl><hp:t>항공유</hp:t>
```

메모 본문은 필드의 `subList`에 들어가고, **앵커 낱말(`항공유`)은 그대로 남는다.**

| 항목 | 실측 |
|---|---|
| 삽입 비용 | **0.08초/건** (본문 20곳 1.5초) |
| 저장 → 재오픈 영속성 | hwp·hwpx **둘 다 20개 전부 보존** |
| 원고 글자 | **불변** (메모 문구를 제외하면 삽입 전과 동일) |
| 작성자 | `Command` 파라미터에 **Windows 계정명**이 박힌다(`…/user9/`) |

### 1.2 ⚠ 함정 셋 — 초판이 "불가"로 잘못 읽힌 이유

**(a) 머리말·꼬리말 스토리에서는 거부된다.** 이게 초판을 뒤집은 원인이다.

| 커서 위치 | `InsertFieldMemo` |
|---|---|
| story 9 (머리말) | **False** |
| story 0 (본문) | **True** |

표본 낱말('연구'·'항공유'…)의 **첫 매치가 하필 머리말**이었다(이 문서의 머리말이
"국방품질연구논집…", "임세환 외, 지속가능항공유(SAF)…"라 표본 낱말을 다 품고 있다).
초판은 그 자리에서만 6가지 변형을 시도했으므로 전부 False였고, 그걸 "액션이 닫혀 있다"로
읽었다. → **구현에서는 반환값을 보고 넘어가지 말고, 실패한 자리를 정오표에 기록할 것.**

**(b) `hwp.Run()`은 쓰지 말 것 — 2010에서 no-op이다.**
포럼에 도는 `hwpctrl.Run("InsertFieldMemo")` 형태를 그대로 옮기면 조용히 실패한다.

```
hwp.Run("InsertFieldMemo") → None,  GetPos (9,0,14) → (9,0,14)   ← 아무 일도 안 일어남
이어서 InsertText          → 사유 문장이 그대로 머리말 본문에 박힘
```
hwpx로 확인: `<hp:t>임세환 외, 지속가능ZQMEMOMARK ‘항공유’ → …(SAF) 전환 운영에…</hp:t>`
— **원고 오염**이다. `Run`은 2010 타입라이브러리에서 반환값이 없어(`MoveDocBegin`조차 `None`)
성공/실패를 구분할 수도 없다. **`HAction.Run()`만 쓴다.**

**(c) 반환값만 믿지 말고 `GetPos`의 story 변화로 검증할 것.**
(a)+(b)의 교집합이 최악의 시나리오다 — 메모가 안 열렸는데 `InsertText`를 하면 사유 문장이
**원고 본문에 삽입**된다. 그래서 브리지 구현은 다음 불변식을 지킨다.

```
story_before = GetPos()[0]
if not HAction.Run("InsertFieldMemo"):        → 이 자리 건너뜀(정오표에 기록)
if GetPos()[0] == story_before:               → 서브스토리 미진입 = 실패로 간주, InsertText 금지
InsertText(...) → CloseEx()
```

**(d) 메모 텍스트는 `GetText` 스캔에 섞여 나온다.** `InitScan(0xFF, 0x77)`이 메모 서브스토리를
포함하기 때문이다(메모 1개당 본문 스캔 +2자(개행) + 메모 내용). 원고 글자 자체는 안 바뀌지만,
⚠ **메모본을 다시 교정 입력으로 넣으면 메모 문구가 원고로 잡힌다.** 메모본은 최종 산출물이지
파이프라인 입력이 아니다.

### 1.3 부수 확인 — 표시본(색만 입히기)도 된다

메모와 별개로, 치환 없이 표시만 하는 것도 가능하다는 걸 같이 확인했다.

| 시도 | 결과 |
|---|---|
| 찾기로 선택 → `HCharShape.TextColor=255` → `Execute("CharShape")` (치환 없음) | **True** |
| 찾기로 선택 → `HCharShape.ShadeColor` → `Execute("CharShape")` | **True** |
| 본문 글자 수 (전/후) | 35,989 → **35,989 (불변)** |
| `MarkPenShape`(형광펜 전용 액션) | com_error — **쓸 수 없다** |

→ **메모 모드에서 앵커 낱말에 색까지 같이 입히면** 메모 아이콘을 놓쳐도 눈에 띈다. 권장 조합이다.

### 1.4 참고 — 다른 삽입 계열은 여전히 막혀 있다

같은 본문 스토리 조건에서도 `InsertNote`·`InsertFootnote`·`InsertEndnote`(각주·미주)는 False다.
각주를 주석 매체로 쓰려던 대안은 그대로 폐기한다. 상위 버전 우회 역시 불가하다
([[hwp-com-version-constraints]] 재확인: 2022를 `-Automation`으로 띄우고 `GetActiveObject`를
12초간 재시도해도 `-2147221021 MK_E_UNAVAILABLE`).

참고로 HWPML2X 왕복은 무손실이라(본문 35,989자·표 10·그림 5·CHARSHAPE 109 동일, 1.1초/0.3초)
XML 주입 경로도 살아 있지만, **메모가 COM으로 직접 되므로 쓸 일이 없다.**

## 2. 옵션 ④ PDF 주석 — 가능하다

### 2.1 1단계: 한/글 → PDF (32비트 브리지, COM)

네 경로 모두 **17쪽 전체·745,135B**로 동일하게 성공했다(2010 내장 `Hancom PDF 1.3.0.509`).

| 경로 | 결과 |
|---|---|
| `GetDefault/Execute("FileSaveAs_S")` + `Format="PDF"` | True · 4.3~5.7초 · 17쪽 |
| `FileSaveAsPdf` + `Attributes=16384` | True · 4.2초 · 17쪽 |
| `hwp.SaveAs(path, "PDF", "")` | True · 4.2초 · 17쪽 |

⚠ **선택 영역이 살아 있으면 그 부분만 나온다.** 첫 실측에서 찾기 직후(선택 상태) 저장했더니
**12,854B / 1쪽**짜리 PDF가 나왔다. 예외도 경고도 없고 반환값은 똑같이 True다. →
**PDF 저장 직전에 반드시 `MoveDocBegin`(선택 해제)** 을 넣을 것. 이건 검증 불변식으로 박아야 한다.

### 2.2 2단계: PDF에서 원문 찾기 (64비트, pypdfium2)

한/글이 만든 PDF의 한글 텍스트는 **정상 추출된다**(1쪽 2,245자, `\r` 개행).

```
'연구' 43곳 · 전 17쪽 검색 0.06초 · rect (85.91, 701.28, 98.36, 708.07)
```

좌표는 PDF 좌표계(원점 좌하단)라 주석 `/Rect`에 그대로 쓸 수 있다.

### 2.3 3단계: 주석 쓰기 (pypdf) — **FreeText는 쓰지 말 것**

세 종류를 넣고 pdfium으로 렌더해 눈으로 확인했다.

| 주석 | 결과 |
|---|---|
| `Highlight` (quad_points) | ✅ 해당 낱말 위에 정확히 노란 형광 |
| `Text` (스티커 메모) | ✅ 아이콘 표시 · `/Contents`에 한글 그대로 (`‘연구’ → ‘공부’\n[맞춤법] …`) |
| `FreeText` (여백 상자) | ⚠ **상자만 그려지고 글자가 안 보임** |

⚠ `FreeText`가 비는 이유는 버그가 아니라 구조다 — 외형(appearance stream)을 뷰어가 아니라
**파일이** 그려야 하는데 `/DA`가 Helv이고 한글 폰트가 임베드돼 있지 않다. 여백 박스형 주석이
꼭 필요하면 **한글 폰트 서브셋 임베딩이 선행**돼야 한다(2차 과제). 반면 `Text`(스티커)는
팝업을 **뷰어 UI가** 그리므로 한글이 안전하다.

→ 채택: **`Highlight`(자리) + `Text`(팝업에 원문→교정문·유형·사유)**.

⚠ `quad_points`는 파이썬 list를 그대로 주면 저장 단계에서 터진다
(`'list' object has no attribute 'write_to_stream'`). `ArrayObject([FloatObject(...)])`로 감쌀 것.

### 2.4 4단계 — **진짜 위험은 '등장 인덱스 정합'이다**

이 저장소는 부분 거절을 **등장 인덱스**(문서 순 0-based)로 나른다(`skip_occurrences`).
PDF에 주석을 달려면 "파이프라인의 k번째 등장"과 "PDF 검색의 k번째 매치"가 같은 자리를
가리켜야 한다. 표본 낱말 25개로 대조한 결과:

```
등장 수 일치 20/25 · 한/글 쪽 − PDF 쪽 오프셋 = 항상 1 (일관)
불일치 5건: 항공유 96→104(+8) · 대한 24→32(+8) · 이해관계 21→29(+8)
            국방분야 23→33(+10) · 국내 21→22(+1)
```

불일치의 정체를 좌표로 확정했다 — **머리말이다.**

```
'국방분야' 초과분: y=701에서 8회, 쪽 [2,4,6,8,10,12,14,16]  ← 짝수 쪽 머리말
'대한'    초과분: y=701에서 8회, 같은 쪽 목록
'이해관계' 초과분: y=701에서 8회, 같은 쪽 목록
```

한/글 본문 스토리에는 머리말이 **한 번** 있지만 PDF에는 **쪽마다 렌더**된다. 그래서 PDF 쪽이
항상 더 많다. 대응은 두 겹으로 둔다.

1. **머리말/꼬리말 필터** — 같은 y(±1pt)에서 **3쪽 이상** 반복되는 매치는 제외한다.
   위 세 낱말은 이것만으로 정확히 상쇄된다(+8 → 0).
2. **그래도 개수가 다르면 인덱스 매핑을 포기한다** — 그 원문은 **모든 등장에 주석을 달고**
   팝업에 `⚠ 위치 자동 대조 실패 — 정오표의 쪽과 대조하세요`를 적는다.
   ⚠ 조용히 첫 매치에 달거나 조용히 건너뛰는 선택지는 없다([[layer-order-silent-drop-audit]]).

⚠ 쪽 번호는 **두 좌표계가 따로 논다**. 정오표의 쪽은 `KeyIndicator()[3]`(prnpageno)이고
PDF는 물리 쪽이다. 이 표본에서 오프셋이 1로 일정했던 건 **우연이 아니라 이 문서가 2쪽부터
번호를 매기기 때문**이고(`KeyIndicator@문서처음 = (True, 3, 1, 2, …)`, PageCount 17인데
문서 끝 prnpageno 18), 구역마다 재시작하는 문서에서는 일정하지도 않다.
→ **PDF 주석에는 PDF 물리 쪽만 쓰고, 두 값 사이에 산술을 하지 않는다.**

### 2.5 성능·의존성

| 항목 | 실측(17쪽/1MB 문서) |
|---|---|
| PDF 저장(COM) | 4.2~5.7초 |
| textpage 준비 | 0.06초 |
| 낱말 25개 전문 검색 | 0.01초 |
| 주석 3개 삽입 + 저장 | 0.02초 (745,135B → 743,077B) |

→ 병목은 **한/글의 PDF 저장 한 번**뿐이다. 30MB급 원고는 별도 실측이 필요하다.

의존성 2개(둘 다 permissive, 배포 가능):

| 패키지 | 라이선스 | 용도 |
|---|---|---|
| `pypdfium2` | BSD-3 / Apache-2.0 | 텍스트 검색 + 좌표(rect) |
| `pypdf` | BSD-3 | 주석 쓰기 |

⚠ **PyMuPDF(fitz)는 쓰지 말 것** — 검색·주석을 혼자 다 하지만 **AGPL-3.0**이다. 이 저장소는
공개이면서 LICENSE 파일이 없어(= 권리 유보) AGPL 산출물을 배포하면 정리해야 할 게 생긴다.

## 3. 공통 설계 — 결과물 축을 bool에서 enum으로

### 3.1 `errata_only: bool` → `output_mode: str`

값이 넷이 되므로 bool로는 못 버틴다.

| `output_mode` | 화면 이름 | 한/글 원본 | 산출물 |
|---|---|---|---|
| `"hwp"` (기본) | 교정본 + 정오표 | 치환 + 빨강 | `_교정본.hwp` + 정오표 |
| `"errata"` | 정오표만 | **무수정** | 정오표 |
| `"memo"` | 메모 + 정오표 | **글자 불변**, 메모 필드 + 앵커 색 | `_메모본.hwp` + 정오표 |
| `"pdf"` | PDF 주석 + 정오표 | **무수정** | `_주석.pdf` + 정오표 |

⚠ **네 값 모두 '교정 방식'(항목별 검토 / 자동 일괄)과 직교한다.** `memo`·`pdf`도 수락/거절이
있어야 무엇을 달지 정해진다 — 기존 `errata_only` 주석의 논리가 그대로 적용된다.

⚠ `gen_errata` 강제 ON + 잠금은 **`hwp`를 제외한 세 값 전부**로 확대한다. 안 그러면
`memo`에서 정오표를 끄는 순간 "메모만 달린 파일 하나"가 되어, 메모를 못 단 자리
(머리말·각주 등 §1.2(a))를 확인할 곳이 사라진다.

메모 본문 서식 제안 — 한 메모 안에 세 줄:
```
‘원문’ → ‘교정문’
[교정 유형] 사유
· 이 낱말 N곳 중 k번째
```

호환 처리: `options["errata_only"]`는 `output_mode in ("errata","mark","pdf")`의 파생값으로
남겨 기존 호출부를 깨지 않되, **결과 dict에는 `output_mode`를 실어** `result_panel`이 분기하게 한다.

### 3.2 집계 불변식 — `applied`의 뜻을 넓히지 않는다

⚠ 현행 규약(`errata_only`에서 `applied`는 0을 유지)을 그대로 이어받는다.
**`applied` = 한/글 본문 글자를 실제로 바꾼 건수.** 따라서

- `memo` → `applied = 0`, 신설 `memoed`(항목) / `memoed_occ`(등장)
- `pdf` → `applied = 0`, 신설 `annotated` / `annotated_occ`
- 두 모드 모두 `to_apply` / `to_apply_occ`(= 사람이 반영할 몫)는 `errata`와 동일하게 채운다
- ⚠ **메모를 못 단 자리는 조용히 사라지면 안 된다** — 머리말·각주 스토리 거부(§1.2(a))는
  실패가 아니라 **구조적 제약**이므로, 정오표 `note`에 `메모 삽입 불가 위치(머리말·각주)`로
  남기고 집계에도 별도로 드러낸다

`result_panel`은 카드 03과 게이지 라벨만 모드별로 갈아 끼운다(이미 `errata_only`로 하고 있는 일).
⚠ 옛 휴리스틱(`flagged > 0 and applied == 0`)을 모드 판정에 되살리지 말 것 — 이제 그 상태를
만드는 모드가 셋이라 더 위험하다.

### 3.3 정오표

행 스키마는 손대지 않는다. `outcome="todo"`(반영 필요)를 `mark`·`pdf`에도 그대로 쓰고,
첫 시트 이름은 `errata`와 같이 **교정**으로 둔다. `mark`는 "표시는 됐지만 글자는 그대로",
`pdf`는 "주석은 달렸지만 원본은 그대로"라 둘 다 사람이 반영할 몫이라는 점에서 동일하다.

⚠ `pdf` 모드에서만 열이 하나 필요할 수 있다 — 정오표의 `쪽`(prnpageno)과 PDF 물리 쪽이
다르기 때문이다(§2.4). **`PDF 쪽` 별도 열**을 두는 쪽을 권한다. 한 칸에 두 좌표계를 섞으면
"Ctrl+G로 찾아가는 숫자"라는 현재 `쪽`의 계약이 깨진다.

### 3.5 브리지 `memo` 명령 설계 요지

`apply()`의 다중 패스 재탐색·`CloseEx` 상태 정규화·재스킵 인덱스 유지 로직은 **그대로
재사용해야 한다**(부분 거절 정합이 거기 걸려 있다). 달라지는 건 매치 자리에서 하는 일뿐이다.

```
apply : RepeatFind → (선택) → InsertText(치환) → 새 글자 재선택 → CharShape(빨강)
memo  : RepeatFind → (선택) → story 기록 → InsertFieldMemo → story 변화 검증
                            → InsertText(사유) → CloseEx → (앵커 재선택) → CharShape
```

⚠ 치환이 없으므로 `self_matching` 무한 증식도, 쪽 밀림도 없다. 즉 `memo` 모드에서는
쪽 스냅샷(`locate`)과 메모가 **같은 장면**이라 정오표 쪽 번호가 apply 모드보다 더 정확하다.
⚠ 되돌리기 어려움은 그대로다 — `_메모본` 사본에만 적용하고 원본은 절대 저장하지 않는다.
⚠ **story 검증 불변식**(§1.2(c))을 브리지에 박아 둘 것. 이걸 빼면 실패한 자리에서
사유 문장이 원고 본문에 삽입된다 — 실측으로 재현된 오염이다.

## 3.6 구현하며 드러난 함정 두 개 (2026-08-07 구현 실측)

설계만으로는 안 보이고 **실제 원고에 돌려야** 드러난 것 두 가지. 둘 다 조용히 틀린
결과를 내는 부류라 여기 남긴다.

### (가) 메모 폭주 — 메모 본문이 원문을 인용하므로 찾기가 자기 메모를 다시 잡는다

메모에 `‘품질특성’ → ‘품질 특성’`이라고 적는 순간 **문서 안에 '품질특성'이 하나 더
생긴다.** 메모 본문은 서브스토리이고 `RepeatFind`는 서브스토리까지 닿으므로, 다음 찾기가
그것을 새 등장으로 오인해 메모를 또 달고, 그 메모가 또 매치를 만든다. apply의
`self_matching`(괄호 증식)과 정확히 같은 구조다.

```
[수정 전] '품질특성' 15등장 → 메모 100개(상한에서 겨우 멈춤)
          '연료'    52등장 → 메모 100개
          본문 스캔 35,997자 → 52,373자
[수정 후] 15 / 52 / 94(96등장 − 부분 거절 2) → OWPML `type="MEMO"` 필드 정확히 161개
```

막는 방법 두 겹:
1. 만든 메모의 **서브스토리 id를 기억**해 그 안의 매치는 건너뛴다. ⚠ 이때
   **등장 카운터(visited)를 늘리지 않는다** — 늘리면 등장 인덱스가 검수 패널과 어긋나
   부분 거절이 엉뚱한 자리에 걸린다.
2. 파이프라인이 센 등장 수(`occ_total`)를 **상한**으로 쓴다. 1이 놓쳐도 원고의 등장 수를
   넘길 수는 없다.

### (나) 머리말 필터가 본문까지 걷어낸다 — 판정 키는 (x, y) 둘 다

§2.4의 머리말 필터를 **y좌표만으로** 구현하면 본문이 함께 날아간다. 조판된 문서에서는
본문 줄의 y가 쪽마다 똑같이 반복되기 때문이다.

```
[y만]    '항공유' PDF 104곳 → 77곳 (원고 96곳과 더 어긋남) · 위치 대조 실패 2건
[(x,y)]  '항공유' PDF 104곳 → 96곳 · 머리말 8곳만 제외 · 위치 대조 실패 0건
```

같은 낱말이 여러 쪽에서 **같은 x·같은 y**에 오는 것은 머리말·꼬리말 말고는 사실상 없다.

### (다) ★메모 컨트롤은 위치 8칸을 차지한다 — 커서 전진을 어림하면 메모가 겹친다

(가)를 고친 뒤에도 **같은 자리에 메모가 두 개씩** 달렸다(사용자 보고 2026-08-07).
메모 삽입 후 커서는 앵커 **앞**(메모 컨트롤 자리)으로 돌아오므로 앵커 뒤로 밀어 줘야
하는데, 컨트롤을 1칸으로 어림한 것이 원인이었다.

```
'기술동향' 삽입 전: 문단 9의 15~19
'기술동향' 삽입 후: 문단 9의 23~27      ← 컨트롤이 8칸을 차지해 +8 밀림
SetPos(20) → 23으로 스냅 → RepeatFind가 **같은 낱말**을 다시 잡음 → 메모 중복
```

⚠⚠ **그리고 이 버그는 개수만 보면 보이지 않는다.** (가)에서 넣은 `occ_total` 상한이
총량을 정확히 맞춰 주기 때문이다 — 초판 검증이 "메모 161개, 등장 수와 일치"를 보고
통과시켰는데 실제로는 앞쪽 등장에 겹쳐 쌓여 있었다. **검증은 '몇 개'가 아니라
'서로 다른 자리 몇 곳'으로 해야 한다**(OWPML에서 본문 글자 없이 맞붙은 메모 쌍을 센다).

```
[사용자 실행본] 메모 64개 중 맞붙은 쌍 10건
[수정 후]       메모 103개 중 맞붙은 쌍 0건 · 낱말별 개수 = 등장 수 정확 일치
```

대응: `_MEMO_CTRL_SPAN=8`로 SetPos 한 번에 넘기되 **GetPos로 확인**하고 못 넘었으면
MoveRight로 밀며(버전이 달라도 안전), 그래도 같은 앵커를 다시 잡으면 **재발견으로 감지해
등장으로 세지 않는다**. 세 겹이라 하나가 틀려도 겹치지 않는다.

### (라) '메모 본문 입력 실패'(서버 오류)는 (다)의 증상이었다

사용자 실행에서 5건이 `(-2147417851, '서버에서 예외 오류가 발생했습니다.')`로 실패했다.
겹침으로 **이미 메모가 달린 자리에 메모를 또 열려다** 난 오류다 — 실패 목록의 '전세계적'이
중복 쌍 목록에도 그대로 있는 것이 증거이고, (다) 수정 후 같은 낱말 전부가 정상 처리됐다.
⚠ 그래도 방어는 남긴다: 본문 입력이 실패하면 **빈 메모를 지운다**(`DeleteFieldMemo`).
안 지우면 내용 없는 말풍선이 원고에 남아 편집자가 무엇인지 알 길이 없다
(사용자 실행본에 실제로 빈 메모 쌍이 남아 있었다).

### (마) 앵커 글자색은 바꾸지 않는다

사용자 지정 2026-08-07. 메모 모드의 약속은 '원고를 손대지 않는다'이고 **글자색도 원고의
서식**이다. `mark_anchor`는 기본 꺼짐이며 `apply_worker`는 색을 아예 넘기지 않는다.

### (바) 진행률은 등장마다 보낼 것

브리지가 **항목 단위로만** 진행률을 보내면 등장이 96곳인 낱말 하나에서 수십 초 출력이
끊기고, 부모의 유휴 타임아웃(`_send_cmd`)이 그걸 '한/글 행업'으로 오판해 프로세스를
죽인다(실측: 120초 타임아웃으로 첫 실행이 통째로 실패).

## 3.7 결과물 추가 — 검토를 다시 거치지 않고 산출물을 하나 더 (2026-08-07)

결과물 축을 enum으로 넓히고 나니 남은 구멍이 하나 드러났다. **한 번 고른 값이 사실상
최종이었다.** 결과물 하나를 받아 본 뒤 다른 형태가 필요하면 초기화 → 옵션 선택 →
**같은 원고의 같은 검토를 처음부터 다시** 하는 것이 유일한 길이었다(사용자 요구).

수락/거절·부분 거절은 이미 확정된 값이므로 다시 물을 이유가 없다. 그래서 결과 화면에
**'산출물' 카드**를 두고, 이미 만든 파일 목록과 **아직 만들지 않은 모드 버튼**을 함께
보여 준다. 버튼은 `ResultPanel.extra_output_requested`만 내보내고, 실행은
`MainWindow._start_extra_output`이 **같은 `ApplyWorker`에 `output_mode`만 갈아** 돌린다.

### 불변식 넷 — 하나라도 깨면 조용히 틀린 산출물이 나온다

| # | 불변식 | 깨지면 |
|---|---|---|
| ① | **언제나 원본 파일에서 만든다** | 교정본 위에 메모·주석을 달면 앵커로 쓸 **원문 문자열이 이미 바뀌어 있어** 한 곳도 못 찾는다. 원본이 안전한 근거: `save_as`는 새 경로에 쓰고 `close`는 맨 `Quit`이라 원본을 덮어쓰는 경로가 없다(실측: mtime·size 불변). |
| ② | **결정은 다시 묻지 않는다** | `self._corrections` + `_applied_occ_rows`(1차 적용 때 뜬 스냅숏)를 그대로 넘긴다. 결과 화면에서 패널에 다시 물으면 그 사이 상태가 달라졌을 수 있다. |
| ③ | **1차 실행의 수치를 덮어쓰지 않는다** | 추가분은 `result["extra_outputs"]`에 실린다. `applied`("본문 글자를 실제로 바꾼 건수")의 뜻을 넓히지 않는다는 §3.2 규율이 그대로 유지된다 — 대시보드 01·02·03은 1차 실행의 기록이다. |
| ④ | **기존 정오표를 덮어쓰지 않는다** | 모드마다 내용이 다르고(PDF는 'PDF 쪽' 칸이 붙고, 메모는 메모 불가 자리가 주석으로 실린다), 사용자가 이미 열어 봤을 수 있다. `_extra_errata_path`가 `_정오표(메모).xlsx`처럼 이름을 비켜 준다. |

### 쪽 번호는 1차 실행 것을 되쓴다

`ApplyWorker(known_pages=…)`에 `result["pages_by_original"]`을 되돌려 주면 locate 단계를
통째로 건너뛴다. 같은 원본의 **같은 장면**이라 다시 잴 이유가 없고, 두 번 재는 순간
두 정오표가 서로 다른 쪽을 적을 여지가 생긴다.

실측(05.hwp 사본 · 낱말 3개 · 등장 82곳):

| 실행 | 시간 | 로그 |
|---|---|---|
| 1차 '정오표만' | 3.6초 | `[정오표] 쪽 번호 확인 3건 · 본문 82항목` |
| 추가 '메모' | 6.6초 | `[정오표] 쪽 번호 재사용 3건` → 메모 36곳 · 불가 4곳 · `_메모본.hwp` |
| 추가 '정오표'(한/글 미기동) | **1.3초** | 열 이유가 없어 브리지를 아예 띄우지 않는다 |

### ⚠ 오류 처리는 `_on_error`를 재사용하면 안 된다

1차용 `_on_error`는 **설정 화면으로 되돌린다.** 추가 산출물에서 그걸 쓰면, 부가 산출물
하나가 실패했다는 이유로 이미 성공한 실행의 결과 화면이 통째로 사라진다. 그래서
`_on_extra_error`는 로그 + 경고 팝업만 하고 결과 화면에 머문다.

## 3.8 ★세 산출물이 같은 자리를 표시해야 한다 (2026-08-08)

사용자 보고: *"교정본·메모본·주석을 다 만들어 봤는데 반영된 항목이 다 다른 것 같다.
세 파일에 적용 부분이나 갯수 차이가 있으면 신뢰성에 치명적이다."*
실측해 보니 **원인이 둘**이었고, 둘 다 같은 뿌리에서 나왔다 — **등장을 무엇으로 세느냐**.

### 원인 ① pdfium의 검색은 공백을 무시한다 (PDF 전용 · 치명적)

실측(05.hwp · 17쪽):

| 찾는 문자열 | 원고 | PDF 검색 | 머리말 제거 후 |
|---|---|---|---|
| `'국방 분야'` | 2곳 | 33곳 | 25곳 |
| `'국방분야'` | 24곳 | 33곳 | 25곳 |

두 결과가 **글자 하나 다르지 않고 같다.** 그래서 '국방 분야'→'국방분야' 띄어쓰기 교정
(수락 2곳)이 PDF에서는 **반대 표기 자리까지 25곳**에 형광으로 칠해졌다.

다행히 `get_text_range(idx, cnt)`는 **실제로 잡은 글자**를 돌려준다:

```
needle='국방 분야' → (cnt=4, '국방분야', rect 1개) × 31   ← 버려야 할 매치
                  → (cnt=5, '국방 분야', rect 2개) × 2    ← 진짜
```

⚠ 그렇다고 단순 문자열 일치로 거르면 **정탐을 잃는다.** PDF는 줄이 바뀌는 자리에
`\r\n`을 끼워 넣기 때문이다 — `'엔\r\n진 부품'`은 진짜 '엔진 부품'이다. 그래서
`_spacing_ok`는 **줄바꿈만 흡수하고 띄어쓰기는 엄격히** 본다(원문 == 잡은 글자 /
줄바꿈 삭제 / 줄바꿈을 공백으로, 셋 중 하나면 통과).
⚠ 남는 모호함: 줄바꿈이 **하필 이음매에서** 일어나면 `'공급사슬\r\n관리'`가 어느
표기인지 글자만으로는 가릴 수 없어 양쪽 다 인정한다(자리 하나 규모).

### 원인 ② 등장 상한의 기준이 모드마다 달랐다

`Correction.occurrences`는 검수 패널이 **추출 텍스트**에서 센 수다. 그런데
`skip_occurrences`가 사는 좌표계는 **브리지 RepeatFind 순서**이고, 둘은 어긋날 수 있다.

실측: '지속가능항공유' — 추출 텍스트 **5곳** / 문서 찾기(`locate`) **4곳**.
메모는 상한을 5로 잡아 **한 곳을 더** 달았고(교정본 3곳·PDF 3곳·메모 4곳), 교정본은
S4 안전망이 "수락 4곳 중 3곳만 치환"이라고 정직히 보고했다.

★**결론 규칙: 등장 좌표계의 정본은 `locate_originals`다.** 메모(`occ_cap`)와
PDF(`_align_occurrences`) 모두 `doc_occ = len(pages_by_original[원문])`을 기준으로 쓴다.
locate는 아무것도 바꾸지 않은 문서를 같은 RepeatFind로 세므로, 메모가 만든 매치에
부풀 수도 없다 — `occ_total`보다 엄격히 낫다. 메모·주석 본문의 '이 낱말 N곳'도 같은 수다.

### 남는 차이 둘 — 정당하고, 이름이 붙어 있고, 정오표에 기록된다

**개수를 억지로 맞추지 말 것.** 둘은 서로 다른 산출물이라는 사실 그 자체다.

| 차이 | 왜 |
|---|---|
| 검수 항목(`dict_flag`, 고칠 말 없음)은 메모·PDF엔 표시, **교정본엔 없음** | 빨강은 '이 자리를 고쳤다'는 뜻이다. 안 고친 자리에 칠하면 빨강의 뜻이 흐려진다. 완료 화면 카드 03에 `검수 N (정오표만)`으로 적어 차이를 설명한다. |
| 머리말·꼬리말 자리는 치환·PDF 주석은 되지만 **메모는 거부** | 한/글의 구조적 제약(§1.2). 정오표에 "이 자리에는 메모를 달 수 없습니다"로 남는다. |

그리고 **표시하지 못한 자리는 반드시 드러낸다** — `result["unmarked"]`가 메모 불가 ·
PDF 미탐 · 문서에서 못 찾은 등장을 한 숫자로 모아 완료 화면에 `표시 못 함 N곳`으로
띄우고, 정오표 각 행에 사유를 적는다. 교정본의 S4 '부분 반영'에 해당하는 장치다 —
이게 없으면 못 단 자리가 `todo`로만 적혀 **메모가 달린 자리처럼 읽힌다**.

### 원인 ③ 메모 순서 — 긴 원문부터 달면 자기 메모가 뒤 항목의 자리를 먹는다

사용자 2차 보고(2026-08-08): 교정본에는 있는데 **메모본에만 18건이 없다**.

`insert_memos`는 apply와 같은 '긴 원문 우선' 정렬을 썼다. 그런데 **메모 본문이 원문을
인용**하므로, 긴 '고려해야한다'에 메모를 달면 그 본문에 '해야한다'가 새로 생기고 —
다음 항목의 찾기가 자기 메모 안의 글자를 원고의 등장으로 오인한다. 그 자리에서
`InsertFieldMemo`는 기존 메모로 들어가거나 `-2147417851`('서버에서 예외 오류')로 죽는다.

실측으로 가른 근거:

| 조건 | 결과 |
|---|---|
| `'해야한다'` **단독** | 14곳 전부 성공 |
| `'고려해야한다'·'협력해야한다'·'검토해야한다'`와 **함께** | 실패 발생 · 실패 자리의 story가 **앞서 만든 메모의 서브스토리** |
| 중첩 3항목을 뺀 18낱말 | 36곳 전부 성공 · 저장된 파일 실측 메모 **36개** |

★**정렬을 apply와 정반대로 — 짧은 원문 우선.** 짧은 것부터 달면 이미 달린 메모의
원문은 항상 더 짧아 뒤에 오는 긴 원문을 품을 수 없다. A/B 실측(22항목 · 정오표 37행):

| 정렬 | 메모 | 교정본과 차이 |
|---|---|---|
| 긴 원문 우선(기존) | 31곳 | **6행** — 그 6건이 사용자 보고 항목과 일치 |
| **짧은 원문 우선** | **32곳** | **3행** |

⚠ 항목 순서는 **등장 인덱스에 영향을 주지 않는다** — 브리지 `memo`는 항목마다
문서 처음부터 다시 훑으므로(MoveDocBegin) 좌표계는 apply/locate와 그대로 같다.
⚠ 되돌리려면 이 A/B를 **먼저 다시 잴 것**.

⚠ **`hwp.InsertText(...)`를 대체 경로로 쓰지 말 것** — HWP 2010에는 아예 없다
(실측: `AttributeError: HWPFrame.HwpObject.InsertText`). 파라미터셋 경로가 유일하다.

**남은 잔차**: 중첩 원문이 서로를 가리는 자리에서 메모가 여전히 몇 곳 실패한다
(37행 중 3행). 그 자리는 `blocked`로 집계되고 정오표에 사유가, 화면에 `표시 못 함 N곳`이
남는다 — **조용히 사라지지 않는다.** 완전 해소는 '찾은 자리를 먼저 다 모아 두고
뒤에서부터 삽입'(컨트롤이 앞 자리를 밀지 않는 순서)이 필요하며 미착수다.

### 원인 ④ ★교정본 — `skip_occurrences`가 치환 전 좌표계다

사용자 3차 보고: *"주석에는 정상 포함된 '해야한다 → 해야 한다'가 교정본에만 미반영."*

`apply`는 **긴 원문 우선**으로 치환한다. 그래서 '고려해야한다'가 먼저 바뀌면 그 안에
있던 '해야한다'가 문서에서 **사라진다**. 그런데 `skip_occurrences`는 **치환 전**
좌표계의 인덱스라, 남은 등장에 그대로 들이대면 엉뚱한 자리를 가리킨다.

```
'해야한다' 추출 등장 14곳 · 그중 긴 교정 안에 든 자리 5곳 → 인덱스 [5, 8, 9, 11, 12]
치환 시점에 남는 등장 9곳(좌표계 0..8)   ← 5곳이 이미 사라짐
skip으로 넘긴 값 [5, 8, 9, 11, 12]      ← 0..13 좌표계

현행 : 치환 [0,1,2,3,4,6,7]  → 문서에 '해야한다' 2곳 잔존   ← 사용자가 본 증상
보정 : 치환 [0..8] 전부       → 0곳 잔존
```

★해법은 `ApplyWorker._plan_occurrences` — 검수 패널이 실어 보내는 등장 구간
(`pos`/`end`, `get_occurrence_rows`에 추가)으로 **다른 적용 교정의 치환 구간이 통째로
품는 등장**을 골라 빼고, 남은 것을 다시 번호 매긴다.

⚠ **`skip_occurrences`를 그냥 비우면 안 된다** — 성격이 다른 셋이 섞여 있다:

| 부류 | 치환 후 | 조치 |
|---|---|---|
| 사용자가 거절한 자리 | 그대로 있음 | **계속 건너뛴다** (지우면 거절한 자리가 치환되는 더 나쁜 사고) |
| `excluded` (교정 대상 아닌 긴 낱말 속 조각) | 그대로 있음 | 계속 건너뛴다 |
| 더 긴 **적용 교정**이 삼키는 자리 | 사라짐 | 빼고 재번호 |

셋을 가르는 유일한 근거가 **구간 겹침**이라 위치가 필요하다.

⚠ **메모·PDF에는 적용하지 않는다** — 문서를 안 바꾸므로 등장이 사라지지 않는다.
보정하면 오히려 그쪽 좌표계가 어긋난다.
⚠ 정오표는 브리지 인덱스를 `survivors`로 되돌려 읽고, S4 기대 치환 수도 보정 후
좌표계로 센다(안 그러면 정상 실행이 '부분 반영'으로 오탐된다).

검증 5종(전부 통과):

| 시험 | 확인한 것 |
|---|---|
| T1 중첩 있음 | 교정본 잔존 **0곳**(이전 2곳) · 정오표 거짓 '실패' 0행 |
| **T2 중첩 + 부분 거절** | 잔존 정확히 1곳이고 **거절한 바로 그 자리** ← 가장 위험한 회귀 |
| T3 중첩 없음 | 보정이 **아예 개입하지 않음**(plan 비어 있음) |
| T4 `excluded` | 교정 대상 아닌 긴 낱말 속 조각은 **계속** 건너뜀 |
| T5 메모·PDF | 보정 무개입 |

종합 실측(22항목·부분 거절 포함·정오표 37행): **교정본 문서 실측 어긋난 항목 0건 ·
교정본 ↔ PDF 완전 일치**.

### 수정 후 실측 (05.hwp · 같은 검토 결과로 세 모드)

정오표 13행을 등장 단위로 대조:

| 대조 | 결과 |
|---|---|
| 교정본 ↔ PDF | **13행 전부 일치** |
| 교정본 ↔ 메모 | 12행 일치 · 1행 차이 = 머리말 자리(메모 불가, 정오표에 명시) |

PDF 주석: **11곳 / 주석 11개 / 한 자리 최대 1개 / 전부 내용 있음**(고치기 전에는 22개).

## 5. 재현 방법

측정에 쓴 프로브는 임시 폴더에만 있다(저장소에 커밋하지 않음). 재현하려면 32비트 파이썬
`C:\Users\user9\AppData\Local\Programs\Python\Python311-32\python.exe`로 COM 쪽을,
`.venv64\Scripts\python.exe`로 PDF 쪽을 돌린다. 핵심 호출은 본문 §1.1·§2.1~2.3에 그대로 있다.

⚠ 측정 전 `taskkill /IM hwp.exe` — COM은 단일 전역 인스턴스라 앞 테스트의 문서 상태가
다음 테스트에 새어 든다([[hwp-com-version-constraints]]).
⚠ 표본은 반드시 **사본**에 대고 돌릴 것. `교정샘플/`의 원본을 직접 열면 프로브가 그 파일을 고친다.
