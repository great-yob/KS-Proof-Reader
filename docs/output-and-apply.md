## 결과물 축 (output_mode)

**결과물 (output) is a user-chosen axis with five values** — `options["output_mode"]`, set by `SetupPanel`'s 2×2 card grid (full rationale + measurements: [docs/output-mode-annotation-design.md](output-mode-annotation-design.md)):

| `output_mode` | HWP 원본 | 산출물 |
|---|---|---|
| `"hwp"` (default) | 치환 + 빨강 표시 | `_교정본.hwp` + 정오표 |
| `"hwp_memo"` | 치환 + 빨강 표시 + **같은 자리에 메모** | `_교정본(메모).hwp` + 정오표 |
| `"errata"` | **무수정** (opened only to read page numbers) | 정오표 |
| `"memo"` | **글자 불변**, 한/글 메모 필드 + 앵커 글자색 | `_메모본.hwp` + 정오표 |
| `"pdf"` | **무수정** (exported to PDF) | `_주석.pdf` (형광 + 스티커 주석) + 정오표 |

⚠ The axis is **orthogonal to 교정 방식** (항목별 검토 / 자동 일괄 적용), not a value of it: every mode still needs the review step, because accept/reject is what decides what gets written, recorded, or annotated. ⚠ Any mode other than `hwp` forces `gen_errata` on and locks that toggle — otherwise `errata` produces nothing at all and `memo`/`pdf` lose the only place that records **the spots that could not be marked**. ⚠ `errata_only` survives only as a derived bool meaning "the HWP was not modified"; it cannot tell them apart, so branch on `output_mode`. 한글 글자를 실제로 바꾸는 모드는 **`ApplyWorker.MODIFY_MODES`(= `SetupPanel.MODIFY_MODES`) 한 곳**에 적혀 있다 — `applied`·`_occ_plan`·S3/S4 재분류·정오표 잠금이 전부 그 집합으로 갈린다.

## HWP(빨간색+메모) 결합 모드

★**`"hwp_memo"`(빨간색+메모)는 메모 앵커가 원문이 아니라 교정문이다**(2026-09-03 사용자 지시). 치환이 끝난 문서에는 원문이 더 이상 없기 때문이다. 그런데 교정문은 **원래부터 그 표기였던 자리에도** 있다 — 실측(05.hwp): '항공유과'→'항공유와'는 1곳을 고치는데 '항공유와'가 문서에 이미 19곳 있고, 그중 첫 자리는 문서 앞쪽(char 2644)이라 순서만 보고 달면 **전혀 다른 자리에 메모가 박힌다**. ★그래서 메모는 **치환 단계가 확인한 자리 좌표**로 곧장 간다(2026-10-17). 브리지 `apply`가 치환마다 `spots_raw`에 `[list, para, 시작, 원문 길이, 교정문 길이, 등장 번호]`를 남기고(삽입 직후 커서가 정확히 '시작 + 교정문 길이'일 때만 — 아니면 그 문단·스토리·문서를 `dirty`로 적는다), `HwpEditor._resolve_spots`가 그 기록을 **치환 순서대로** 되짚어 최종 좌표 `detail["spots"]`를 만든다(같은 문단 뒤쪽 자리는 길이 차만큼 밀린다 · 겹침·`dirty`는 무효 → 그 항목은 좌표 없음). 브리지가 상태를 들지 않는 것은 그대로다. ⚠ 빨간 글자색(`_match_is_red`)으로 자리를 고르는 길은 **좌표가 없는 항목의 폴백**일 뿐이다 — 빨강은 '누가 고친 빨강인지'를 모른다: 짧은 교정문이 긴 교정문 속에서 남의 자리를 제 것으로 세고('취업 유지' ⊂ '취업 유지 후 이탈'), 같은 교정문을 내는 두 교정('성별 임금 격차'·'성별임금격차' → '성별 임금격차')은 자리를 나눌 수 없다(실측 24만 자 원고: 충돌 30곳). 폴백에서도 **긴 앵커부터** 자리를 차지하고, 이미 주인이 있는 구간과 겹치는 빨간 매치는 버린다(`insert_memos` ②). ⚠ 색을 못 읽으면 통과시킨다 — 그래서 `doc_occ`(실제 치환 수)가 상한이다. ⚠ 검수 카드(`dict_flag`, 글자 불변)는 빨강이 없으므로 **원문 앵커 + `red_only` 꺼짐**으로 찾는다. ⚠ 그 앵커는 **다른 교정이 새로 만들 수 있다**('설치 대학'→'설치대학'이 '설치대학'을 하나 더 만든다) — 카드의 등장 수는 치환 전 문서 기준이므로, 치환 좌표 중 교정문에는 앵커가 있고 원문에는 없는 자리에 걸린 매치는 등장으로 세지 않는다(`insert_memos`의 `created`·`made_here` · 그만큼 더 찾는다).
★**결과 화면의 '빨간색+메모' 추가는 이미 만든 교정본 위에 메모를 단다** — 불변식①('산출물은 언제나 원본에서 만든다')의 **유일한 예외**이고, 예외인 이유가 곧 그 불변식의 근거다(앵커가 교정문이라 교정본이라야 찾을 수 있다). `main_window._start_extra_output`이 `source_is_corrected`와 `hwp_output_path`(원본 기준 이름 — 안 그러면 `…_교정본_교정본(메모)`)를 넘기고, `ApplyWorker`는 치환 단계를 건너뛴다. ⚠ 그 실행의 `applied`·`occurrences`는 **0**이다(고친 게 없다). 메모 detail의 `original`은 앵커(=교정문)라 정오표가 어긋나므로 `anchor_of`로 원문을 되돌려 싣는다. ★그 교정본을 만든 실행의 치환 좌표를 함께 넘긴다(`result["apply_spots"]` → `MainWindow._corrected_hwp` → `opts["base_spots"]`) — 저장한 교정본이라 좌표가 그대로이므로 빨간 글자를 다시 찾지 않는다(실측 24만 자 원고: 좌표 없이 575곳·못 함 47 → 좌표로 609곳·못 함 13, 1차 결합 모드와 동일).
⚠ 예전엔 결합 모드가 메모 전에 문서를 저장·닫기·다시 열기(`reindex_first`)했다 — **폐기**(2026-10-17). '낡은 찾기 색인'은 오진이었고 진짜 원인은 아래 **메모 모드** 단락의 세션 오염이다.
★**결합 모드의 정오표는 메모 결과를 겹쳐야 한다** (2026-10-17 수정 — 감사 실측: 메모 68곳 중 9곳 실패인데 사유 0건·로그는 '정오표에 사유 기록'이라 거짓 안내·결과 화면 누락 0). 정오표 행은 치환 detail로 만들고 `ApplyWorker._overlay_memo_notes`가 메모 detail을 겹친다. 자리 대응은 **`red_rank`**(그 교정이 치환한 자리 중 문서 순 순번 — 메모 단계가 빨간 자리를 세는 좌표계와 같다)이고, 검수 카드는 원문 앵커라 `occ` 그대로다. 실패 자리는 `outcome="applied"`를 유지한 채(글자는 고쳐졌다) '교정은 반영됨 · …' 사유와 `unmarked`가 붙고, `result["unmarked"]`·결과 화면 '메모 못 함'에 잡힌다. ★결과 화면 추가 실행은 **진짜 교정본만** 입력으로 쓴다(`MainWindow._corrected_hwp` — 1차가 `hwp`이거나 추가 실행 `hwp`가 만든 것). ⚠ `result["hwp_path"]`를 쓰면 안 된다: 1차가 메모본이면 그 칸이 `_메모본.hwp`라, 그것을 교정본으로 여겨 **교정 51건 중 0건**이 반영된 `_교정본(메모).hwp`가 나왔다(감사 실측). 교정본이 없으면 원본에서 결합 모드를 처음부터 돈다. 교정본 위에 다는 경로는 그 교정본을 만든 실행의 정오표 행을 `base_errata_rows`로 받아 메모만 겹친다 — 메모 detail로 행을 다시 만들면 빨간 자리 순번이 패널 등장 번호로 읽혀 부분 거절 시 엉뚱한 행이 실패가 된다. (그때 남은 '…해야한다.'→'…해야 한다.' 2곳 누락은 2026-10-17 좌표 방식으로 해소 — 05.hwp 68/68.)

## `result["applied"]`의 의미

⚠ **`result["applied"]` means "characters actually changed in the HWP" and that meaning is never widened** — it stays **0** in the other three modes (the completion dashboard renders "적용 N건" from it). Accepted work rides on `to_apply`/`to_apply_occ`; what was actually marked rides on `memoed`/`memo_blocked`/`annotated`/`pdf_missing`. `result_panel` swaps card 03 (정오표 / 메모 / PDF 주석) but keeps the gauge titled 교정 수락률 in all three, because that is what the gauge counts. Do **not** revive the old heuristic `flagged > 0 and applied == 0` as the mode test — that state still exists (a run where nothing was accepted) and means something different.

## 결과 화면의 '결과물 추가' · 경고/취소

**결과물은 사후에 더 만들 수 있다 — 결과 화면의 "결과물 추가"** (2026-08-07). Picking one mode used to be final: getting a second artifact meant 초기화 → re-pick → **redo the entire review**, even though accept/reject was already settled. `ResultPanel._build_outputs` (the 산출물 card) lists what was produced and offers **all four modes as buttons, always — the already-produced ones disabled** rather than removed (user directive 2026-08-12: dropping them shifted the remaining buttons on every click, and the right column alone could not say what had already been made). It only emits `extra_output_requested`, and `MainWindow._start_extra_output` runs the *same* `ApplyWorker` with `output_mode` overridden. The card is a **2-column grid — left "만들어진 것", right "더 만들 수 있는 것"** (user directive 2026-08-12): stacked in one column, the add-buttons read as more produced artifacts. Each artifact row is 형식 아이콘 + 산출물명 over its 서브 내용, with a filled accent 폴더 열기 on the right; **the file name is not printed** (the artifact name already says what it is, and long names wrapped the row to two lines). **One extra run = one row**: an extra output always carries its own errata, so the pair is merged — '메모본 + 정오표 (메모)' with both icons and both counts ('메모 61항목 · 정오표 68행'). The primary run is *not* merged: its errata is a separately toggleable artifact that may not exist. ★And `_produced_modes` treats `errata` as produced only when the errata is the **primary run's own** (`errata_path` without `errata_from_extra`) — a 정오표-off run that later adds a 메모본 gets `result["errata_path"]` filled by that memo run, and the old "any errata file exists" test then **deleted the Excel(정오표) button**, leaving no way to produce an errata for the 교정본 (user report 2026-08-12). Four invariants, each of which silently produces a wrong artifact if broken: ① **always built from the original file** — memo/PDF anchor on the 원문 string, and on a 교정본 that string has already been replaced, so it cannot be found (the original is never written to: `save_as` writes a new path and `close` is a bare `Quit`); ② **decisions are never re-asked** — `_applied_corrections` (a deep copy of the correction list) plus `_applied_occ_rows`, the snapshots taken at `_start_apply`, so partial rejects survive (★since 2026-10-23 the review cards stay editable after apply — 다시 적용 — so the live `self._corrections` may already hold newer decisions; the extra run must use the snapshot, and logs `[추가] 적용 뒤 바꾼 결정은 빠짐` when they differ — docs/ui-reference.md '검토 저장 · 이어서 하기 · 다시 적용'); ③ **the first run's numbers are never overwritten** — an extra run lands in `result["extra_outputs"]`, keeping the `applied` invariant above intact and the dashboard's 01/02/03 cards a record of the primary run; ④ **an existing errata is never overwritten** — `_extra_errata_path` names it `_정오표(메모).xlsx` etc., because the content differs per mode (PDF adds a column, memo adds 메모 불가 notes) and the user may already have the old one open. ⚠ It used to fall back to the plain `_정오표.xlsx` when the primary run had produced no errata; that exception cost a user their answer (2026-08-10). A 교정본 run with 정오표 turned off, then a memo run added: the memo errata landed on the plain name, and the 산출물 card labelled it just "정오표" with the *primary* run's row count — so "메모 불가 150곳" had its explanation sitting in a file that looked like something else and the user read it as "정오표(메모)가 생성되지 않았다". The suffix is now unconditional, and `result["errata_from_extra"]` keeps `_artifact_rows` from attributing an extra run's errata to the primary one. The extra run also passes `known_pages=result["pages_by_original"]`, so `ApplyWorker` skips the locate pass — which makes an added 정오표 open **no HWP at all** (실측 1.3s), and guarantees both errata files quote the same 쪽. ⚠ Errors take `_on_extra_error`, **not** `_on_error`: the latter returns to 설정, which would throw away the completed run's result screen because a *second*, optional artifact failed.
★**`ApplyWorker.error` means "this run ended without a result"; non-fatal problems go on `ApplyWorker.warning`** (정오표 저장 실패 · PDF 변환/주석 실패), which is always followed by `finished`. They used to share `error`: `_on_error` opened a modal and then jumped to 설정, `finished` was processed inside that modal's nested event loop and drew the result screen, and closing the modal **bounced the user back to 설정** (audit, reproduced on MainWindow). `MainWindow._on_worker_warning` only logs and collects; `_flush_warnings` shows them in one popup on the next tick after the result screen is up. ★Cancellation has one common gate after the editor/PDF stage: if `_stop` is set and no HWP output was saved, the run emits the cancel `error` and returns (deleting a just-exported, unannotated `_주석.pdf`). Before, a cancel during the page-number scan skipped the memo/PDF branch, built the errata and sent `finished` — the user pressed 취소 and got "메모본 생성 완료 · 메모 0곳".

## 산출물 카드

**The 산출물 card is the only place 완료 단계 owns artifacts** (2026-08-11, user directive). The footer's result-only actions (정오표 열기/생성 · 폴더 열기) and `StatusFooter.set_result_actions`/`errata_clicked`/`folder_clicked` are **removed** — the only footer action left on the result screen is 초기화. The card already lists every file produced with its own name and row/곳 count and opens each one's folder, so a second copy in the footer could not say *which* 정오표 it meant once memo/PDF runs add their own (`_정오표(메모).xlsx` …) and would contradict the list. `main_window._on_generate_errata_requested` (manual errata build) went with it: the card's 결과물 추가 → `errata` runs the real `ApplyWorker` with `output_mode="errata"`, so 쪽 번호와 적용 결과가 실제 실행에서 나오고 파일 이름이 출처를 밝힌다 — the manual path blanked 쪽 when it had no row data and wrote the ambiguous plain name. The four 결과물 추가 buttons carry **원색 파일형식 아이콘** (`assets/icons/hwp·memo·pdf·excel.svg`, mapped in `ResultPanel._OUT_META` **and `SetupPanel._OUTPUT_CARDS` — the two screens must picture the same choice identically, same rule as the shared names**); those SVGs have no `currentColor`, so `icons.pixmap`'s recolor is a no-op and they stay brand-colored in both themes — intended, and the reason no icon role is chosen there. ⚠ That also means a **locked** choice card would not dim its icon, so a future locked 결과물 value needs a line icon or another lock cue. ⚠ Their height **must** be set as `min-height` inside the button's own QSS: a stylesheet-styled widget has its minimum size recomputed from the QSS box model, so the global `QPushButton{min-height:18px}` beats `setMinimumHeight()` — a 46px button rendered 24px tall with the icon filling it (measured).

## 바뀐 곳만 칠한다 — 교정문 전체가 아니라

★**교정본의 빨강(과 형광펜)은 교정문 안의 바뀐 곳에만 남는다** (사용자 요청 2026-10-22: "'기술 개발' 전체가 빨가면 교정본만 본 사람은 무엇이 틀렸는지 모른다"). 판정은 브리지 `_red_spans(원문, 교정문)` 하나다 — 글자를 바꾸거나 넣은 곳은 그 글자('리플렛'→'리플릿' = '릿', 괄호 보충 = 그 괄호), **공백만 넣거나 뺀 곳은 양옆 한 글자씩**('기술개발'→'기술 개발' = '술 개', '소재 (36건'→'소재(36건' = '재(', '),센'→'), 센' = ', 센' — 공백은 칠해도 안 보인다), 글자를 지운 곳은 지운 자리 양옆. 띄어쓰기만 다르면 SequenceMatcher 대신 글자를 하나씩 짝지어 공백열을 견준다(되풀이 글자에서 엉뚱하게 정렬하지 않게). 치환 방식은 그대로다(매치 전체 `InsertText` → 글자모양 스냅샷 되씌움) — **칠하기만** 좁혔으므로 교정본 계획(`_plan_by_replay`)·좌표(`spots`)는 무관하다.
- **보통 자리**: 예전처럼 교정문 전체를 칠한 뒤, 바뀌지 않은 조각만 같은 스냅샷 객체에 **원래 글자색**을 넣어 되씌운다(`_recolor_outside` — 결과가 원래 글자모양과 같아 원래 id로 돌아간다). 조각을 고르지 못하면 그 조각은 빨간 채로 둔다 — **덜 칠하는 쪽으로는 무너지지 않는다.**
- **글자 스타일 자리(형광펜)**: 형광펜은 지울 길이 마땅치 않아 순서가 반대다 — 스냅샷 되씌움(전체) 뒤 바뀐 조각에만 칠하고, 한 조각이라도 못 고르면 전체에 칠한다(`_markpen_spans`).
- 조각 선택은 치환 전 선택 되살리기와 같은 방식(`SetPos` + `MoveSelRight` + 커서 위치 확인)이고, 교정문이 `[시작, 시작+길이)`에 그대로 들어갔음이 확인된 자리(`ins_ok` — `spots` 기록과 같은 조건)에서만 한다. 문단을 넘는 교정문(`\r`)은 예전처럼 전체를 칠한다. 끝나면 커서를 칠하기 전 자리로 되돌린다 — 다음 찾기가 같은 자리에서 이어져야 `_BridgeReplay`가 맞는다.
- ★'교정본+메모'의 빨간 글자 찾기 폴백(`memo_scan` · `_match_is_red`)은 선택 전체의 색이 섞인 값이 되므로, `anchor_of`(원문)로 같은 `_red_spans`를 다시 계산해 **칠한 글자 하나를 골라** 읽는다(`red_at`). ⚠ 고르지 않고 커서만 두고 읽지 말 것 — 한/글 2010은 선택이 없으면 **커서 앞 글자**의 모양을 준다(실측: 위치 i에서 글자 i−1, 문단 첫머리만 글자 0). 그 앞 글자는 칠하지 않은 글자다.
- 실측(2026-10-22, 시험 원고 · HWPML로 런 판독): `소[재(]36건, 25.7%)[, 센]서 및 제[어(]35건` · `기[술 개]발` · `리플[릿 등]` · `협력해[야 한]다` · `[(]고립예방센터)`(자기 재매칭) · `[콘]텐츠를` — 6항목 7곳 전부 의도대로, 치환 실패 0. 같은 교정본에 빨간 글자 찾기로 메모를 달면 원래부터 '기술 개발'·'협력해야 한다'로 쓰인 앞 문단은 건너뛰고 7곳 모두 교정 자리에만 달린다. 형광펜(05.hwp 글자 스타일 런 · `.hwpx`로 저장해 `<hp:markpenBegin>` 판독 — HWPML2X는 형광펜을 담지 않는다): `Tabl{e2}.` · `Figure 1{:}` · `(High{,H}igh)`, 글자모양 id 원본과 동일. E2E 05.hwp 수치 기준선과 동일.
- ⚠ **알려진 한계(기존 결함, 미수정)**: 텍스트에 글자 스타일 참조가 직접 붙은 런(`.hwpx`의 `<hp:t charStyleIDRef=…>`)은 형광펜이 **아예 칠해지지 않는다** — 부분이든 전체든, 이 변경 전 코드도 같다. 브리지는 `pen=True`로 보고하므로 교정본에 **표시 없이** 남는다(예: 05.hwp 참고문헌 이탤릭 제목). 05.hwp에 그런 텍스트 런 93개. 같은 글자모양이라도 참조 없는 런은 칠해진다.

## 빨강 대신 형광펜 — 글자 스타일 보존

★**교정본의 빨강은 원고의 글자 스타일을 해제한다 — 그래서 스타일이 걸린 자리는 빨강 형광펜으로 표시한다** (사용자 보고 2026-09-10). HWP 5.0 파일에는 "이 런은 어떤 글자 스타일이다"라는 참조가 **없다**: 런의 `charShapeId`가 그 스타일의 `charShape`와 **같을 때만** 그 스타일로 인식된다. 그래서 글자색만 바꿔도 한/글이 '원래 모양 + 빨강'인 **새 글자모양**을 만들어 물리고, id가 달라지는 순간 스타일이 풀린다(실측: 본문강조 cs#48 → 색만 다른 cs#278. 사용자 파일 한 개에서 35곳 — 표볼드 6·박스볼드 2·본문강조 5·본문강조(제목) 5·※글자 17. 표본 19개 중 글자 스타일을 쓰는 원고가 18개라 전 원고에 해당한다). **빨강과 스타일 소속은 글자모양 id 하나를 두고 다투므로 양립 불가**다(스타일 재적용도 실측 — 빨강이 지워지고 원래 id로 돌아간다). 해법은 표시 수단을 바꾸는 것이다: **형광펜은 글자모양이 아니라 런 안의 별도 요소**(`<TEXT CharShape="7"><CHAR><MARKPENBEGIN Color="255"/>…`)라 스타일을 건드리지 않는다. 판정은 [core/hwp_styles.py](../core/hwp_styles.py)가 **파일을 직접 읽어**(COM 아님 — `GetTextFile("HWPML2X")`는 큰 문서에서 `None`을 돌려준다. 실측: 322쪽 문서에서 실패) 만든 글자모양 **지문**을 브리지가 매치 자리 지문과 견주는 것이다. ⚠ 지문에서 필드를 빼지 말 것 — 장평·자간·상대크기·글자위치를 빼면 오탐 +19,327건, 밑줄모양~아래첨자 비트를 빼면 +19,299건(전체 3,496건 대비). 현재 구성의 오탐은 **+3건(0.09%)**이고, 오탐의 대가는 '빨강 대신 형광펜'뿐이라 무해하다. ⚠ 세 가지가 순서·객체까지 load-bearing이다: ① 글자모양은 **매치 시작 커서**에서 읽는다(한/글은 커서 **뒤쪽** 글자의 모양을 준다 — 찾기 선택 위에서 읽으면 글꼴 이름이 빈 섞인 값이 오고, 매치 끝에서 읽으면 **다음 런**의 모양이 온다. 실측으로 start·start+1만 맞았다); ② 읽은 뒤 `MoveSelRight`로 선택을 되살리고 **커서 위치로 확인**한다(`SelectText`는 개발 환경에서 예외를 던진다. 선택 없이 `InsertText`를 하면 치환이 아니라 **삽입**이라 원고가 오염된다 — 확인 실패 시 재탐색, 그래도 실패면 그 항목은 적용하지 않는다); ③ 되씌울 때 **떠 둔 파라미터셋 객체 그대로**를 Execute한다(`HParameterSet.HCharShape`를 다시 꺼내면 빈 셋이 와서 **예외도 로그도 없이** 아무 일도 안 한다 — 실측). ★그리고 이 스냅샷 되씌움은 **독립적인 두 번째 버그도 고친다**: 원문이 런 전체를 덮으면 `InsertText`가 새 글자에 **옆 런의** 글자모양을 물려, 색을 안 칠해도 글꼴이 바뀐다(실측: 'Figure 1.' KoPub돋움체 **Bold** → **Light**). ★**`hwp_memo`(빨간색+메모)는 형광펜 자리도 치환 좌표(`spots`)로 간다** — 빨강이든 형광펜이든 같은 좌표다(실측 24만 자 원고: 형광펜 17곳 전부 메모 · 예전엔 일부 누락). 아래 문단 좌표(`pen_paras`)는 **좌표를 확인하지 못한 항목의 빨간 글자 찾기 폴백**에서만 쓰인다. `_match_is_red`는 형광펜을 **인정할 수 없다** — `HMarkpenShape.Color`는 선택 자리의 형광펜이 아니라 **마지막으로 쓴 펜 색**을 돌려주므로(실측: 칠하지 않은 자리에서도 255) 그 값을 믿으면 모든 자리가 통과해 메모가 엉뚱한 자리에 박힌다. 다른 길도 전부 막혔다: 선택 블록만 HWPML로 내보내기(`saveblock:true`)는 형광펜을 담지 않고, `MarkPenPrev/Next`는 **자기 형광펜을 건너뛰는 경우**가 있어 자리 판정에 못 쓴다(둘 다 실측). 그래서 `apply`가 형광펜을 단 자리의 **문단 좌표**(`detail["pen_paras"]`)를 돌려주고, 메모 단계가 빨강 필터에 걸린 매치를 그 문단에서 만나면 우리 자리로 인정한다(`_consume_pen_para`). ⚠ **글자 위치가 아니라 문단 번호만** 쓴다 — 뒤이은 치환이 글자 위치는 밀지만 문단은 만들거나 없애지 않는다. ⚠ 이미 인정한 문단도 True로 돌려줘야 한다: 재탐색 패스에서 걸러 버리면 `reskip_left`에 닿지 못해 **등장 계수가 어긋난다**. ⚠ 치환 직후 그 자리에 바로 메모를 다는 길은 **기각**됐다 — 되긴 하지만(실측 ok=True) 메모 컨트롤이 글자 사이에 끼어들어 **같은 문단의 뒤이은 치환이 실패**했다(실측). 실측(실파일I, 형광펜 9곳): 메모 10/10곳 · 메모 컨트롤 +10 · 스타일 손실 0. 결과 화면의 '결과물 추가' 경로도 1차 실행의 좌표(`base_spots`)로 간다 — 좌표가 없을 때만 형광펜 자리를 잃는다.

**`.hwpx`도 같은 방식으로 보호된다** — [core/hwp_styles.py](../core/hwp_styles.py)가 ZIP 안 `Contents/header.xml`(OWPML)에서 같은 지문을 만든다. 검증은 **같은 원고를 두 형식으로 저장해 지문 목록이 한 글자도 다르지 않은지**로 했다(표본 3개·56종 전부 일치). ⚠ 그 과정에서 잡은 함정 셋: ① 꺼져 있는 속성의 색은 **0으로 눕혀야** 한다(.hwp는 밑줄이 없어도 밑줄색을, 그림자가 없어도 그림자색을 들고 있는데 OWPML은 요소 자체가 없다 — 안 눕히면 23종이 전부 어긋난다); ② 선 모양 **실선(SOLID)은 0**이다; ③ **취소선은 바이너리에서 '밑줄 종류 2'로 들어간다**(OWPML은 `<hh:strikeout>`로 따로 적는다). ⚠ hwpx에는 `<hp:t charStyleIDRef>`라는 명시적 스타일 참조가 **있지만 지킬 수 없다** — 편집 없이 열었다 저장만 해도 134→104로 줄어드는 한/글 자체의 손실이다(실측). 우리가 지킬 수 있는 것은 `.hwp`와 같은 **charPr 동일성**이고, 형광펜이 그것을 지킨다(실측: 빨강은 새 charPr 109를 만들고 형광펜은 스타일의 charPr 1을 유지).

## 메모 모드

**메모 모드** goes through three bridge commands — `memo_scan` (find only, no memo) → `memo_keys` (document-order key for substory spots) → `memo_place` (go to each coordinate and attach, **zero finds**) — driven by `HwpEditor.insert_memos`. Three invariants from the first design still hold — see the memo header in `hwp_bridge_worker.py`: ① use `HAction.Run("InsertFieldMemo")`, **never** the top-level `hwp.Run(...)` (a no-op on HWP 2010 that returns `None` for everything, so a following `InsertText` writes the reason **into the manuscript**); ② verify the memo actually opened by checking that `GetPos()[0]` (story) changed, not the return value; ③ 머리말·꼬리말·캡션류 stories **refuse** memos — a structural limit, counted as `blocked` and written to the errata (stories the edit cursor cannot even enter — `MoveSelRight` does not move — get the same note). The two-phase design adds three more: ④ **no find after the first memo** (next paragraph); ⑤ **attach back to front** — one memo shifts its own paragraph (anchor start +8, text after the anchor +16: field begin/end) **and every later substory's list id by +2** (measured: one body memo → table cells 26→28, 110→112), so placing from the end leaves every pending spot untouched; that is why substory spots need `memo_keys` (`CloseEx` out to the body position of their control); ⑥ **verify before attaching** — select the anchor length from the coordinate and require the exact end position and the anchor text, else skip with a '글자가 예상과 달라' note. ⚠ `GetTextFile("TEXT","saveblock")` returns some symbols as **HTML numeric references** ('≈' → `&#8776;`, so it is `html.unescape`d) and **prepends the auto-bullet glyph** for any selection in a bullet paragraph ('◯ 주요내용' — the bullet is a paragraph attribute, not a character), which is why the check is "ends with the anchor" given the exact end position. ⚠ **Never verify by counting memos** — count distinct spots; the cheap COM check is a `HeadCtrl` walk over CtrlID **`%%me`** with `GetAnchorPos`, reading the text after each field begin (sanity script pattern used 2026-10-17). Anchor text is never recolored (user directive 2026-08-07: the manuscript's formatting is part of the manuscript), and the memo body carries **no '이 낱말 N곳 중 k번째' line** (user directive 2026-08-10 — the errata already says that, one row per occurrence; the PDF annotation dropped its '· 이 낱말 N곳' line for the same reason). ⚠ The memo and PDF bodies are built by **one function, `output/annot_text.annotation_body`** — they must say the same thing, and building them separately is how they drifted. It drops the `[검수]` tag (user directive 2026-08-11: a memo/annotation artifact *is* the review list, so tagging every line 검수 says nothing) and collapses the duplicated type label — the pipeline's reasons often re-state their own category, so `[규범표기]` + `[규범표기] 규범표기인 '슈퍼마켓' 권장` printed 규범표기 **three times** on one line; the leading tag is stripped and the category prefix omitted when the reason already opens with it.
★**Searching a document that already holds memos poisons the HWP session — that, not a stale find index, is why memo runs lost half their memos** (re-diagnosed 2026-10-17 by controlled experiment on a 24만 자 원고's 교정본: 메모 48곳 + 찾기 300회 → fine · 메모 0~5곳 + 찾기 2,000회 → fine · **메모 48곳 + 찾기 2,000회 → every later memo dies** with `RPC_E_SERVERFAULT` in `InsertText`, page and position irrelevant, color reads irrelevant, until the document is closed and reopened). The old design (each item re-scans from the document start and attaches as it goes) therefore always collapsed as memos accumulated, and `"hwp_memo"` collapsed fastest because its anchors are common corrected strings ('자녀 출산', '정책 효과') with thousands of non-red matches to walk past. The old explanation — "a memo control is invisible to `RepeatFind`, so overlapping words fail" — described the *first* failure on one path; the cascade after it was the poisoning, and the old fix `HwpEditor._reindex_document` (save → close → reopen every 25 items / 40 memos) merely washed it out periodically (also why tightening the threshold or reordering items never helped). The periodic reindex and its constants are **removed**; with no finds after the first memo there is nothing to wash out on a normal manuscript (0 faults in ~4,800 placements over 7 manuscripts). What is left is a **fault-triggered** net: `memo_place` stops at the first `RPC_E_SERVERFAULT` (`poisoned`), and `HwpEditor._reopen_document` saves to a stage file in `cache_dir()`, closes, reopens and continues (≤ `_MEMO_MAX_REOPENS`; back-to-front order keeps every pending coordinate valid). It exists for manuscripts that **already carry many memos**, where the scan's finds alone poison the session before the first placement. Measured old → new (memo / missed spots, same decisions, real 한/글 2010): 24만 자 원고 교정본+메모 291/331 (339s) → **609/13** (157s) · same with every 4th card rejected 582/510 (460s) → 1069/23 (258s) · 메모만 577/45 → 609/13 · 결과 화면 추가 260/374 → 609/13 (66s) · 21만 자 원고 교정본+메모 794/197 (589s) → 983/8 (279s), 메모만 871/120 (427s; one old run **crashed** — bridge died) → 983/8 (177s) · 27만 자 원고 교정본+메모 809/123 (473s) → 930/2 (242s) · hwpx 원고 교정본+메모 290/10 → 300/0, 메모만 300/0 → 300/0 (79s → 44s) · 다른 hwpx 247/9 → 255/1 · 05.hwp 58/10 → 68/0, 부분 거절 47/15 → 62/0. 교정본 글자는 옛 코드와 **완전히 같다**(SHA-1 일치 — `apply`는 좌표 기록만 덧붙였다). What remains is structural (memo-refusing caption/text-box/header stories) plus one representation edge (a word stored as decomposed jamo `ㅍㅠㄱ스` cannot equal the composed anchor in the text check). ⚠ Do not reintroduce finds after attaching memos (a "re-scan the failed spots" sweep included), and do not reintroduce periodic reopen as a "safety net" — it hides the cause and costs ~15s per cycle on large files. ⚠ `HwpEditor.open()` still clears `_stderr_stop` and drains both queues (harmless now, required if an editor is ever reopened). ⚠ Manuscripts that already carry memos (e.g. a 메모본 fed back in) remain out of scope (the 폐기된 '메모 달린 원고 재교정' case): their memo bodies are in the extracted text, so the scan treats them as occurrences and attaching inside a memo body faults — the reopen net only limits the damage (measured on a 245-memo file: old 73 → new 97 of 353).
⚠ **memo and PDF skip `shadowed` occurrences; the 교정본 does not** (`ApplyWorker._annot_skip_for`). One spot gets one mark, the errata already omits shadowed rows, and marking them would both re-introduce an artifact divergence and create the overlapping-anchor collision above. Replacement keeps them because a longer correction may leave the substring intact for the shorter one to normalize (`ReviewPanel._derive`).

## PDF 모드

**PDF 모드** exports via bridge `export_pdf` (⚠ clear the selection first — a live selection makes HWP export **only that range**, returning True either way) and then annotates with [output/pdf_annotator.py](../output/pdf_annotator.py) (`pypdfium2` search + `pypdf` write; both BSD — ⚠ never PyMuPDF, it is AGPL). ⚠ `FreeText` annotations render **empty** for Korean (no embedded font in the appearance stream) — use `Highlight` (which carries the note in its own `/Contents`) or `Text` sticky notes. ★**One correction spot = exactly one annotation**: the highlight holds the text, so pairing it with a sticky note doubles every row in the viewer's 주석 목록 (290 rows for 145 corrections — user report 2026-08-08). The hard part is occurrence alignment: a running head lives once in the HWP story but is rendered on every PDF page, so matches repeating at the same **(x, y)** across ≥3 pages are dropped as running heads (y alone also drops body lines); if the counts still disagree, index mapping is abandoned and **every** occurrence is annotated with a visible 자동 대조 실패 warning rather than silently guessing. ⚠ The errata's `PDF 쪽` column is a **separate coordinate system** from `쪽` (prnpageno) — never compute one from the other.

## 세 산출물은 같은 자리를 표시한다

★**The three artifacts must mark the same spots** (2026-08-08 — user report: "반영된 항목이 다 다르다, 신뢰성에 치명적"). They drifted for two independent reasons, both now fixed, and the shared rule that came out of it is: **the occurrence coordinate system is what the bridge's `RepeatFind` sees on the unmodified document** — i.e. `locate_originals` — *not* `Correction.occurrences`, which the review panel counts over the *extracted text*. Both `memo` (`occ_cap`) and `pdf` (`_align_occurrences`) now take `doc_occ = len(pages_by_original[original])` as their bound; 실측 05.hwp: '지속가능항공유' is 5곳 in the extracted text but 4곳 in the document, and the memo pass used to run to 5 and mark one spot the other two artifacts never touched. ⚠ The second cause was PDF-only and worse: **pdfium's `search()` ignores whitespace** — `'국방 분야'` and `'국방분야'` returned *byte-identical* result sets (33 matches), so a 띄어쓰기 correction accepted at 2곳 got highlighted at 25곳. `_search_all` now reads back `get_text_range(idx, cnt)` and drops matches whose spacing differs (`_spacing_ok`), tolerating only whitespace introduced by a line break (`'엔\r\n진 부품'` is a genuine '엔진 부품'). ⚠ That line-break tolerance had a false-positive twin, fixed 2026-08-10: '도움요청'→'도움 요청' (문서 4곳) matched **5** places in the PDF because a correctly-spaced '도움 요청' on p.114 happened to break across a line, so deleting the break made it read '도움요청'. The count mismatch then failed alignment and stamped "⚠ 위치 자동 대조 실패" on *all four* good highlights plus the bogus one. Matches now carry `exact` (the glyphs matched literally) and `_drop_ambiguous` discards the line-break-only ones **when, and only when, the remaining exact matches equal `doc_occ`** — evidence, not preference. It never fires when matches are already correct or too few, so the genuine `'엔\r\n진 부품'` case survives (verified on the same PDF: '도움 요청' 8곳 keeps its one line-broken match). ⚠ Two differences remain and are **legitimate, named, and recorded per-occurrence in the errata** — never "fix" them by making the counts equal: ① 검수 항목 (`dict_flag`, corrected == original) is marked in memo/PDF but **not** in the 교정본, because 빨강 means "이 자리를 고쳤다" and nothing was; ② 머리말·꼬리말 spots accept a replacement and a PDF highlight but **refuse a memo**. The errata's outcome class is identical across all three (`applied`↔`todo` is the same decision, worded for who does the work), and anything a mode could not mark carries a `note` and is counted in `result["unmarked"]` — the memo/PDF equivalent of the 교정본's S4 부분 반영 safety net, without which a missed spot reads as a completed one.

## 옛 검수 모드(폐기)

⚠ The old dictionary-only 검수 모드 (entered by "selecting 0 AI scopes") is gone: that entry path was unreachable — `scopes_selected()` gates 분석 시작, and 윤문 is locked, so a scope is always on — and its `nikl_dict.extract_flags` was deleted 2026-10-18. Its successors are the `errata` output mode (HWP not modified; it *is* opened read-only for page numbers) and the 'AI 분석 제외' option. `docs/proofreading-architecture.md` records it in its removal table.

## 정오표 — 등장 단위 · 쪽 번호

**The errata is per-occurrence, keyed by 한/글 page number** (2026-08-05 rework). One row = one physical spot in the manuscript, so a word corrected in 12 places yields 12 rows — which is also what makes a partial reject legible (the accepted spots land in 적용, the rejected one in 거절). Sheets split by outcome — 적용 / 거절 / 확인 필요 (실패+검수), created only when non-empty — and every sheet carries the same five columns 쪽·수정 전·수정 후·교정 이유·교정 유형 so they can be concatenated. ⚠ Manuscript strings must never be interpreted by Excel: `errata_generator._wcell` strips openpyxl's illegal control characters (**one** of them used to abort the whole errata with `IllegalCharacterError`) and pins any `=`-leading value to a string (openpyxl stores it as a formula → `#NAME?`/`#REF!`). 교정 유형 is `Correction.category` (맞춤법·띄어쓰기·규범표기…); the *source* is carried by row background color instead, which is why the old 출처 column is gone (it duplicated 교정 유형, both being the source label).

⚠ **The page number is `KeyIndicator()[3]` (prnpageno) — the coordinate 한/글's own Ctrl+G navigates by** (verified: `Goto` 10 lands on prnpageno 10), so a user can type an errata number straight into 쪽 찾아가기. It is deliberately *not* an absolute page count: it honours per-구역 renumbering, so it is neither globally monotonic nor unique (실측: 실파일F ends at prnpageno 152 with `PageCount` 160; 실파일G starts at 2). **Never sort or do arithmetic on it.** ⚠ **Pages must be collected from one pre-apply snapshot** (`HwpEditor.locate_originals` → bridge `locate`, find-only, document unmodified): replacements repaginate as they go, and apply runs in longest-original order, so pages read *during* apply drift out of step with each other (실측: the 12th occurrence of a word moved 15쪽 → 16쪽 mid-run). The bridge's `apply` still records `occ_pages` per match — but that is used to decide **which occurrence was actually replaced**, with its page only a fallback. `KeyIndicator` costs 0.13ms so it rides along free; the cost is `RepeatFind` (~9ms/occurrence measured over 297 occurrences), bounded by `_LOCATE_BUDGET`/`_LOCATE_SECONDS` — exhausting them blanks the 쪽 cell ("—") and never drops a row. `HwpxEditor` (direct backend) has no `locate_originals` at all: it edits XML with no layout engine, so page numbers are unknowable there and every 쪽 reads "—".

## 등장 좌표 · 교정본 적용 계획

★**`skip_occurrences` lives in the pre-apply coordinate system, and apply invalidates it** (fixed 2026-08-08 — user report: "교정본에만 '해야한다'가 미반영"). `apply_corrections` replaces **longest original first**, so by the time a short original runs, every occurrence of it that sat inside a longer *applied* correction is **gone from the document** — the survivors renumber, and the old indices then point at innocent spots. 실측: '해야한다' 14곳 중 5곳이 '고려해야한다' 등에 먹혀, skip `[5,8,9,11,12]`가 남은 9곳(0..8)의 5·8번을 건너뛰어 **멀쩡한 2곳이 교정본에만 안 고쳐진 채 남았다**. `ApplyWorker._plan_occurrences` now recomputes this: it takes the occurrence spans (`pos`/`end`, newly carried by `get_occurrence_rows`), drops the occurrences that a *different* accepted correction's span fully contains, and renumbers the rest — so `skip` is expressed in the coordinate system the bridge will actually see. ⚠ **Never "fix" this by just clearing `skip_occurrences`**: it carries three different things — user rejections and `excluded` substring hits both **survive** the replacement and must keep being skipped; only the ones a longer *applied* correction swallows disappear. Dropping all three would replace spots the user explicitly rejected. ⚠ The remap runs for the text-modifying modes **only** (`MODIFY_MODES` = `hwp`·`hwp_memo`; written `mode == "hwp"` before `hwp_memo` existed) — memo/PDF never change the document, so their occurrences never vanish and remapping there would itself desync them. `_build_errata_rows` translates bridge indices back through the same map (`survivors`), and S4's expected counts use the post-remap totals so a normal run no longer reads as 부분 반영.
★**When the bridge finds fewer occurrences than the panel expects, the errata realigns by 쪽, never by position** (`_realign_by_page`, 2026-08-10 — user report: "94쪽 리플렛 2개는 치환 성공인데 정오표엔 실패로 나온다"). HWP's 찾기 cannot reach some spots at all (auto-bullet paragraphs — memory `find-blindspot-auto-bullet`), so the bridge's occurrence list is simply shorter. Pairing the two lists by order then shifts everything after the first gap, and the *last* rows get blamed instead of the missing ones: 실측 '리플렛' 15곳 → 4 absorbed by longer corrections → 11 expected, 9 found; the 교정본 actually kept 51·69쪽 unfixed while the errata marked 94쪽 ×2 as failed. 쪽 is the only coordinate both sides share, so the alignment walks both in document order and skips panel occurrences whose 쪽 does not match. ⚠ It is accepted only when it explains the gap exactly (leftover bridge entries, or an unfound count ≠ the size difference, means the alignment is wrong) — otherwise it falls back to the positional map rather than guessing.
★**The rule for "is this occurrence skipped" has exactly one implementation: `core.models.occurrence_skipped`** (fixed 2026-08-10 — user report: PDF missing a '고립예방'→'고립 예방' annotation). Two layers were deciding it independently: `ReviewPanel._derive` (`excluded` ⇒ skip, `shadowed` ⇒ don't) and `_plan_occurrences` (which looked only at `status != "accepted"`). Consistency unification (`_apply_unify` — at the time `_apply_unify_forward`) marks **every** occurrence of a consistency group accepted — including `excluded` ones — so the moment the remap fired, every excluded occurrence became a replacement target: '고립예방' was accepted at 3 spots in the review panel and the PDF annotated exactly those 3, while the 교정본 replaced **all 10** ('고립예방사업'→'고립 예방사업', '고립예방플랫폼'→…). The 교정본 was the wrong one; the PDF was right. Both layers now call the shared predicate, so fixing one can no longer be silently undone by the other. ★A second, independent shift in the same remap was found by re-running the same file: an occurrence contained in a longer applied correction **only disappears if that correction's replacement removes it**. `'고립예방센터)'→'(고립예방센터)'` merely adds a paren, so '고립예방' is still there and `RepeatFind` still finds all 10 — while `skip` had been computed for 9, shifting every index by one. 실측: 수락 {3,4,7} → 교정본이 바꾼 자리 **{2,3,6,9}** (수락한 2곳 누락 · 등장 아닌 3곳 오적용). The test is now `orig not in wc`, which still catches the case the remap was built for ('해야한다' inside '고려해야한다'→'고려해야 한다', where the substring genuinely dies).
★★**The 교정본 plan is a replay of the bridge loop, not a remap** (`ApplyWorker._plan_by_replay`, 2026-10-17 — audit 치명 3, confirmed real: in 8 real-HWP E2E runs the simulator's prediction equalled the actual 교정본 character for character; the old plan produced 13·128·5 mismatched spots while the app reported 실패 0 · 부분 반영 0). The remap above only knew occurrences that *vanish*; four other paths desynced the bridge's match sequence from the panel's: ① an earlier (longer) correction **creates** a shorter one's original ('고용복지 정책'→'고용복지정책' makes '복지정책', which '복지정책'→'복지 정책' re-splits — the shift then skips accepted spots and splits the stem-boundary-protected '고용복지정책'; happens with **zero** rejections), ② a hidden (shadowed) inner card applied where the visible outer was rejected or is a 검수 필요 card ('출산월' 속 '월이→다리' → '출산다리'), ③ **partial** overlaps — the panel hides one of two overlapping cards, the bridge applied both (user decision 2026-10-17: apply **only the visible card**, as errata/memo/PDF already do), ④ HWP find is **ASCII case-insensitive** (measured: 'AI' also finds 'ai' — 2,101 vs 2,061) while the panel is not. The plan therefore replays `HwpBridge.apply` on the extracted text (`full_text` — `MainWindow` must pass it at **both** ApplyWorker constructions): same length-desc stable order, sequential find from the start, case folding, multi-pass reskip, self-matching single pass (★judged **case-folded** on both sides since 2026-10-22 — HWP find ignores ASCII case, so a case-only fix like 'TRaining'→'Training' (guard ⑭'s Shift-typo carve-out, a real high card in the corpus) re-found its own insertion and was replaced at the same spot up to the 1,000 cap: measured on a real manuscript's English reference title, 'X Drives'→'X drives' = 1 spot → 1,000 replacements, identical before and after the partial-red change), `_clean`, caps — and replaces a match **only if it is untouched original text at a visible accepted occurrence** (`not occurrence_skipped(r) and not r["shadowed"]`, not absorbed); everything else goes into `skip`. ⚠ Two guards: a correction whose intended spots the replay cannot all reach falls back to `_plan_occurrences_legacy` (0 in the 20-manuscript corpus), and a correction whose plan equals the no-plan path stays out of the plan (3,410 of 3,560 keep the exact old path). ⚠ `_BridgeReplay` must mirror the bridge loop and `_BRIDGE_INVISIBLE` must equal `hwp_bridge_worker._INVISIBLE_RE` — change one, change the other. `survivors` may now hold `None` (a created match with no panel spot); `_build_errata_rows`/`_realign_by_page` handle it. S4 now also flags **over**-replacement (`got > exp`) — it used to check only `got < exp`, which is why all of the above read 실패 0. Measured: 20 manuscripts × 2 scenarios 불일치 35·423곳 → 0, planning ≤0.6s on 268K chars. ⚠ Verify with real clicks (`ReviewPanel._set_status` with the popups auto-answered) — there is no bulk-accept path: the uncalled `_accept_all`/`_reject_all`, which set junction groups contradictorily, were deleted 2026-10-18; don't simulate "accept all" by writing statuses directly. ⚠ The `hwpx` direct backend ignores `skip_occurrences` entirely (pre-existing limit).

## 겹치는 교정의 자리 합성

★**Overlapping corrections are composed into one spot, not raced** — `ApplyWorker._compose_spots` (2026-08-10, user report "세 산출물의 정합성이 맞지 않는다"). `Correction` is *one original → one corrected*, so a word cannot have a different result per position. But overlap makes exactly that happen: '리플렛' is '리플릿' normally, yet inside '리플렛등'→'리플렛 등' it is part of '리플릿 등'. The old model raced them (longest span wins ⇒ `shadowed`) and the workaround leaked differently into each output — the 교정본 replaced twice and produced the composed text, the errata dropped the shadowed row so the composition went **unrecorded**, and memo/PDF did not mark the spot at all. Four outputs, three answers. Now a pre-pass folds each overlap group into a single composed edit: the outer correction replaces the whole span with the composed string in one operation, the inner occurrences are marked `absorbed` and skipped in **every** mode, and errata/memo/PDF all quote that one string. ⚠ **Not composing is not an option** — outer-only gives '리플렛등'→'리플렛 등', leaving the typo in place; this is a correctness bug before it is a consistency bug. ⚠ Scope is **inside an already-accepted correction span only** (user directive): there the editor has already decided to change that region, so even a fragment that `_mark_stem_boundary_skips` marked `excluded` is composed in ('고립예방' inside '고립예방센터)' ⇒ '(고립 예방센터)'), while the same fragment **outside** any accepted span stays protected ('고립예방' inside '고립예방사업' is untouched). ⚠ Composition is **declined when a correction's occurrences would compose differently**, because one `Correction` cannot carry two results — picking one would corrupt the other spots. 실측 (실파일 고독사): 14 overlapping spots, 5 corrections composed / 6 occurrences absorbed; the other 8 spots needed nothing because the outer already subsumed the inner ('고독사예방 홍보'→'고독사 예방 홍보').
★**The composition happens in the review panel, so the card shows what will actually happen** (`ReviewPanel._compose_overlaps`, 2026-08-10 — user report: "애초에 검수 카드에 '리플릿 등'으로 제안하지를 않네, 그래서 사용자가 '리플렛 등'으로 수락"). Composing only at apply time left the card advertising '리플렛 등' — the dependent-noun spacing card's own mechanical output — while the document ended up '리플릿 등'. **That is worse than an artifact mismatch: the user's decision rests on a string that will never exist.** So `_derive_all` recomputes it on every status change and `_sync_corrected_widgets` updates the field in place. ⚠ It is **reversible**: rejecting the inner card ('리플렛'→'리플릿') returns the outer card to '리플렛 등', which is why the pre-composition value is kept in `_compose_base` and recomputed rather than written once. ⚠ A card the user edited by hand (`_edited`) is never overwritten. ⚠ **When the outer card is a 검수 필요 card (`dict_flag`, 원문 = 교정문), `excluded` fragments are not composed** (user decision 2026-10-17). The "compose excluded fragments inside an accepted span" rule rests on "the editor already chose to change that span", and accepting a 검수 필요 card only means "checked" — without this, accepting '국가형긴급복지지원' (검수) spaced it to '국가형긴급복지 지원' via the stem-boundary-protected '긴급복지지원'→'긴급복지 지원'. Same-span duplicates ('테이블수' 검수 + '테이블수'→'테이블 수') are still composed — that just shows the spacing card. ⚠ Containment is found by an **O(n log n) stack sweep cached in `_ov_pairs`** (invalidated whenever occurrences are created or a reverse correction joins) — the naive pairwise scan is O(occurrences²) and would add hundreds of ms to every click on a 3,800-occurrence manuscript (measured here: 4,000 occurrences → 3.1ms first call, 1.0ms cached). ⚠ **The card value is canonical — `ApplyWorker._compose_spots` no longer composes** (2026-10-17): recomposing on top of the panel's value applied self-matching inner cards (괄호·따옴표 보충) a second time (card '포함))' → 교정본 '포함))))') and composed where the panel had declined. It now only marks inner occurrences absorbed by an **applied** (visible accepted) composed outer — counting an excluded outer once dropped a visible accepted card from the 교정본. ⚠ The panel must recompose after every status/value change: `_set_status` and `_on_corrected_edited` call `_compose_overlaps()` (<1ms at 1,900 occurrences) — before, rejecting the inner card with normal clicks left the outer showing and applying the rejected change (7 of 35 targeted cases). Residual, out of scope: `_compose_overlaps`' position-blind `replace(…, 1)` can itself compose a self-matching inner at the wrong place (one manuscript, one card).

## 등장별 결정의 정본 · 모델 위치

⚠ `ReviewPanel.get_occurrence_rows()` is the only truthful source for per-occurrence decisions — `skip_occurrences` alone **cannot** be inverted, because it mixes user rejections with `excluded` positions (a substring hit that was never a real occurrence, e.g. '성장단계' inside '성장단계별'). Writing those to the errata as 거절 would record a decision the user never made, so `excluded` and `shadowed` occurrences are dropped from the errata entirely.

The `Correction` dataclass and highlighting colors (Windows COLORREF) live in [core/models.py](../core/models.py). All API/chunk/throttle constants are in that same file — change tuning there, not at call sites.
