# /release 참조 — 왜 이렇게 하는가

SKILL.md는 **절차**만 담는다(2026-10-18 개편: 32KB → 절차 + 이 문서). 여기에는 각 규칙의 근거·사고
경위·실측을 둔다. 규칙을 바꾸거나 "이 단계는 빼도 되지 않나" 싶을 때 먼저 읽을 것.

## 실측 (2026-10-18)

| 단계 | 소요 |
|---|---|
| `build_dist.py --clean` 전체 | **120초** — 키 0.3 · PyInstaller 57 · bridge32 13 · 배치+verify 0.4 · Inno lzma2/max 31 · app.zip 9.6 · data.zip 7.8 |
| 골드셋(결정론 전 Phase, Phase E 포함) | **22초** |
| 적용 경로 E2E(05.hwp, 실제 한/글) | **약 80초** |
| 실원고 코퍼스 재생(20원고 × AI 켬·끔, 8프로세스) | **약 160~175초**(순차면 약 13분) · 지문이 같으면 즉시 |
| 업로드 | 앱 채널 약 305MB(Setup + app.zip) — 회선이 정한다 |

**권하지 않는 최적화(실측상 이득 없음)**: 브리지 재빌드 생략(13초 — 게다가 `--clean`이 지운다),
앱 릴리스에서 data.zip 생략(8초), 설치 파일 압축 낮추기(31초를 아끼고 모든 사용자의 다운로드가
커진다), 골드셋·빌드 병렬(22초). 시간을 잡아먹는 것은 계산이 아니라 **에이전트의 단계 수와 스킬
분량**이었다 — 그래서 점검을 `release.py`로 묶었다.

## 실행 원칙의 근거 (사용자 지시 2026-07-28 · 07-31)

- **완주**: 사용자가 "릴리스"라고 한 시점에 끝까지 할 권한을 받은 것이다. "빌드할까요?"는 묻지 않는다.
  애매하면 더 안전한 쪽(전체 점검·앱 채널·PATCH)으로 간다.
- **자동 승인 잠금**: 릴리스는 명령을 수십 번 돌려 사용자가 그때마다 Yes를 눌러야 했다. 잠금 파일이
  있는 동안만 PreToolUse 훅(`.claude/hooks/release-autoapprove.sh`, 배선 `.claude/settings.local.json`)이
  자동 승인한다. 2시간이 지나면 훅이 무시하고, 턴이 끝나면 Stop 훅이 지운다 — 그래도 해제는 스킬의
  책임이다(자동 승인이 켜진 채 다른 작업이 이어지지 않게). 잠금은 **승인 창만** 없앤다 — 금지 목록은
  그대로이고, 사용자가 중간에 막아 줄 수 없으므로 더 엄격히 지킨다. `touch` 명령은 허용 규칙과
  **글자 그대로** 일치해야 승인 없이 통과한다.
- **출력 최소**: 통과한 검사·중간 수치는 침묵한다. 성공 시 2줄. 리마인드(기준선 갱신·남은 실기 확인·
  의도적으로 남긴 미탐)는 판단해서 필요할 때만 2줄 뒤에.

## 왜 골드셋을 항상 돌리나 (2026-10-18 — 빠른/전체 경로 폐지)

예전엔 바뀐 파일을 손으로 관리하는 정규식(GUARD)으로 '교정 로직이 바뀐 릴리스'만 골드셋을 돌렸다.
전제는 "골드셋이 매번 수 분을 태운다"였는데 실측은 22초다. 반면 목록은 새 모듈을 따라가지 못했다 —
2026-10-16 감사 때 워커가 실제로 쓰는 `junction_pass`·`consistency_family`·`realword`·`user_dict_file`
넷이 빠져 있어, 그것만 고친 릴리스가 골드셋 없이 나갈 수 있었다. 22초를 아끼려고 조용한 구멍을
유지할 이유가 없다.

## Phase E 기준선 — 왜 결과로 판정하나

Phase E는 중의성 데이터셋 3,000 정문에서 **finder별 발화 수가 늘면 FAIL**하는 델타 게이트다. 기준선
(`.ks_ambig_baseline.json`, 레포 밖 데이터셋 clone 옆)이 실제보다 높게 낡으면 그 차이만큼 여유가 생겨
**회귀가 조용히 통과한다.**

> 사고 직전 사례(2026-07-28): 기준선이 401로 낡아 실제 발화 367과 34건 차이가 있었다. 결정론 규칙
> 수정으로 발화가 31건 늘었는데 Phase E는 "증가 없음 ✅"으로 통과했다. 기준선을 실측값으로 갱신한
> 뒤에야 다음 변경(unit_spacing 32→40)을 즉시 FAIL로 잡았다.

예전엔 "이 파일들(DET)이 바뀌면 갱신"이라는 목록으로 정했다. 그런데 기준선이 낡았다는 사실은 골드셋
출력이 직접 말한다 — 발화가 준 finder마다 `✅ 개선` 줄이 찍힌다. 목록은 빠뜨릴 수 있지만 출력은
빠뜨리지 않는다. 그래서 `release.py preflight`가 그 줄을 '판단 필요(△)'로 올린다.

- 줄어든 것(`✅ 개선`)은 정문 오발화가 준 것 — 정당하면 갱신.
- 늘어난 것(`✗ FAIL [E 발화증가]`)은 **전수 확인**한다(`eval/ambiguity_scan`으로 수정 전/후 스냅샷을
  떠 신규 발화를 하나씩 본다). 원고가 실제로 틀린 탐지면 갱신, 과교정이면 릴리스 중단.
- ⚠ 확인 없이 `--save-ambig-baseline`으로 덮지 말 것. 갱신은 "사람이 보고 정당하다고 판정했다"는
  서명이다. 기준선 파일은 레포 밖이라 커밋되지 않으므로 **커밋 메시지가 유일한 기록**이다.
- 데이터셋(`KS_AMBIG_DATA`)이 없는 PC에서는 Phase E가 돌지 않는다 → preflight가 실패시킨다.

## 적용 경로 E2E — 왜 생겼나 (2026-10-18)

골드셋은 교정 **판단**만 본다. 검수 결정이 교정본·메모·PDF·정오표에 실리는지는 한 줄도 시험하지
않는다. 그런데 2026-10-17의 치명 결함(교정본이 검수 결정과 다름 · 메모 절반 유실)이 전부 그 경로에
있었고, 앱은 둘 다 '실패 0'이라고 보고했다. 예전 스킬은 "적용 경로를 고쳤으면 실제 .hwp로 1회"라고만
적어 수동·모호했고, 정작 `apply_worker.py`를 고치면 그 경로를 안 보는 골드셋이 돌았다.
`eval/e2e_apply/run_e2e.py`는 앱을 화면 없이 그대로 띄워 진짜 클릭으로 검토하고, 교정본을 다시 추출해
**기대 문서(보이는 수락 등장만 카드 값으로 바꾼 원문)와 한 글자도 다르지 않은지** 본다 — 앱의 적용
계획과 독립된 판정이다. 수치 기준선은 원고 옆 `<원고>.e2e.json`(레포 밖).

## 실원고 코퍼스 재생 게이트 — 왜 생겼나 (2026-10-19)

골드셋은 **문장 단위** 자물쇠라 계층 사이의 간섭을 못 본다. 2026-10-19 두 세션 내내 골드셋은 통과했는데
결함은 전부 실원고 코퍼스의 카드 diff에서만 나왔다 — 안전망 카드가 다른 카드의 한 글자 조각에 덮여 오타가
숨던 것, 안전망 카드가 문서 전체 띄어쓰기 통일을 막던 것, 고친 가드가 '[검수]' 표지를 떨어뜨린 것,
노이즈를 줄이다 '훗가이도현'·'금용소득에'를 잃은 것. 그 diff를 손으로 하던 것을 점검으로 고정했다.

- `eval/corpus_harness/run_corpus.py gate`가 레포 밖 원고 캐시(`교정샘플/.corpus/`, 고객 원고) 20개를 워커
  그대로 돌린다 — **AI 켬**은 저장해 둔 Gemini 응답 재생(오프라인 · 무료 한도 0 · 원고 전송 없음),
  **AI 끔**은 결정론 계층만. 둘 다 도는 이유: AI가 고친 오타 뒤에 숨는 손실은 AI 끔에서만 보인다(실측).
- 기준선은 **판정해 둔 카드 집합**(`runs/_gate_ai_base`·`_gate_det_base`)이다. 차이가 있으면 △ — 한 장씩
  보고(사라진 카드 포함) 옳으면 `--save-baseline`. 기준선 파일이 레포 밖이라 **커밋 메시지가 유일한 기록**이다.
- AI 캐시가 빗나가면 ✗ — AI 입력(프롬프트·청커·글로서리·seed)이 바뀐 것이고, 채우려면 Gemini를 불러야
  한다. 무료 한도와 고객 원고 전송이 걸린 일이라 릴리스가 혼자 하지 않는다(`--ai-live`는 사용자 확인 후).
- 원고 하나는 독립이라 4개 묶음 × 2방식으로 병렬 실행한다(순서까지 순차 실행과 같다 — 실측).
  런타임 코드(`git ls-files *.py` 중 런타임)·사전 DB·kiwi 모델·원고 캐시·AI 캐시 크기의 지문이 지난 실행과
  같으면 다시 돌리지 않는다 — 기준선 갱신 뒤 preflight 재실행이 즉시 끝나는 이유.
- 절대치 점검이 아니다: 하네스는 우리말샘·온용어 온라인 조회를 막아 실제 앱보다 '사전 미등재' 카드가 조금
  많다. 보는 것은 **변화**다.
- ★**계층 간 불변식 검사**(2026-10-19 추가 — `eval/corpus_harness/invariants.py`): 기준선 비교는 기준선에
  처음부터 박힌 결함을 못 본다. 그래서 어떤 원고에서도 성립해야 하는 성질 10종(원문이 원고에 있다 · `[검수]`
  사유면 low · 같은 원문 카드는 한 장 · 띄어쓰기 카드는 글자 불변 등)을 두 방식 출력 전체에 매번 검사한다
  (지난 실행을 재사용해도). 위반은 △가 아니라 **✗** — 서명할 대상이 아니라 고칠 대상이라 기준선 저장도 막는다.
  검사기 자체 시험(불변식마다 일부러 어긴 카드를 넣어 반드시 걸리는지)이 실패해도 ✗다. 첫 실행에서
  기준선 속 '같은 원문 카드 두 장'(안전망 빼기 규칙이 [7]에만 있어 [9.2] 이음매 카드에 닿지 않음)을 찾았다.
  지문은 미추적 `.py`까지 본다(`--others` — 새 미커밋 모듈 수정을 재사용하던 결함).

## 빌드 셸 PATH (2026-10-18)

Git Bash에서 빌드하면 PATH의 Git `mingw64\bin`에서 PyInstaller가 `libssl-3-x64.dll`·
`libcrypto-3-x64.dll`을 집어 번들에 넣었다(PowerShell 빌드인 v1.8.5엔 없음) — 같은 커밋이 셸에 따라
다른 번들이 됐다. `build_dist._build_env()`가 PyInstaller에 넘기는 PATH에서 Git·MSYS 경로를 빼고,
`verify()`가 그 DLL을 발견하면 빌드를 무효로 본다. 이제 빌드는 어느 셸에서 해도 된다.

## 🚫 설치 검증을 하지 않는 이유 (2026-07-28 폐기, 사용자 판단)

**개발 PC에는 사용자가 실제로 쓰는 설치본이 들어 있다.**

- `.iss`의 `AppId`는 고정 GUID → 새 버전 무인 설치는 기존 설치본을 그 자리에서 덮어쓰는 업그레이드다.
- `DisableDirPage=yes` + 사용자 전용 설치라 경로는 `%LOCALAPPDATA%\Programs\KS-AI Editor` 하나뿐이다.
- 따라서 "설치 → 확인 → 제거"를 돌리면 **사용자의 실사용 설치본이 사라진다**(2026-07-23 실제 사고:
  v1.0.3 검증이 사용자의 v1.0.2 설치본을 지웠다).
- 구버전 설치본은 **자동 업데이트를 실기로 확인할 유일한 기준선**이다.

실익도 없다: `[Files]`가 `Source: "{#SrcDir}\*" … recursesubdirs` 한 줄이라 설치본은 `dist\KS-AI Editor\`
트리의 미러이고, 그 트리는 `build_dist.verify()`가 게이트한다. 남는 차이는 `[Setup]`의 한 줄짜리 정적
값뿐이라 설치해 보는 것보다 그 줄을 읽는 게 빠르고 확실하다 → `release.py preflight`의 `.iss` 8항목.
되살리자는 판단이 들면: 정말 필요하면 **개발 PC가 아닌 곳**(VM·다른 계정)에서 해야 하고, 그건 이
스킬의 범위 밖이다. `unins000.exe`도 같은 이유로 등장할 일이 없다(쓰게 되면 `/SUPPRESSMSGBOXES` 금지 —
사용자 데이터 삭제 질문에 '예'가 자동 선택돼 `%LOCALAPPDATA%\KS-AI Editor`가 증발한다).

## 설치 파일 백업을 빌드 직후에 하는 이유 (2026-08-05)

예전엔 "구버전을 지우기 직전"에 백업했고, 그래서 4-b에서 "백업에 없네? → GitHub에서 194MB를 다시 받아
채우기"를 매번 했다(2026-08-04 v1.5.2). 백업이 확실히 가능한 시점은 파일이 손에 있는 지금뿐이다 —
`--clean`은 `dist/`를 통째로 지우고, 릴리스를 지운 뒤엔 GitHub에서도 받을 수 없다. app.zip·data.zip은
백업하지 않는다(되돌아갈 때 필요한 건 최초 설치 파일이다).

## 인증 (토큰을 요구하지 않는다)

| 작업 | 인증 주체 |
|---|---|
| `git push` | Git Credential Manager(`credential.helper=manager`) |
| 릴리스 생성·업로드·삭제 | `gh` CLI(`gh auth login` 1회 — 브라우저 대화형이라 **에이전트가 대신 못 한다**) |

토큰을 remote URL에 넣지 말 것(`.git/config`에 평문). `git remote -v`는 토큰 없는 https여야 한다.
릴리스 본문은 `--notes-file`로 넘긴다(한글을 셸 인자로 주면 이스케이프가 깨진다).
⚠ `gh … --jq '…'`는 Bash에서 실행할 것 — PowerShell 5.1은 작은따옴표 안의 큰따옴표를 망가뜨린다.

<details><summary>gh를 못 쓸 때의 폴백 (curl + 토큰)</summary>

사용자에게 토큰을 요청한다(스코프 `repo`+`workflow`). 한글 본문은 JSON 파일로:
```bash
curl -s -X POST -H "Authorization: token $GH_TOKEN" -H 'Accept: application/vnd.github+json' \
  https://api.github.com/repos/great-yob/KS-Proof-Reader/releases --data-binary @rel.json
curl -s -X POST -H "Authorization: token $GH_TOKEN" -H "Content-Type: application/octet-stream" \
  --data-binary @"dist/release/<파일>" \
  "https://uploads.github.com/repos/.../releases/<id>/assets?name=<파일명>"
```
zip은 `application/zip`, exe는 `application/octet-stream`. 끝나면 **토큰 폐기를 안내**한다.

## 구버전 릴리스 삭제 (정책)

채널당 하나만 남긴다 — 결함 있는 구버전을 Releases 페이지에서 직접 받아 가는 경로를 없애기 위함
(자동 업데이터는 최신만 제시하므로 기존 사용자에겐 영향이 없다). 채널을 섞지 않는다(앱 릴리스면
`v*`만 — `data-*`·`stdict-*`는 독립 현행 릴리스). **git 태그는 지우지 않는다**(`--cleanup-tag` 금지 —
태그는 그 버전이 어느 커밋이었는지의 기록이다). 삭제 전에 그 버전의 설치 파일이 백업에 있어야 한다 —
새 버전에 결함이 드러났을 때 되돌아갈 배포본이 그것뿐이다. ⚠ 삭제 직후 **비인증** API로 확인하면
캐시된 옛 목록이 보인다(`gh`는 인증 조회라 문제없다).

## 부록 — kiwipiepy(형태소 분석기) 업그레이드

주기적 갱신 항목이 아니라 **의존성 업그레이드**다. `core/morph.py`가 교정 가드 수십 곳에서 쓰므로
토크나이저 동작이 바뀌면 가드 판정이 흔들린다 → 필요할 때만 올리고 `run_goldset.py` before/after로
게이트한다(발화가 늘면 되돌린다). 릴리스 이력: 0.22.0 '25-11 → 0.23.0 '26-03 → 0.23.2 '26-06.
`kiwipiepy`와 `kiwipiepy_model`을 **같은 마이너로 함께** 올리고 `requirements.txt` 고정값도 바꾼다.

| 변경 | 릴리스해야 할 것 |
|---|---|
| 패치만(0.23.2 → 0.23.3, 모델 동일) | 앱만 |
| 마이너 이상(0.23.x → 0.24.0, 모델도 바뀜) | **앱 + 데이터 둘 다** |

마이너를 올리고 앱만 내면 사용자는 새 라이브러리 + 옛 모델이 된다. `datapaths.kiwi_model_ok()`가 형태소
분석을 꺼서 크래시는 면하지만 활용형 복원·띄어쓰기 백스톱·인명 가드가 빠져 교정 품질이 조용히 무너진다.
`build_dist.verify()`가 빌드 시점에 이 불일치를 잡는다.
