## Project overview

KS-Proof Reader — Korean-language proofreading tool for HWP (한/글) documents. It uses a modern 3-stage pipeline (Local NIKL Dictionary Screening → Google Gemini AI → Dictionary Re-validation) and writes corrections back into the HWP file via COM automation. Code, comments, and UI strings are predominantly Korean.

⚠ **Product display name vs project/repo name are deliberately split.** The shipped product is **"KS-AI Editor"** — that string is the EXE name, the `dist/` and install folders (`%LOCALAPPDATA%\Programs\KS-AI Editor`), the user-data folder (`%LOCALAPPDATA%\KS-AI Editor`), the window title, and the release-asset prefix. It lives in exactly two constants: `build_dist.APP_NAME` and `datapaths.APP_DIR_NAME` (the `.iss` `[Code]` uninstall path must match the latter). The **project/repo stays "KS-Proof Reader" / `great-yob/KS-Proof-Reader`** — the on-disk repo folder, the GitHub repo, the release tags (`v1.0.1`), and the `.iss` filename. That name is the updater's polling URL, so changing it breaks auto-update; never rename it to match the product. Docs below that say "KS-Proof Reader" mean the project.

## Application Architecture

- **v5 (current)** — PySide6 native desktop app. Entry point: `main.py`. UI in `ui/`, engine in `core/`. This is the only codebase; the legacy v4 FastAPI + React webapp (`_archive_v4/`) was removed on 2026-06-17.

## Building for distribution

```powershell
.\.venv64\Scripts\python.exe build_dist.py --clean      # → dist/KS-AI Editor/ (~518MB)
```

Prerequisites: **Inno Setup 6** (installer) and a **32-bit Python 3.11 with `pywin32` + `pyinstaller`** (HWP bridge). Missing Inno only skips the setup file with a warning; a missing 32-bit Python **fails the build** — see below for why that's deliberate. Useful flags while iterating: `--skip-bridge` (reuse the last 32-bit bridge), `--no-installer`, `--no-zip`.

[build_dist.py](build_dist.py) (PyInstaller `--onedir`; `--onefile` is forbidden — the 160MB `stdict.db` would be re-extracted to temp on every launch). It:
1. Reads the three API keys from `config.ini`/env, Fernet-encrypts them into a generated `core/_org_keys.py`, bundles it, and **deletes it in a `finally` block** so no plaintext survives in the repo. `ConfigLoader._load_org_keys()` decrypts at runtime.

⚠ **The repo and its releases are PUBLIC, and the decryption key ships in the same file as the ciphertext — so the embedded keys are extractable by anyone.** This was an accepted trade-off (2026-07-22): the three keys are free-tier, read-only, rate-limited and individually revocable (Gemini free tier — no billing attached; 우리말샘/온용어 — free dictionary lookups), and a public repo is what makes the unauthenticated auto-updater work at all. **The rule that follows: only ever embed keys of that character.** Never add a key with billing attached, write access, or access to customer/personal data to `collect_keys()` — route those through a server proxy instead. Rotate the embedded keys if abuse shows up in the quota dashboards.

⚠ **Public repo ⇒ no customer-identifying content may be committed.** `교정샘플/` is gitignored, and measurement tables in `docs/` refer to manuscripts as 실파일A/B/C (same convention as the goldset's `실파일06/24`). Keep it that way when adding new measurements.
2. Excludes secrets/customer data from the bundle (`key.txt`, `config.ini`, `교정샘플/`, `korean-ambiguity-data/`, caches) and verifies afterwards that none leaked — **never add a rule that includes the repo root wholesale**.
3. Excludes `torch`/`transformers`/`tokenizers`/`huggingface_hub` — dead weight from the **removed KoGEC engine**, still present in `.venv64` but imported by nothing (960MB → 485MB). Unexclude only if a verified local model is ever reintroduced.

**App and data ship separately** — they change at wildly different rates, so one build emits three artifacts into `dist/release/`:

| Artifact | Size | When |
|---|---|---|
| `…-Setup-{ver}.exe` | ~200MB | first install (what users download) |
| `…-{ver}-app.zip` | **93MB** | code changes (frequent) — updater app channel |
| `…-data-{YYYY.MM}.zip` | 131MB | dictionary updates (rare) — updater data channel |

**The first-install artifact is an Inno Setup installer**, not a zip ([installer/KS-Proof-Reader.iss](installer/KS-Proof-Reader.iss), compiled by `build_installer()` via `ISCC.exe`; `winget install --id JRSoftware.InnoSetup -e`, discovered through `ISCC_PATH` → known paths → PATH, and **skipped with a warning** rather than failing the build if absent). It installs per-user into `%LOCALAPPDATA%\Programs\KS-AI Editor` with Start-menu/desktop shortcuts and an Add-or-Remove-Programs entry. ⚠ **Per-user is not cosmetic**: Program Files would make the install folder read-only, and `updater.install_app()` replaces that folder wholesale with robocopy — it would die on permissions. `PrivilegesRequired=lowest` also means no UAC prompt. `DisableDirPage=yes` hides the destination-folder page — not just for convenience but to **enforce** that install path, since a user picking Program Files would break auto-update. `AppId` is a fixed GUID — changing it makes Windows treat an upgrade as a second product. `[UninstallDelete]` sweeps `{app}` because files added later by the auto-updater aren't in the uninstall log; uninstall then *asks* before removing `%LOCALAPPDATA%\KS-AI Editor` (settings, cache, updater-installed dictionary data — this path must match `datapaths.APP_DIR_NAME`). The `.iss` must stay **UTF-8 with BOM** or Inno reads it as ANSI and mangles the Korean.
⚠ The installer is **unsigned**, so Windows SmartScreen shows "알 수 없는 게시자" on first run — users must click 추가 정보 → 실행. Signing needs a paid code-signing certificate; the old zip had the same problem, just less visibly.
`full.zip` was retired on 2026-07-22 (the installer replaces it). `updater._pick_asset` still falls back to `-full.zip` when no `-app.zip` exists — harmless, since app releases always carry `app.zip`.

Data (`stdict.db`, `eomun.db`, `userdict.db`, **`kiwipiepy_model/`**) is staged **next to the EXE in `data/`**, never inside `_internal/` — bundling it there would make it unreplaceable. `verify()` fails the build if it finds `_internal/data/stdict.db`. The kiwi model is excluded from PyInstaller (`--exclude-module kiwipiepy_model`) and passed to `Kiwi(model_path=…)` instead; `kiwipiepy` never imports the model package, so this is safe.

⚠ **Never call `Kiwi(model_path=…)` without validating the path first.** A missing or mismatched model raises a catchable Python exception and *then* takes the process down with a native heap corruption (`0xC0000374`) — `try/except` does not save you. `datapaths.kiwi_model_ok()` is the guard: it checks the required model files exist **and** that the model's minor version matches the installed `kiwipiepy` (the model is version-locked to it — lib 0.23.2 ↔ model 0.23.0). `core/morph._get_kiwi()` consults it and, when frozen with no valid model, refuses to construct `Kiwi` at all. A mismatch therefore degrades to "morphology off" (graceful) instead of crashing — but that silently removes lemma restoration, the spacing backstop and the personal-name guard, so `build_dist.verify()` also fails the build on mismatch. **kiwipiepy is a dependency upgrade, not periodic maintenance**: bump it only when worthwhile, gate on `run_goldset.py`, and if the *minor* changes you must ship the data package too.

**Two version numbers, deliberately independent** — top-level [version.py](version.py): `APP_VERSION` (semver) and `DATA_VERSION` (`YYYY.MM`). The sidebar shows both on two lines. ⚠ The *authoritative* data version is `stdict.db`'s `meta.data_version` via `nikl_dict.data_version()` — `version.py` only records what a build packaged, and data updates independently. UI and updater both prefer the DB value. Release tags: `v1.0.0` (app), `data-2026.07` (data), `stdict-2026.07` (CI's partial DB).

[core/updater.py](core/updater.py) polls GitHub Releases on both channels. Data installs into `user_dir()/data` (staged → validated → swapped; datapaths ranks it first, so a restart is enough). App updates need a helper `.bat` because a running EXE can't overwrite itself. ⚠⚠ The helper's final `rmdir /S /Q "{tmp}"` must target **only the update's own `mkdtemp` work folder** (`install_app`'s `work`) — it used to receive `staging.parent`, which *is* `%TEMP%`, so every in-app update recursively deleted the user's entire temp folder (other programs' temp/recovery files included; found 2026-10-16 audit, fixed — verified in a sandbox with canary files). `_discard_download` likewise removes only a `ksproof-upd-*` folder directly under `gettempdir()`. ⚠ **A data install can't swap the folder while the app runs** — `nikl_dict` keeps its DB connection open for the whole process, so from the *second* in-app data update on (user `data/` already exists and is in use) the rename died with `WinError 5`, every time. `install_data` now validates into `data.new`, stamps it with `datapaths._PENDING_READY`, tries the swap, and on `OSError` leaves it pending; `main.py` calls `datapaths.apply_pending_data()` **first thing, before anything opens a DB** (frozen only — in dev `user_dir()` is the repo root). An unstamped `data.new` is a half-extracted leftover and is discarded. ⚠ `data_dir()` picks the candidate with the **highest `meta.data_version`** (ties → user dir first): the old "first that exists" rule let a stale updater-installed copy in the user folder shadow a newer dictionary shipped by a fresh installer, forever and silently. `find_data`/`kiwi_model_dir` search the chosen folder first. ⚠ `install_data` **refuses to run in dev** unless given an explicit `dest` — in dev `user_dir()` is the repo root, so it would clobber `data/` including the 1.8GB exports. Checking is automatic; **installing is never automatic** — a forced restart mid-proofread would destroy the user's work.

**UI wiring** (added 2026-07-23 — before that `updater.py` was complete but *nothing imported it*, so the app never checked and users saw no update path at all): `MainWindow._start_update_check()` runs [ui/workers/update_worker.py](ui/workers/update_worker.py) `UpdateCheckWorker` at startup (network I/O off the GUI thread; `core/` stays PySide6-free). A hit shows a persistent accent badge in the sidebar footer (`Sidebar.set_update_available`, clicking emits `update_clicked`) **and** opens [ui/widgets/update_dialog.py](ui/widgets/update_dialog.py) `UpdateDialog` once per run (`_update_prompted`). The dialog is one window walking three states — 안내 → 진행률 → 재시작 — because swapping windows makes the frameless modal jump; it downloads via `UpdateDownloadWorker` and emits `apply_requested`, and **never installs**: only `MainWindow._on_update_apply` calls `install_app`/`install_data`, since only it knows whether a proofread is running (`_open_update_dialog` refuses during `running`/`apply_running`). `install_app` returning True means the helper `.bat` is already waiting on this PID, so the window **must** then `close()`. It reuses the light-fixed `build_light_card`/`LIGHT_CARD_QSS` surface (no `refresh_theme` — theme-independent by design). ⚠ `_summarize_notes` deliberately hunts for the changelog heading rather than taking the first lines: this repo's release bodies **open with install instructions**, so a naive head-truncation summarized "받아 실행하세요" instead of what changed. ⚠ The check worker has no cancel path (a blocking socket read), so `closeEvent` disconnects it and waits only 800ms before `terminate()` — routing it through `_cleanup_worker` would stall shutdown by 5s on a dead connection.

⚠ **Every data-package DB must resolve through `datapaths`** — `eomun_rules` and `userdict` used to hard-code `_MEIPASS/data` + EXE-side only, so an in-app data update (installed in the user folder) never reached them. `eomun.db` now uses `find_data`; `userdict.db` picks the **highest `meta.snapshot_ver`** among the sync build (`datapaths.userdict_runtime_path()` = `cache_dir()` when frozen) and the data-package copies, and `userdict.reload()` (called by `userdict_sync.pull`) switches to a fresh build without a restart. `build_userdict_db` takes both its write path and its **homograph-guard `stdict.db`** from `datapaths` — when frozen its `Path(__file__).parent/"data"` is `_internal/data`, where `stdict.db` does not exist, so guards 2·3 were silently off in every shipped build (the warning print goes nowhere in a windowed app).

**Path resolution is centralized in [datapaths.py](datapaths.py)** — a deliberately dependency-free top-level module (importing `core` would drag in `google.genai` and the HWP bridge just to look up a word). It resolves data as user dir → EXE-side → bundle, so an updater-installed copy wins. Anything written at runtime goes to `cache_dir()` (`%LOCALAPPDATA%\KS-AI Editor` when frozen) — the install folder and `_internal/` can be read-only. `ConfigLoader._save()` swallows `OSError` so a read-only install degrades to "settings don't persist" instead of crashing the theme toggle; when frozen, `config.ini` is **read** from both the EXE folder (deployer override) and the user folder, but **written** only to the user folder.

## Dictionary data maintenance

`data/stdict.db` (~1.64M words) has **two independently-updated halves**, and they are maintained by *different* scripts on purpose. Never rebuild one in a way that clobbers the other.

| Half | Source | Script | Cadence |
|---|---|---|---|
| `source='stdict'` (표준국어대사전, ~437K) | `spellcheck-ko/korean-dict-nikl` **`stdict/`** | CI builds `stdict_part.db` ([build_stdict_part.py](build_stdict_part.py)) → [update_stdict.py](update_stdict.py) merges | semiannual, automated |
| `source='opendict'` (우리말샘, ~1.21M) | official 전체 내려받기 export in `data/전체 내려받기_우리말샘_json_YYYYMMDD/` | [update_opendict.py](update_opendict.py) | manual, whenever the user downloads a new export |

우리말샘 can't be automated — its official export sits behind a login. The GitHub mirror *can* be, which is why CI only handles 표준국어대사전. [setup_dict.py](setup_dict.py) still does a full from-scratch build of both (`REPO_NIKL` — all three dictionaries live in that one repo; the standalone `-stdict`/`-krdict` repos have been dead since 2019).

⚠ **`norm_map` (12,750 rows, built by [build_norm_map.py](build_norm_map.py) from the 우리말샘 export) lives in the same DB file and is easy to destroy.** `update_opendict.py` builds a fresh temp DB and swaps it in, which silently dropped `norm_map` — killing every 규범표기 correction (컨텐츠→콘텐츠) with no error at all. It now rebuilds `norm_map` from the same export and gates on a table-loss invariant. `update_stdict.py` avoids the class of bug entirely by writing in-place inside a transaction. Both print an invariant check; **run `eval/ai_goldset/run_goldset.py` after any DB update** — that's what caught it.

Cadence rationale (measured 2026-07-22): upstream mirror refreshes irregularly (~semiannual); the 7-year-stale stdict source cost **0 headwords** of coverage because the fresh 우리말샘 covered all 391 gaps; and the residual gap is already handled live by the two API fallbacks. Monthly/quarterly data releases would ship 131MB for near-zero gain.

## Architecture you must understand before editing

### The 64-bit ↔ 32-bit HWP bridge (critical)

Hancom HWP's COM server (`HWPFrame.HwpObject`) is **32-bit only**, but the v5 app runs as **64-bit** PySide6. Direct `win32com.client.Dispatch` from the main process will fail.

The workaround in [core/hwp_editor.py](core/hwp_editor.py):
1. `HwpEditor` (64-bit, in-process) spawns a 32-bit Python subprocess running [core/hwp_bridge_worker.py](core/hwp_bridge_worker.py).
2. Communication is line-delimited JSON over stdin/stdout. Commands: `open`, `get_text`, `apply`, `save_as`, `close`, `quit`.
3. **`_bridge_command()` picks the worker**: a bundled `bridge32/hwp_bridge_worker.exe` next to the EXE wins; otherwise it falls back to `_find_python32()` + the `.py` script (dev only). 32-bit Python is discovered via `PYTHON32_PATH`, then hardcoded candidate paths (`…\Python311-32\…`), then `shutil.which`.

⚠ **Distributed builds must ship `bridge32/`** — `build_dist.py` freezes the worker with the *32-bit* interpreter into its own onedir (22MB) and stages it beside the EXE. Before this existed (fixed 2026-07-22) the released zip had **no HWP correction at all**: PyInstaller never bundled `hwp_bridge_worker.py`, so the path didn't exist, and even with it the user's PC would have needed 32-bit Python + pywin32 (candidate path #1 was a dev-machine path). `verify()` now fails the build if `bridge32/hwp_bridge_worker.exe` is missing **or its PE header says 64-bit** — a 64-bit worker installs fine and then fails only on the user's machine, at `Dispatch`. Two build-side details are load-bearing: the worker is frozen `--console` (a `--windowed` build has no usable stdout, which *is* the protocol channel; the parent hides the window with `CREATE_NO_WINDOW`), and `pyhwpx` is `--exclude-module`d (its `import` inside `_security_dll_path()` drags in PyQt5 → 85MB; only its `FilePathCheckerModule.dll` is wanted, and that gets copied in as a file). The worker also disables `win32com` gen_py cache rebuilding when frozen — it printed to stdout, i.e. into the JSON stream.

When changing HWP behavior, edit both sides of the bridge and keep the JSON protocol in sync. Don't try to "simplify" by removing the subprocess — it's load-bearing.

⚠ **`SaveAs`/PDF export fail by return value, not by exception** — when the target is open in another 한/글 (or a PDF viewer), `SaveAs` returns `False` and the file is untouched. The bridge used to ignore that and report success; `close`'s `Quit()` then raised a **'저장할까요?' modal for the *original* file** (default button 저장 — pressing it overwrote the original with the corrections, measured) and the parent killed only the bridge, leaving a zombie hwp.exe. Now `save_as`/`export_pdf` require both a non-False return **and** a changed file stamp (`_file_stamp`/`_written`: mtime·size·id) and raise a "다른 프로그램에 열려 있으면 닫고" error otherwise, and `close` calls `Clear(1)` (hwpDiscard) before `Quit()` so no save prompt can ever appear. ⚠ Match caps count **only matches actually replaced/marked**: the old `max_iters=100` counted *skipped* matches too, so a card whose real occurrence was #155 of 172 was never applied and S3 reclassified the miss as '정상' (dashboard 실패 0). Caps are now `_APPLY_MAX_REPLACE`/`_APPLY_MAX_MATCHES`, `_LOCATE_MAX_OCC`, `_MEMO_MAX_OCC` (runaway guards only) with a progress heartbeat every `_APPLY_HEARTBEAT` matches so the parent's idle timeout doesn't fire on long words.

★**한/글이 띄운 모달을 우리가 숨겨 영구 대기에 빠질 수 있다** (배포 첫날 실사고 2026-08-21 — 다른 직원 PC 전부가 `[원고 추출 시작]`에서 120초 무응답). `_WindowHider`는 새 `hwp.exe`의 **보이는 최상위 창을 전부** `SW_HIDE`하는데, 여기엔 사용자 등록·개인정보 동의·문서 복구·자동화 접근 승인 **모달도 포함**된다. 모달이 숨겨진 채 `Dispatch`/`Open`이 블록되면 사용자에겐 보이지도 클릭할 수도 없다. ★**원인은 보안 모듈 등록 차이이고, 등록 위치는 COM ProgID가 아니라 한/글 전용 per-user 키다** (직원 PC 현장 확증 2026-08-21: 그 값이 실제로 **없었고**, 등록해 주자 전 배포 PC가 최종 단계까지 정상 구동) — `HKCU\Software\HNC\HwpAutomation\Modules\FilePathCheckerModule` = DLL 절대경로. 개발 PC엔 pyhwpx가 만든 이 값이 있어 `RegisterModule`이 True를 돌려주고 승인 모달이 우회되는데, pyhwpx를 깔 일이 없는 배포 PC엔 이 값이 없다. ⚠ COM ProgID는 개발 PC에도 **없다** — HKCR·WOW6432Node·HKCU\Software\Classes 어디에도 없이 True가 나온다. 그래서 `regsvr32`는 답이 아니고 (HKLM 쓰기라 `PrivilegesRequired=lowest`와도 맞지 않는다), **HKCU 값 하나만 쓰면 된다 — 관리자 권한 불필요**. `_ensure_security_module_registered()`가 `RegisterModule`보다 먼저 그 값을 채운다(이미 유효한 등록이 있으면 건드리지 않는다 — 앱 삭제 시 한/글이 사라진 DLL을 가리키지 않게). ⚠ 다른 후보도 살아 있다: **32비트 브리지 EXE 기동 실패**(백신/SmartScreen, 서명 없는 22MB EXE)는 배포본 로그상 COM 블록과 구분되지 않으므로, 진단 배치가 `{"cmd":"quit"}`만 먼저 보내 둘을 가른다. ⚠ '악성코드 차단 > 프로그램 실행 중 문서 열 때 차단' 옵션은 원인이 **아니다**(개발 PC는 켜진 채 정상 동작). 방어는 `_StallWatch`(20초 초과 시 `_WindowHider.unhide()`로 창을 되살리고 **1회만** 경고 — ⚠ 반복하면 stderr 출력이 부모의 유휴 타임아웃을 리셋해 120초가 영원히 오지 않는다)와, **호출 전에** 남기는 단계 로그(`[브리지] 워커 시작` / `[HWP] Dispatch 시도` / `파일 열기 시도` — 성공 후 로그는 블록되면 영영 오지 않는다), 그리고 부모가 보관한 `_last_worker_line`을 타임아웃 메시지에 싣는 것이다. ⚠ 브리지 진단 로그는 `activity_panel._DROP`이 `[Worker stderr]`·`Dispatch`·`[보안]`을 **화면에서 통째로 감추므로**, 사용자가 봐야 할 라인은 그 금칙어를 피하고 전용 `[태그]`를 달아야 한다(지연 경고는 `[한/글 대기]`). 현장 진단은 `KS_HWP_VISIBLE=1`(창 숨김 해제)과 [tools/hwp_bridge_diag.bat](tools/hwp_bridge_diag.bat) — 후자는 **이미 설치된 배포본**의 `bridge32` EXE를 visible로 돌리므로 새 릴리스를 기다릴 필요가 없다.

**`HwpEditor` is a factory, not a class.** [core/__init__.py](core/__init__.py) exposes `HwpEditor(file_path, ...)` which returns one of two backends with the same interface:

- `KS_HWP_BACKEND=direct` + `.hwpx` → [core/hwpx_editor.py](core/hwpx_editor.py) `HwpxEditor`, which edits the HWPX ZIP/OWPML XML directly (no Hancom process) but applies **text only, no color**. For fast bulk hwpx processing.

### Engine pipeline (v5)

Defined in [ui/workers/proofreading_worker.py](ui/workers/proofreading_worker.py), executed on a `QThread`:

1. **Extract** — `HwpEditor.open()` → `get_text()` (via the bridge/backend above).
2. **Local Dictionary Screening (1st Pass)** — `KoreanDictValidator` (top-level [nikl_dict.py](nikl_dict.py), *not* under `core/`) queries `data/stdict.db` to extract suspicious words (unregistered words, neologisms, dialects). [core/morph.py](core/morph.py) uses kiwipiepy to restore inflected surface forms to their dictionary lemma so genuine conjugations aren't flagged as unregistered (graceful no-op if kiwipiepy is missing). Two **cached online fallbacks** then prune false "미등재" flags, in order: [nikl_api.py](nikl_api.py) (우리말샘, serial — its lock spans the network call) → [onterm_api.py](onterm_api.py) (**온용어**, 국립국어원 전문용어 120만, parallel `ThreadPoolExecutor(4)`). Both gate on `is_likely_typo` and cache permanently in `data/api_cache.db` (separate tables `cache` / `onterm_cache` — never merge them). ⚠ 우리말샘 answers an invalid/revoked key with **HTTP 200 + a root `<error>` XML even for `req_type=json`**; the old parser read that as total 0 and **permanently cached every queried word as 미등재** (a key rotation would poison every user's cache). `nikl_api._parse_response` now returns a number only when the result shape (`channel.total` / `<total>`) is confirmed — `(None, [])` = 확인 불가 (not cached) vs `(0, [])` = 미등재 확정 (cached) must never blur — an error response disables lookups for the run (`last_error()`, logged by worker [2]), and `_migrate_cache` (`nikl_cache_meta.cache_ver`) purged the old `found=0` rows once. ⚠ 온용어 contains non-standard spellings, so `is_registered_onterm` carries a **norm_map/spelling_pairs veto guard** (`_norm_pair_components`) — see [docs/onterm-integration-design.md](docs/onterm-integration-design.md).
3. **Gemini AI** — generation is built via [core/correction_engine.py](core/correction_engine.py) `build_engine()` → `GeminiEngine`, a thin adapter over [core/gemini_checker.py](core/gemini_checker.py) `GeminiChecker` (the role-separation seam — generation is the swappable part). It uses a 30-year expert persona ([core/prompts.py](core/prompts.py)) plus the local dictionary context. API calls are chunked (`AI_CHUNK_TYPO=15000`, `AI_CHUNK_POLISH=8000`) and throttled (`AI_CALL_DELAY=4.1s`) for the 15 RPM free tier. ⚠ **Do not reach for `AI_CHUNK_TYPO` as a recall lever — that was measured and rejected (2026-07-27).** A full-document sweep of 8 sizes appeared to favour 6,000, but a control that held the size fixed and merely *shifted the boundaries by half a chunk* changed ~80% of the output (6,000: 84%/29% → 61%/20% precision/recall; 15,000: 92%/20% → 76%/24%). **Boundary placement, not size, dominates**, so the sweep really measured eight boundary configurations and the size ranking is close to accidental. The real lever is a chunker that pins boundaries to document structure (`eval/ai_goldset/ab_chunker.py`'s preservation chunker), evaluated on *variance against a phase-shift control* rather than peak score. Full tables and the RPD budget are in the comment above the constant in `core/models.py`. Model: `gemini-3.5-flash-lite`, with an automatic fallback chain (`_MODEL_CANDIDATES` in `gemini_checker.py`) ordered by **free-tier RPD** — `3.5-flash-lite` (15 RPM/500 RPD) → `3.1-flash-lite` (15/500) → `2.5-flash-lite` (10/20) → `3.5-flash` (5/20). The chain advances on two distinct triggers: model unavailable (404/deprecated/permission) **and quota exhaustion** — `_is_quota_error` (narrower than `_is_transient_error`, so 5xx/timeouts don't burn a model) switches **immediately, with no backoff**, since free-tier quota is per-model. ⚠ Only a **daily** 429 (`quotaId …PerDay…`, `_is_daily_quota`) adds the model to `self._quota_blocked` (skipped for the rest of the process). A per-minute or unclassified 429 switches to the next model **without blocking and without unlocking** `_model_id`, so the next chunk asks the preferred model again; if every candidate is minute-limited, the backoff waits at least the server's `retryDelay` (capped at `_RPM_WAIT_CAP`). Treating RPM as RPD (the old behaviour) dropped the 500-RPD model for the whole run after a burst of chunks and could pin the run to 3.5-flash (20 RPD). Only when every candidate is exhausted does it fall through to `_RETRY_DELAYS` backoff.
4. **Merge** — `CorrectionMerger.merge()` deduplicates and sorts suggestions.
5. **Consistency post-pass** — [core/consistency_pass.py](core/consistency_pass.py) `enforce_consistency()` unifies AI per-chunk nondeterminism: Case A (조사 변형, high confidence) and Case 4 (부분 매칭 전파, low confidence, dictionary-guarded). `reconcile_variant_confidence()` follows. ⚠ The old Case B (edit-distance-1 whole-word substitution) is permanently removed — see file header.
6. **Dictionary Re-validation (3rd Pass)** — The AI's suggestions are cross-checked against the local DB. Non-standard terms are assigned `confidence="low"`.
6.5. **Junction coherence pass** — [core/junction_pass.py](core/junction_pass.py) `resolve()` (worker step `[9.2]`) fixes nested words deciding the *same* spacing junction in opposite directions ('수당수급자'→'수당 수급자' vs '수당수급자확인서'→'수당수급자 확인서'). Measured on 4 reports: 22 conflicts, **20 involving an auto-applied card** — i.e. the split happened without the user ever seeing a card. ⚠ **Automatic resolution is provably impossible**: half the conflicts are legitimate distinctions (한글 맞춤법 제49·50항 allow joined 고유명사/전문용어 — '출산 전후' 44:4 vs '출산전후휴가' 3:1, a 고용보험법 term), and neither the dictionary (출산전후휴가·서비스판매종사자·아파트매매가격지수 are all unregistered) nor frequency aggregation (출산|전후 is 45:7 spaced, which would wreck 출산전후휴가) can tell them apart. So the pass applies a **precedence hierarchy — a word's own document-wide majority beats the junction's, which beats the 규범 default** — and splits conflicts three ways: both sides clear ⇒ *legitimate distinction, untouched*; one side clear and the other has **no** evidence ⇒ auto-harmonized; otherwise ⇒ `Correction.junction_group` + demoted to `low` for the user to decide once. It also recovers cards the binary-split finder structurally cannot see (`find_compound_spacing_consistency` splits a word at exactly **one** point, so '기초연금 수급자 확인서' at 9:1 produced no card at all). ⚠ Invariants: `original` is **never** modified (the document string must stay findable — that's what makes "search for a string that isn't in the file" structurally impossible), letters never change (spaces only), and the 미탐 recovery only ever **splits a joined run** — joining a spaced phrase is the banned 294-noise class. Full rationale in the module header and the `junction-spacing-coherence` memory.
7. **Apply** — `ApplyWorker` sends accepted corrections back through the bridge, and `output/errata_generator.py` emits an Excel errata file.

**사용자 첨부 사전은 이 파이프라인 전체보다 위에 있다** ([core/user_dict_file.py](core/user_dict_file.py), 2026-09-03 사용자 지시). 설정 화면 우측 첨부 칸 아래쪽(`SetupPanel`이 아니라 `AttachPanel`의 `DictPanel`)에 2단 엑셀(**A열 원문 · B열 교정문**)을 첨부하면 `options["user_dict_path"]`로 실려 두 가지가 동시에 켜진다: ① 그 목록이 그대로 교정 카드가 되고, ② **다른 어떤 계층도 그 낱말을 고치지 못한다.** 첨부가 없으면 `udict is None`이라 계층이 통째로 잠들어 기존 동작이 한 글자도 달라지지 않는다 — 이게 "엑셀 없으면 기존 로직 그대로"의 구현이다. ⚠ 이름이 비슷한 [core/userdict.py](core/userdict.py)(서버에서 내려받는 **조직 공유 학습 사전** userdict.db, 워커 [5.6])와 **다른 것**이다. 우선순위는 사용자 첨부 > 국가 표준·사내 페어 > 나머지.
워커 진입점은 넷이고 각각 이유가 있다: **[1.5]** 추출 직후 로드(스크리닝보다 앞) · **[2.5]** `suspicious_words`에서 보호 낱말 제거(이 목록이 AI 프롬프트 컨텍스트 겸 안전망 카드 씨앗이라, 남겨 두면 AI에게 "이 낱말 미등재"라고 일러 주는 셈) · **[4.6]** 카드 주입 + 같은 `original`을 다르게 고치려던 카드 대체 · **[9.7]** 직렬화 직전 **마지막 관문**. ★[9.7]이 진짜 보증이다 — [4.6] 이후에도 [5.6]~[9.6]이 계속 카드를 만들기 때문에, 계층마다 검사를 심는 방식은 새 계층이 생길 때마다 빠뜨린다. 판정식(`violates`)이 한 곳뿐이라 두 번 불러도 어긋나지 않는다.
**엑셀 한 행의 뜻은 앞뒤 공백이 가른다** — 판정은 `classify_row` 하나뿐: 교정문이 비었거나 원문과 완전히 같으면 **보호 전용**(고치지 말 것) · 앞뒤 공백을 떼고도 **글자가 다르면 낱말 페어**(가나문화시→가나문화사, 부분문자열 치환) · 앞뒤 공백을 떼면 **글자가 같으면**(공백만 다름) **경계 규칙**(띄어쓰기 통일 — `' 기술'→'기술'`은 `xx 기술`·`xx기술` 혼재를 `xx기술`로, `'정보 '→'정보'`는 `정보 xx`·`정보xx`를 `정보xx`로). ⚠ 그래서 로더는 셀 값을 **`strip()` 하지 않는다**. `'가나문화시 '`처럼 엑셀에서 딸려 온 우연한 공백은 글자가 다르므로 낱말 페어로 떨어져 무해하다 — 경계 규칙이 되려면 양쪽 글자가 완전히 같아야 한다.
★**경계 규칙은 어절 쌍으로 펼쳐서 카드를 만든다.** `' 기술'`을 그대로 `original`로 쓰면 카드가 "원본 기술 / 교정 기술"로 보여 **차이가 눈에 안 보이고**, 정오표·메모·PDF도 같은 꼴이 되며 인라인 편집은 공백 의미를 잃는다. 그래서 문서에서 매칭된 자리를 양옆 어절까지 넓혀 `'정보 기술을'→'정보기술을'`로 펼친다(한 어절 무리에 규칙이 여럿 걸리면 **한 번에 모아** — '정보 통신 기술'+두 규칙 ⇒ '정보통신기술' 한 장). ⚠⚠ **문자열 그대로 적용하면 안 된다 — 실측으로 확인**(2026-09-03 · 실파일H · 규칙 2개): 가드 없이는 174곳이 나오는데 '한다. 기술'·'정책, 기술'·'하는 기술을'·'및 기술과'·'각 기술'처럼 **명백히 틀린 자리가 절반을 넘었다**. 전부 수락 상태로 뜨므로 사용자가 100장을 거절해야 한다. 그래서 `core/morph.is_joinable_left`/`is_joinable_right`로 양옆 어절을 거른다 → 90곳. ⚠ **앞말과 뒷말의 기준이 다르다**: 조사는 복합어 전체에 붙으므로 앞말에 조사가 있으면 별개 구(句)라는 증거라 불가, 뒷말의 조사는 정상이라 가능 — 이 비대칭을 놓치면 '인공지능 기술의'처럼 **맞는 자리가 통째로 막힌다**(실측). kiwi가 없으면 **붙이지 않는다**(조용한 오적용보다 조용한 미적용). ⚠ 반대 방향(`'기술'→'기술 '`, 붙은 것을 띄운다)에는 `is_word_split_point` — **형태소 경계에서만** 띄운다. 없으면 '기술이'가 '기술 이'로 쪼개진다(실측).
보호 판정은 **문자열 규칙**이다: 보호 낱말 t가 원문에 있을 때 교정문에도 t가 그대로 있으면 허용(주변만 손댄 교정 — '콘텐츠개발'→'콘텐츠 개발'), 사용자가 정한 결과 u가 있으면 허용(겹침 합성 결과 — '리플렛등'→'리플릿 등'), 둘 다 아니면 드롭('가나문화사'→'가나 문화사'). 원문==교정문(검수 필요 카드)도 드롭 — 사용자가 이미 답을 적어 둔 낱말이다. ⚠ **1글자 표제어는 보호에서 제외**한다(교정은 한다): 부분문자열 보호라 '사' 하나로 문서 절반의 교정이 죽는다. ⚠ 교정문 칸이 비면 **보호 전용**(고치지 말 것)이 되고, 표제어 검색은 어절이 아니라 **부분문자열**이다(사용자는 '가나깅'만 적지 '가나깅은'까지 적지 않는다 — 부분문자열이면 조사형이 저절로 맞고 브리지 `RepeatFind` 좌표계와도 같다). ⚠ 경계 규칙의 **낱말 토큰**('기술'·'정보')은 보호 집합에 넣지 않는다 — 흔한 명사를 부분문자열로 보호하면 '기술울' 같은 오탈자 검수 카드까지 조용히 사라진다. 경계 보호는 ① 펼쳐 낸 어절 쌍을 보호에 등록하고 ② 다른 계층 교정의 **교정문에 경계 규칙을 적용해 어긋나면 맞춰 고쳐 준다**(`harmonize`) — 드롭이 아니라 조율인 이유는, 드롭하면 '그는 긔술을'→'그는 기술을' 같은 **오탈자 교정까지 함께 잃기** 때문이다. 조율 결과가 원문 그대로면(= 사전 결정을 되돌리기만 하는 교정) 그때는 드롭한다.
카드는 `source="user_dict"` · `category="사용자 사전"` · `reason="사용자 사전에 등록된 항목"`(문구 고정) · `confidence="high"`이며, 직렬화에서 **`status="accepted"`로 나간다** — 검수 화면에 수락된 상태로 등장한다. 거절·직접수정·재수락은 일반 카드와 같은 경로다. ⚠ 단 `_build_occurrences`가 이 카드만 `auto=False`로 둔다: `auto=True`면 거절할 때마다 "반복 항목을 반대로 처리할까요?" 팝업이 끼어드는데, 수락 상태로 뜬 이유가 반복 전파가 아니라 사용자의 사전이기 때문이다. `nikl_dict.validate`도 이 source를 건너뛴다(low로 떨어지면 `_needs_review`가 '검수 필요' 배지를 달아, 이미 답한 것을 되묻는 카드가 된다). `event_queue._SKIP_SOURCES`에도 들어 있다 — 개인 목록이지 조직 합의가 아니고, 사람 판단이 실린 적 없는 accepted가 학습 큐에 쏟아진다.
⚠ **AI 프롬프트는 건드리지 않는다.** 보호는 전부 결정론 후처리다 — 프롬프트는 내용뿐 아니라 순서 변경만으로 정밀도가 88→75%로 무너졌고(memory `gemini-call-hardening-and-prompts`), 글로서리 지침은 반복 표기 문서에서 504 폭주를 낸 전력이 있다(`glossary-runaway-504`). [2.5]는 지침을 더하는 게 아니라 목록에서 빼는 것이다.

**결과물 (output) is a user-chosen axis with five values** — `options["output_mode"]`, set by `SetupPanel`'s 2×2 card grid (full rationale + measurements: [docs/output-mode-annotation-design.md](docs/output-mode-annotation-design.md)):

| `output_mode` | HWP 원본 | 산출물 |
|---|---|---|
| `"hwp"` (default) | 치환 + 빨강 표시 | `_교정본.hwp` + 정오표 |
| `"hwp_memo"` | 치환 + 빨강 표시 + **같은 자리에 메모** | `_교정본(메모).hwp` + 정오표 |
| `"errata"` | **무수정** (opened only to read page numbers) | 정오표 |
| `"memo"` | **글자 불변**, 한/글 메모 필드 + 앵커 글자색 | `_메모본.hwp` + 정오표 |
| `"pdf"` | **무수정** (exported to PDF) | `_주석.pdf` (형광 + 스티커 주석) + 정오표 |

⚠ The axis is **orthogonal to 교정 방식** (항목별 검토 / 자동 일괄 적용), not a value of it: every mode still needs the review step, because accept/reject is what decides what gets written, recorded, or annotated. ⚠ Any mode other than `hwp` forces `gen_errata` on and locks that toggle — otherwise `errata` produces nothing at all and `memo`/`pdf` lose the only place that records **the spots that could not be marked**. ⚠ `errata_only` survives only as a derived bool meaning "the HWP was not modified"; it cannot tell them apart, so branch on `output_mode`. 한글 글자를 실제로 바꾸는 모드는 **`ApplyWorker.MODIFY_MODES`(= `SetupPanel.MODIFY_MODES`) 한 곳**에 적혀 있다 — `applied`·`_occ_plan`·S3/S4 재분류·정오표 잠금이 전부 그 집합으로 갈린다.

★**`"hwp_memo"`(빨간색+메모)는 메모 앵커가 원문이 아니라 교정문이다**(2026-09-03 사용자 지시). 치환이 끝난 문서에는 원문이 더 이상 없기 때문이다. 그런데 교정문은 **원래부터 그 표기였던 자리에도** 있다 — 실측(05.hwp): '항공유과'→'항공유와'는 1곳을 고치는데 '항공유와'가 문서에 이미 19곳 있고, 그중 첫 자리는 문서 앞쪽(char 2644)이라 순서만 보고 달면 **전혀 다른 자리에 메모가 박힌다**. 그래서 브리지 `memo`가 항목별 `red_only` 플래그를 받아 `_match_is_red()`(매치의 글자색이 교정 표시 빨강 255인가)로 **우리가 고친 자리만** 고른다. 검증: 치환 자리 쪽 8 ↔ 메모 자리 쪽 8 일치(필터가 없으면 앞쪽 자리가 나온다). ⚠ 색을 못 읽으면 통과시킨다(자리를 잃는 것보다 낫다) — 그래서 `doc_occ`(실제 치환 수)가 2차 방어선이다. ⚠ 검수 카드(`dict_flag`, 글자 불변)는 빨강이 없으므로 **원문 앵커 + `red_only` 꺼짐**으로 간다.
★**결과 화면의 '빨간색+메모' 추가는 이미 만든 교정본 위에 메모를 단다** — 불변식①('산출물은 언제나 원본에서 만든다')의 **유일한 예외**이고, 예외인 이유가 곧 그 불변식의 근거다(앵커가 교정문이라 교정본이라야 찾을 수 있다). `main_window._start_extra_output`이 `source_is_corrected`와 `hwp_output_path`(원본 기준 이름 — 안 그러면 `…_교정본_교정본(메모)`)를 넘기고, `ApplyWorker`는 치환 단계를 건너뛴다. ⚠ 그 실행의 `applied`·`occurrences`는 **0**이다(고친 게 없다). 메모 detail의 `original`은 앵커(=교정문)라 정오표가 어긋나므로 브리지가 `anchor_of`로 원문을 되돌려 싣는다.
⚠ 결합 모드는 치환 **직후** 메모를 다는데, 그 시점의 찾기 색인은 낡아 있다 — `_run_memo(reindex_first=True)`가 첫 묶음 전에 한 번 다시 만든다(memory `memo-reindex-stale-find-index`와 같은 부류).
★**결합 모드의 정오표는 메모 결과를 겹쳐야 한다** (2026-10-17 수정 — 감사 실측: 메모 68곳 중 9곳 실패인데 사유 0건·로그는 '정오표에 사유 기록'이라 거짓 안내·결과 화면 누락 0). 정오표 행은 치환 detail로 만들고 `ApplyWorker._overlay_memo_notes`가 메모 detail을 겹친다. 자리 대응은 **`red_rank`**(그 교정이 치환한 자리 중 문서 순 순번 — 메모 단계가 빨간 자리를 세는 좌표계와 같다)이고, 검수 카드는 원문 앵커라 `occ` 그대로다. 실패 자리는 `outcome="applied"`를 유지한 채(글자는 고쳐졌다) '교정은 반영됨 · …' 사유와 `unmarked`가 붙고, `result["unmarked"]`·결과 화면 '메모 못 함'에 잡힌다. ★결과 화면 추가 실행은 **진짜 교정본만** 입력으로 쓴다(`MainWindow._corrected_hwp` — 1차가 `hwp`이거나 추가 실행 `hwp`가 만든 것). ⚠ `result["hwp_path"]`를 쓰면 안 된다: 1차가 메모본이면 그 칸이 `_메모본.hwp`라, 그것을 교정본으로 여겨 **교정 51건 중 0건**이 반영된 `_교정본(메모).hwp`가 나왔다(감사 실측). 교정본이 없으면 원본에서 결합 모드를 처음부터 돈다. 교정본 위에 다는 경로는 그 교정본을 만든 실행의 정오표 행을 `base_errata_rows`로 받아 메모만 겹친다 — 메모 detail로 행을 다시 만들면 빨간 자리 순번이 패널 등장 번호로 읽혀 부분 거절 시 엉뚱한 행이 실패가 된다. 잔여 한계(실측 05.hwp): '…해야한다.'→'…해야 한다.' 꼴 2곳은 찾기로는 잡히는데 메모 단계가 놓친다(빨강 판정 추정) — 이제는 정오표·화면에 드러난다.

⚠ **`result["applied"]` means "characters actually changed in the HWP" and that meaning is never widened** — it stays **0** in the other three modes (the completion dashboard renders "적용 N건" from it). Accepted work rides on `to_apply`/`to_apply_occ`; what was actually marked rides on `memoed`/`memo_blocked`/`annotated`/`pdf_missing`. `result_panel` swaps card 03 (정오표 / 메모 / PDF 주석) but keeps the gauge titled 교정 수락률 in all three, because that is what the gauge counts. Do **not** revive the old heuristic `flagged > 0 and applied == 0` as the mode test — that state still exists (a run where nothing was accepted) and means something different.

**결과물은 사후에 더 만들 수 있다 — 결과 화면의 "결과물 추가"** (2026-08-07). Picking one mode used to be final: getting a second artifact meant 초기화 → re-pick → **redo the entire review**, even though accept/reject was already settled. `ResultPanel._build_outputs` (the 산출물 card) lists what was produced and offers **all four modes as buttons, always — the already-produced ones disabled** rather than removed (user directive 2026-08-12: dropping them shifted the remaining buttons on every click, and the right column alone could not say what had already been made). It only emits `extra_output_requested`, and `MainWindow._start_extra_output` runs the *same* `ApplyWorker` with `output_mode` overridden. The card is a **2-column grid — left "만들어진 것", right "더 만들 수 있는 것"** (user directive 2026-08-12): stacked in one column, the add-buttons read as more produced artifacts. Each artifact row is 형식 아이콘 + 산출물명 over its 서브 내용, with a filled accent 폴더 열기 on the right; **the file name is not printed** (the artifact name already says what it is, and long names wrapped the row to two lines). **One extra run = one row**: an extra output always carries its own errata, so the pair is merged — '메모본 + 정오표 (메모)' with both icons and both counts ('메모 61항목 · 정오표 68행'). The primary run is *not* merged: its errata is a separately toggleable artifact that may not exist. ★And `_produced_modes` treats `errata` as produced only when the errata is the **primary run's own** (`errata_path` without `errata_from_extra`) — a 정오표-off run that later adds a 메모본 gets `result["errata_path"]` filled by that memo run, and the old "any errata file exists" test then **deleted the Excel(정오표) button**, leaving no way to produce an errata for the 교정본 (user report 2026-08-12). Four invariants, each of which silently produces a wrong artifact if broken: ① **always built from the original file** — memo/PDF anchor on the 원문 string, and on a 교정본 that string has already been replaced, so it cannot be found (the original is never written to: `save_as` writes a new path and `close` is a bare `Quit`); ② **decisions are never re-asked** — `self._corrections` plus `_applied_occ_rows`, the snapshot taken at `_start_apply`, so partial rejects survive; ③ **the first run's numbers are never overwritten** — an extra run lands in `result["extra_outputs"]`, keeping the `applied` invariant above intact and the dashboard's 01/02/03 cards a record of the primary run; ④ **an existing errata is never overwritten** — `_extra_errata_path` names it `_정오표(메모).xlsx` etc., because the content differs per mode (PDF adds a column, memo adds 메모 불가 notes) and the user may already have the old one open. ⚠ It used to fall back to the plain `_정오표.xlsx` when the primary run had produced no errata; that exception cost a user their answer (2026-08-10). A 교정본 run with 정오표 turned off, then a memo run added: the memo errata landed on the plain name, and the 산출물 card labelled it just "정오표" with the *primary* run's row count — so "메모 불가 150곳" had its explanation sitting in a file that looked like something else and the user read it as "정오표(메모)가 생성되지 않았다". The suffix is now unconditional, and `result["errata_from_extra"]` keeps `_artifact_rows` from attributing an extra run's errata to the primary one. The extra run also passes `known_pages=result["pages_by_original"]`, so `ApplyWorker` skips the locate pass — which makes an added 정오표 open **no HWP at all** (실측 1.3s), and guarantees both errata files quote the same 쪽. ⚠ Errors take `_on_extra_error`, **not** `_on_error`: the latter returns to 설정, which would throw away the completed run's result screen because a *second*, optional artifact failed.
★**`ApplyWorker.error` means "this run ended without a result"; non-fatal problems go on `ApplyWorker.warning`** (정오표 저장 실패 · PDF 변환/주석 실패), which is always followed by `finished`. They used to share `error`: `_on_error` opened a modal and then jumped to 설정, `finished` was processed inside that modal's nested event loop and drew the result screen, and closing the modal **bounced the user back to 설정** (audit, reproduced on MainWindow). `MainWindow._on_worker_warning` only logs and collects; `_flush_warnings` shows them in one popup on the next tick after the result screen is up. ★Cancellation has one common gate after the editor/PDF stage: if `_stop` is set and no HWP output was saved, the run emits the cancel `error` and returns (deleting a just-exported, unannotated `_주석.pdf`). Before, a cancel during the page-number scan skipped the memo/PDF branch, built the errata and sent `finished` — the user pressed 취소 and got "메모본 생성 완료 · 메모 0곳".

**The 산출물 card is the only place 완료 단계 owns artifacts** (2026-08-11, user directive). The footer's result-only actions (정오표 열기/생성 · 폴더 열기) and `StatusFooter.set_result_actions`/`errata_clicked`/`folder_clicked` are **removed** — the only footer action left on the result screen is 초기화. The card already lists every file produced with its own name and row/곳 count and opens each one's folder, so a second copy in the footer could not say *which* 정오표 it meant once memo/PDF runs add their own (`_정오표(메모).xlsx` …) and would contradict the list. `main_window._on_generate_errata_requested` (manual errata build) went with it: the card's 결과물 추가 → `errata` runs the real `ApplyWorker` with `output_mode="errata"`, so 쪽 번호와 적용 결과가 실제 실행에서 나오고 파일 이름이 출처를 밝힌다 — the manual path blanked 쪽 when it had no row data and wrote the ambiguous plain name. **`.hwpx`도 같은 방식으로 보호된다** — [core/hwp_styles.py](core/hwp_styles.py)가 ZIP 안 `Contents/header.xml`(OWPML)에서 같은 지문을 만든다. 검증은 **같은 원고를 두 형식으로 저장해 지문 목록이 한 글자도 다르지 않은지**로 했다(표본 3개·56종 전부 일치). ⚠ 그 과정에서 잡은 함정 셋: ① 꺼져 있는 속성의 색은 **0으로 눕혀야** 한다(.hwp는 밑줄이 없어도 밑줄색을, 그림자가 없어도 그림자색을 들고 있는데 OWPML은 요소 자체가 없다 — 안 눕히면 23종이 전부 어긋난다); ② 선 모양 **실선(SOLID)은 0**이다; ③ **취소선은 바이너리에서 '밑줄 종류 2'로 들어간다**(OWPML은 `<hh:strikeout>`로 따로 적는다). ⚠ hwpx에는 `<hp:t charStyleIDRef>`라는 명시적 스타일 참조가 **있지만 지킬 수 없다** — 편집 없이 열었다 저장만 해도 134→104로 줄어드는 한/글 자체의 손실이다(실측). 우리가 지킬 수 있는 것은 `.hwp`와 같은 **charPr 동일성**이고, 형광펜이 그것을 지킨다(실측: 빨강은 새 charPr 109를 만들고 형광펜은 스타일의 charPr 1을 유지).

**메모 모드** goes through bridge command `memo` (`HwpEditor.insert_memos`). Three invariants are load-bearing, all found by measurement — see the module header in `hwp_bridge_worker.py`: ① use `HAction.Run("InsertFieldMemo")`, **never** the top-level `hwp.Run(...)` (a no-op on HWP 2010 that returns `None` for everything, so a following `InsertText` writes the reason **into the manuscript**); ② verify the memo actually opened by checking that `GetPos()[0]` (story) changed, not the return value; ③ 머리말·꼬리말 stories **refuse** memos — that is a structural limit, not a failure, so those spots are counted as `blocked` and written to the errata. ⚠ And because the memo body quotes the original, `RepeatFind` finds **its own memos** and multiplies them — the bridge remembers each memo's substory id and skips matches inside it **without advancing the occurrence counter** (advancing it would desync `skip_occurrences`), capped by `occ_total`. ⚠ A memo control occupies **8 position units** (`_MEMO_CTRL_SPAN`), and after insertion the caret returns to the control, *in front of* the anchor — approximating that advance leaves the caret short and `RepeatFind` re-finds the same word, stacking memos on one spot (and then failing with a COM server fault when it tries to open a memo on top of a memo). Three layers guard it: SetPos, verified via GetPos, then MoveRight, then a re-find detector. ⚠ **Never verify this by counting memos** — `occ_total` caps the total, so a stacked run counts correct; count *distinct spots* instead (in OWPML, memo controls with no body text between them). Anchor text is never recolored (user directive 2026-08-07: the manuscript's formatting is part of the manuscript), and the memo body carries **no '이 낱말 N곳 중 k번째' line** (user directive 2026-08-10 — the errata already says that, one row per occurrence; the PDF annotation dropped its '· 이 낱말 N곳' line for the same reason). ⚠ The memo and PDF bodies are built by **one function, `output/annot_text.annotation_body`** — they must say the same thing, and building them separately is how they drifted. It drops the `[검수]` tag (user directive 2026-08-11: a memo/annotation artifact *is* the review list, so tagging every line 검수 says nothing) and collapses the duplicated type label — the pipeline's reasons often re-state their own category, so `[규범표기]` + `[규범표기] 규범표기인 '슈퍼마켓' 권장` printed 규범표기 **three times** on one line; the leading tag is stripped and the category prefix omitted when the reason already opens with it.
★**A memo control is invisible to `RepeatFind` for the rest of the session, and that is why memo runs used to lose half their memos** (fixed 2026-08-10 — user report "메모 다량 유실": 메모 127곳 · 메모 불가 150곳 on a 152-item manuscript). Once a spot has a memo, a later search for a word that *overlaps or abuts* it still returns a match computed from the pre-memo text; opening a memo there makes `InsertText` die with `RPC_E_SERVERFAULT`, and **that spot never recovers in the same session** — CloseEx+reopen, DeleteFieldMemo+retry, retrying at the match tail, sleeping, and re-running the failed spots at the end of the run were all measured and all failed (102 spots retried, 1 recovered); worse, the reopen variants leave an **empty memo** behind (302 good memos + 92 empty ones in the saved file). Do not add an in-place retry. The fix is `HwpEditor._reindex_document`: every `_MEMO_REINDEX_ITEMS` (25) items the document is **saved to a staging file in `cache_dir()`, closed, and reopened**, which rebuilds HWP's find index. The trigger is **memos written, not items processed** (`_MEMO_REINDEX_MEMOS`, 40) with the item count as a backstop — how fast the index goes stale tracks how many memo controls were planted since the last reopen, and a single 36-occurrence word can eat a whole item-based window (실측 per 25-item window, memos→failures: 24→0 · 40→0 · 49→2 · 51→0 · 58→12 · 97→11, i.e. it degrades sharply past ~50). Measured on the same manuscript: **116 → 312 of 335 spots, 0 empty memos, 68s → 64s** (the reopen cost is offset by no longer burning time on doomed inserts). ⚠ Two tempting knobs were measured and rejected: tightening the memo threshold to 25 made it *worse* (23 → 31 failures — each reopen bakes the memo controls in, so more neighbouring spots become unfindable), and ordering real typos first so they run while the index is fresh also made it worse (312/335 → 305/336) **and did not save them** — the residual failures are bound to a *place*, not to a position in the queue (verified: the same typos succeed 6/6 in an isolated session). Two supporting details are load-bearing: `HwpEditor.open()` must clear `_stderr_stop` **and drain both queues** (a leftover EOF sentinel makes the first command after a reopen fail with "브리지에서 응답 없음"), and `_memo_stories` is now **document-scoped, not per-`memo`-command** — `insert_memos` sends 5 items per command, so resetting it per command forgot the earlier batches' memos and let the finder treat memo bodies as manuscript occurrences. ⚠ The bisection that found this is the cheap way to re-verify: '키메세지'(36 spots) then '메세지를' (which lives inside '키메세지를') fails; drop '키메세지' from the same item set and it is 12/12.
⚠ **memo and PDF skip `shadowed` occurrences; the 교정본 does not** (`ApplyWorker._annot_skip_for`). One spot gets one mark, the errata already omits shadowed rows, and marking them would both re-introduce an artifact divergence and create the overlapping-anchor collision above. Replacement keeps them because a longer correction may leave the substring intact for the shorter one to normalize (`ReviewPanel._derive`).

**PDF 모드** exports via bridge `export_pdf` (⚠ clear the selection first — a live selection makes HWP export **only that range**, returning True either way) and then annotates with [output/pdf_annotator.py](output/pdf_annotator.py) (`pypdfium2` search + `pypdf` write; both BSD — ⚠ never PyMuPDF, it is AGPL). ⚠ `FreeText` annotations render **empty** for Korean (no embedded font in the appearance stream) — use `Highlight` (which carries the note in its own `/Contents`) or `Text` sticky notes. ★**One correction spot = exactly one annotation**: the highlight holds the text, so pairing it with a sticky note doubles every row in the viewer's 주석 목록 (290 rows for 145 corrections — user report 2026-08-08). The hard part is occurrence alignment: a running head lives once in the HWP story but is rendered on every PDF page, so matches repeating at the same **(x, y)** across ≥3 pages are dropped as running heads (y alone also drops body lines); if the counts still disagree, index mapping is abandoned and **every** occurrence is annotated with a visible 자동 대조 실패 warning rather than silently guessing. ⚠ The errata's `PDF 쪽` column is a **separate coordinate system** from `쪽` (prnpageno) — never compute one from the other.
★**The three artifacts must mark the same spots** (2026-08-08 — user report: "반영된 항목이 다 다르다, 신뢰성에 치명적"). They drifted for two independent reasons, both now fixed, and the shared rule that came out of it is: **the occurrence coordinate system is what the bridge's `RepeatFind` sees on the unmodified document** — i.e. `locate_originals` — *not* `Correction.occurrences`, which the review panel counts over the *extracted text*. Both `memo` (`occ_cap`) and `pdf` (`_align_occurrences`) now take `doc_occ = len(pages_by_original[original])` as their bound; 실측 05.hwp: '지속가능항공유' is 5곳 in the extracted text but 4곳 in the document, and the memo pass used to run to 5 and mark one spot the other two artifacts never touched. ⚠ The second cause was PDF-only and worse: **pdfium's `search()` ignores whitespace** — `'국방 분야'` and `'국방분야'` returned *byte-identical* result sets (33 matches), so a 띄어쓰기 correction accepted at 2곳 got highlighted at 25곳. `_search_all` now reads back `get_text_range(idx, cnt)` and drops matches whose spacing differs (`_spacing_ok`), tolerating only whitespace introduced by a line break (`'엔\r\n진 부품'` is a genuine '엔진 부품'). ⚠ That line-break tolerance had a false-positive twin, fixed 2026-08-10: '도움요청'→'도움 요청' (문서 4곳) matched **5** places in the PDF because a correctly-spaced '도움 요청' on p.114 happened to break across a line, so deleting the break made it read '도움요청'. The count mismatch then failed alignment and stamped "⚠ 위치 자동 대조 실패" on *all four* good highlights plus the bogus one. Matches now carry `exact` (the glyphs matched literally) and `_drop_ambiguous` discards the line-break-only ones **when, and only when, the remaining exact matches equal `doc_occ`** — evidence, not preference. It never fires when matches are already correct or too few, so the genuine `'엔\r\n진 부품'` case survives (verified on the same PDF: '도움 요청' 8곳 keeps its one line-broken match). ⚠ Two differences remain and are **legitimate, named, and recorded per-occurrence in the errata** — never "fix" them by making the counts equal: ① 검수 항목 (`dict_flag`, corrected == original) is marked in memo/PDF but **not** in the 교정본, because 빨강 means "이 자리를 고쳤다" and nothing was; ② 머리말·꼬리말 spots accept a replacement and a PDF highlight but **refuse a memo**. The errata's outcome class is identical across all three (`applied`↔`todo` is the same decision, worded for who does the work), and anything a mode could not mark carries a `note` and is counted in `result["unmarked"]` — the memo/PDF equivalent of the 교정본's S4 부분 반영 safety net, without which a missed spot reads as a completed one.

⚠ `docs/proofreading-architecture.md` Phase 2b describes an earlier 검수 모드 entered by "selecting 0 AI scopes". **That entry path is unreachable** — `scopes_selected()` gates 분석 시작, and 윤문 is locked, so a scope is always on. It also claims the apply stage never *opens* HWP; that is no longer true (it opens read-only to read page numbers). Treat that section as history.

**The errata is per-occurrence, keyed by 한/글 page number** (2026-08-05 rework). One row = one physical spot in the manuscript, so a word corrected in 12 places yields 12 rows — which is also what makes a partial reject legible (the accepted spots land in 적용, the rejected one in 거절). Sheets split by outcome — 적용 / 거절 / 확인 필요 (실패+검수), created only when non-empty — and every sheet carries the same five columns 쪽·수정 전·수정 후·교정 이유·교정 유형 so they can be concatenated. ⚠ Manuscript strings must never be interpreted by Excel: `errata_generator._wcell` strips openpyxl's illegal control characters (**one** of them used to abort the whole errata with `IllegalCharacterError`) and pins any `=`-leading value to a string (openpyxl stores it as a formula → `#NAME?`/`#REF!`). 교정 유형 is `Correction.category` (맞춤법·띄어쓰기·규범표기…); the *source* is carried by row background color instead, which is why the old 출처 column is gone (it duplicated 교정 유형, both being the source label).

⚠ **The page number is `KeyIndicator()[3]` (prnpageno) — the coordinate 한/글's own Ctrl+G navigates by** (verified: `Goto` 10 lands on prnpageno 10), so a user can type an errata number straight into 쪽 찾아가기. It is deliberately *not* an absolute page count: it honours per-구역 renumbering, so it is neither globally monotonic nor unique (실측: 실파일F ends at prnpageno 152 with `PageCount` 160; 실파일G starts at 2). **Never sort or do arithmetic on it.** ⚠ **Pages must be collected from one pre-apply snapshot** (`HwpEditor.locate_originals` → bridge `locate`, find-only, document unmodified): replacements repaginate as they go, and apply runs in longest-original order, so pages read *during* apply drift out of step with each other (실측: the 12th occurrence of a word moved 15쪽 → 16쪽 mid-run). The bridge's `apply` still records `occ_pages` per match — but that is used to decide **which occurrence was actually replaced**, with its page only a fallback. `KeyIndicator` costs 0.13ms so it rides along free; the cost is `RepeatFind` (~9ms/occurrence measured over 297 occurrences), bounded by `_LOCATE_BUDGET`/`_LOCATE_SECONDS` — exhausting them blanks the 쪽 cell ("—") and never drops a row. `HwpxEditor` (direct backend) has no `locate_originals` at all: it edits XML with no layout engine, so page numbers are unknowable there and every 쪽 reads "—".

★**`skip_occurrences` lives in the pre-apply coordinate system, and apply invalidates it** (fixed 2026-08-08 — user report: "교정본에만 '해야한다'가 미반영"). `apply_corrections` replaces **longest original first**, so by the time a short original runs, every occurrence of it that sat inside a longer *applied* correction is **gone from the document** — the survivors renumber, and the old indices then point at innocent spots. 실측: '해야한다' 14곳 중 5곳이 '고려해야한다' 등에 먹혀, skip `[5,8,9,11,12]`가 남은 9곳(0..8)의 5·8번을 건너뛰어 **멀쩡한 2곳이 교정본에만 안 고쳐진 채 남았다**. `ApplyWorker._plan_occurrences` now recomputes this: it takes the occurrence spans (`pos`/`end`, newly carried by `get_occurrence_rows`), drops the occurrences that a *different* accepted correction's span fully contains, and renumbers the rest — so `skip` is expressed in the coordinate system the bridge will actually see. ⚠ **Never "fix" this by just clearing `skip_occurrences`**: it carries three different things — user rejections and `excluded` substring hits both **survive** the replacement and must keep being skipped; only the ones a longer *applied* correction swallows disappear. Dropping all three would replace spots the user explicitly rejected. ⚠ The remap runs for `mode == "hwp"` **only** — memo/PDF never change the document, so their occurrences never vanish and remapping there would itself desync them. `_build_errata_rows` translates bridge indices back through the same map (`survivors`), and S4's expected counts use the post-remap totals so a normal run no longer reads as 부분 반영.
★**When the bridge finds fewer occurrences than the panel expects, the errata realigns by 쪽, never by position** (`_realign_by_page`, 2026-08-10 — user report: "94쪽 리플렛 2개는 치환 성공인데 정오표엔 실패로 나온다"). HWP's 찾기 cannot reach some spots at all (auto-bullet paragraphs — memory `find-blindspot-auto-bullet`), so the bridge's occurrence list is simply shorter. Pairing the two lists by order then shifts everything after the first gap, and the *last* rows get blamed instead of the missing ones: 실측 '리플렛' 15곳 → 4 absorbed by longer corrections → 11 expected, 9 found; the 교정본 actually kept 51·69쪽 unfixed while the errata marked 94쪽 ×2 as failed. 쪽 is the only coordinate both sides share, so the alignment walks both in document order and skips panel occurrences whose 쪽 does not match. ⚠ It is accepted only when it explains the gap exactly (leftover bridge entries, or an unfound count ≠ the size difference, means the alignment is wrong) — otherwise it falls back to the positional map rather than guessing.
★**The rule for "is this occurrence skipped" has exactly one implementation: `core.models.occurrence_skipped`** (fixed 2026-08-10 — user report: PDF missing a '고립예방'→'고립 예방' annotation). Two layers were deciding it independently: `ReviewPanel._derive` (`excluded` ⇒ skip, `shadowed` ⇒ don't) and `_plan_occurrences` (which looked only at `status != "accepted"`). `_apply_unify_forward` marks **every** occurrence of a consistency group accepted — including `excluded` ones — so the moment the remap fired, every excluded occurrence became a replacement target: '고립예방' was accepted at 3 spots in the review panel and the PDF annotated exactly those 3, while the 교정본 replaced **all 10** ('고립예방사업'→'고립 예방사업', '고립예방플랫폼'→…). The 교정본 was the wrong one; the PDF was right. Both layers now call the shared predicate, so fixing one can no longer be silently undone by the other. ★A second, independent shift in the same remap was found by re-running the same file: an occurrence contained in a longer applied correction **only disappears if that correction's replacement removes it**. `'고립예방센터)'→'(고립예방센터)'` merely adds a paren, so '고립예방' is still there and `RepeatFind` still finds all 10 — while `skip` had been computed for 9, shifting every index by one. 실측: 수락 {3,4,7} → 교정본이 바꾼 자리 **{2,3,6,9}** (수락한 2곳 누락 · 등장 아닌 3곳 오적용). The test is now `orig not in wc`, which still catches the case the remap was built for ('해야한다' inside '고려해야한다'→'고려해야 한다', where the substring genuinely dies).

★**Overlapping corrections are composed into one spot, not raced** — `ApplyWorker._compose_spots` (2026-08-10, user report "세 산출물의 정합성이 맞지 않는다"). `Correction` is *one original → one corrected*, so a word cannot have a different result per position. But overlap makes exactly that happen: '리플렛' is '리플릿' normally, yet inside '리플렛등'→'리플렛 등' it is part of '리플릿 등'. The old model raced them (longest span wins ⇒ `shadowed`) and the workaround leaked differently into each output — the 교정본 replaced twice and produced the composed text, the errata dropped the shadowed row so the composition went **unrecorded**, and memo/PDF did not mark the spot at all. Four outputs, three answers. Now a pre-pass folds each overlap group into a single composed edit: the outer correction replaces the whole span with the composed string in one operation, the inner occurrences are marked `absorbed` and skipped in **every** mode, and errata/memo/PDF all quote that one string. ⚠ **Not composing is not an option** — outer-only gives '리플렛등'→'리플렛 등', leaving the typo in place; this is a correctness bug before it is a consistency bug. ⚠ Scope is **inside an already-accepted correction span only** (user directive): there the editor has already decided to change that region, so even a fragment that `_mark_stem_boundary_skips` marked `excluded` is composed in ('고립예방' inside '고립예방센터)' ⇒ '(고립 예방센터)'), while the same fragment **outside** any accepted span stays protected ('고립예방' inside '고립예방사업' is untouched). ⚠ Composition is **declined when a correction's occurrences would compose differently**, because one `Correction` cannot carry two results — picking one would corrupt the other spots. 실측 (실파일 고독사): 14 overlapping spots, 5 corrections composed / 6 occurrences absorbed; the other 8 spots needed nothing because the outer already subsumed the inner ('고독사예방 홍보'→'고독사 예방 홍보').
★**The composition happens in the review panel, so the card shows what will actually happen** (`ReviewPanel._compose_overlaps`, 2026-08-10 — user report: "애초에 검수 카드에 '리플릿 등'으로 제안하지를 않네, 그래서 사용자가 '리플렛 등'으로 수락"). Composing only at apply time left the card advertising '리플렛 등' — the dependent-noun spacing card's own mechanical output — while the document ended up '리플릿 등'. **That is worse than an artifact mismatch: the user's decision rests on a string that will never exist.** So `_derive_all` recomputes it on every status change and `_sync_corrected_widgets` updates the field in place. ⚠ It is **reversible**: rejecting the inner card ('리플렛'→'리플릿') returns the outer card to '리플렛 등', which is why the pre-composition value is kept in `_compose_base` and recomputed rather than written once. ⚠ A card the user edited by hand (`_edited`) is never overwritten. ⚠ **When the outer card is a 검수 필요 card (`dict_flag`, 원문 = 교정문), `excluded` fragments are not composed** (user decision 2026-10-17). The "compose excluded fragments inside an accepted span" rule rests on "the editor already chose to change that span", and accepting a 검수 필요 card only means "checked" — without this, accepting '국가형긴급복지지원' (검수) spaced it to '국가형긴급복지 지원' via the stem-boundary-protected '긴급복지지원'→'긴급복지 지원'. Same-span duplicates ('테이블수' 검수 + '테이블수'→'테이블 수') are still composed — that just shows the spacing card. ⚠ Containment is found by an **O(n log n) stack sweep cached in `_ov_pairs`** (invalidated whenever occurrences are created or a reverse correction joins) — the naive pairwise scan is O(occurrences²) and would add hundreds of ms to every click on a 3,800-occurrence manuscript (measured here: 4,000 occurrences → 3.1ms first call, 1.0ms cached). `ApplyWorker._compose_spots` stays as a safety net and simply declines when the value is already composed.

⚠ `ReviewPanel.get_occurrence_rows()` is the only truthful source for per-occurrence decisions — `skip_occurrences` alone **cannot** be inverted, because it mixes user rejections with `excluded` positions (a substring hit that was never a real occurrence, e.g. '성장단계' inside '성장단계별'). Writing those to the errata as 거절 would record a decision the user never made, so `excluded` and `shadowed` occurrences are dropped from the errata entirely.

The `Correction` dataclass and highlighting colors (Windows COLORREF) live in [core/models.py](core/models.py). All API/chunk/throttle constants are in that same file — change tuning there, not at call sites.

### Config and API key resolution

[core/config_loader.py](core/config_loader.py) `ConfigLoader.get_gemini_key()` resolution order:
1. `GEMINI_API_KEY` env var
2. `[API] GEMINI_API_KEY` in `config.ini` (next to the EXE, or repo root in dev)
3. Encrypted org key from the build-injected `core/_org_keys.py` (see "Building for distribution").

⚠ `config.ini` is read with **`utf-8-sig`** and a malformed file is ignored with a stderr note (`_load_ini`) — a BOM (Notepad adds one) used to raise `MissingSectionHeaderError` inside `MainWindow()` and the app never opened. ⚠ The user-folder `config.ini` receives **only what was read from it plus what the app set** (`_user_cfg`); the merged view `_cfg` is read-only. Writing the merged view (the old behaviour) copied the deployer's EXE-side values into the user file on the first theme toggle, and since the user file wins, later deployer changes were ignored forever. `_save` also drops non-[APP] entries identical to the EXE-side value, which cleans up copies made by older versions without changing any effective value.

All three keys resolve identically (env → `config.ini [API]` → encrypted org key): `get_gemini_key()`, `get_nikl_key()` (`NIKL_API_KEY`, 우리말샘), `get_onterm_key()` (`ONTERM_API_KEY`, 온용어). 우리말샘 and 온용어 are **different services — their keys are not interchangeable** (verified: the 우리말샘 key returns `returnCode 100` on 온용어). A missing Gemini key disables the app's core function; a missing dictionary key silently disables just that fallback.

### 실행 게이트 — 사내 계정 로그인 (2026-08-05)

`main.py`는 테마 적용 후 [ui/widgets/login_dialog.py](ui/widgets/login_dialog.py) `require_login()`을 호출하고, None이면 `sys.exit(0)` — **통과 전에는 `MainWindow`를 생성하지 않는다.** 창을 띄운 뒤 기능만 잠그면 해제 경로가 UI 전역으로 번지기 때문. 저장된 세션(DPAPI `data/.ks_session`)이 있으면 `SessionRestoreWorker`가 먼저 검증해 입력 없이 통과하고, 게이트 모드에서는 취소 문구가 '종료'다. 로그아웃(`MainWindow._logout`)은 게이트를 다시 세우고, 재로그인을 취소하면 창을 닫는다.

**계정은 두 종류이고, 신원은 서버 함수 `ksai_my_profile()` 하나가 판정한다** (2026-10-16 분리 — 사용자 결정: 무료 프로젝트 상한 때문에 ks-works와 **같은 Supabase 프로젝트 안에서** 분리, 기존 직원 계정은 무변경). ① `employee` — ks-works 직원(`employees`), 지금처럼 그 계정으로 로그인. ② `member` — 앱 전용 회원(`ksai_members`: 로그인 ID·이름·권한·상태만, 인사 정보·평문 비밀번호 없음). 회원은 employees 행이 없으므로 ks-works가 로그인 직후 로그아웃시키고 ks-works RLS(전부 `current_employee_id()`/`is_admin()`)도 막는다. 관리자가 헤더 계정 메뉴 → **사용자 관리**([ui/widgets/member_admin_dialog.py](ui/widgets/member_admin_dialog.py))에서 추가하며 초기 비밀번호는 **ks2026**(서버 Edge Function 상수가 정본, `core/member_admin.INITIAL_PASSWORD`는 표시용), 첫 로그인 때 `require_login`이 **게이트 안에서** 변경을 강제한다(오프라인 유예 통과 시엔 강제 안 함 — 서버에 못 닿으니 바꿀 수도 없다). ★**ks-works 퇴사자는 같은 ID로 회원 전환**한다: auth.users 이메일은 유일해 새 계정을 만들 수 없으므로, 확인(`code=former_employee` → `allow_former_employee`) 후 **그 auth 계정을** 차단 해제·비밀번호 초기화하고 `ksai_members`에 등록한다. employees의 퇴사 기록은 읽기만 하므로 ks-works는 계속 막힌다(퇴사자는 `current_employee_id()`가 null). 그래서 `ksai_my_profile()`의 판정 순서가 **재직 직원 → 회원 → 퇴사 직원(거부)**이다 — 직원 행이 무조건 이기면 퇴사 행이 회원 행을 가린다. ⚠ ks-works에서 그 사람을 다시 '퇴사' 처리하면 auth 차단이 걸려 앱 로그인도 막힌다(사용자 관리 '사용 재개'로 해제). 서비스 키가 필요한 일(생성·초기화·중지·비밀번호 변경)은 전부 Edge Function(`ksai-admin-members`·`ksai-change-password`)이 하고, 소스 정본은 [server/supabase/](server/supabase/)다 — **서비스 키를 앱에 넣지 말 것.** ⚠ **앱에서 비밀번호를 바꿀 수 있는 건 회원뿐이다**: 직원은 auth.users를 ks-works와 공유하므로 여기서 바꾸면 ks-works 비밀번호와 관리자용 평문 미러(`employee_credentials`)가 어긋난다 — 서버가 403으로 거부하고 메뉴는 ks-works 마이페이지로 안내한다. ★**명단과 공유 뇌 기여자** (2026-10-16): 추가 대상 직원 명단의 인사 정보는 `ksai_roster`(로그인 이메일 PK — 계정 생성 **전에도** 존재해야 해서 `ksai_members`와 분리)에, 공유 뇌 **이벤트 기여자**는 `ksai_brain_contributors`(이메일 목록 — 명단 밖 ks-works 직원도 지정하므로 명단의 열이 아니라 별도 테이블) + **관리자는 규칙**(`userdict_can_contribute()` = 활성 AND (큐레이터 OR 목록))으로 정한다. `userdict_events` INSERT 정책이 이 함수를 요구하고, `ksai_my_profile()`의 `brain_access`로 앱이 비기여자의 이벤트를 **기록부터 하지 않는다**(`auth.can_contribute()` — 정책만 막으면 업로드가 매번 거부돼 로컬 큐만 자란다). 스냅샷 수신은 전원 유지(승인된 결과물은 노이즈가 아니다). 둘 다 개인정보/권한 테이블이라 RLS on·정책 0 — Edge Function `list`도 전화번호·성별은 내보내지 않는다. ⚠ **명단 데이터는 저장소에 두지 말 것**(퍼블릭) — DB에만 있다. 관리 화면의 '명단 계정 일괄 생성'(`provision_roster`)이 계정 없는 명단 인원을 만든다(퇴사자는 전환, 재직자는 건너뜀).
⚠ **Supabase MCP는 파괴적 SQL(`TRUNCATE`·`DROP POLICY`)을 사용자 확인 없이 자동 거절한다**(`status: declined` — 사용자가 거절한 게 아니다, 3회 실측). `DELETE … WHERE true`·`ALTER POLICY`는 통과한다.

⚠ **`employees`를 직접 SELECT하지 말 것**: ks-works RLS상 직원 토큰은 전 직원의 전 열(휴대폰·생년월일·휴직 여부…)을 읽을 수 있다. 앱이 받는 신원은 이름·권한·상태뿐이어야 한다.

⚠ **게이트가 막는 건 "릴리스를 받아서 그냥 쓰는" 비사용자다** — 내장 키 자체는 퍼블릭 릴리스에서 추출 가능하므로(위 "Building for distribution" 참조) 키 유출 대책이 아니다. 그 목적이면 서버 프록시가 필요하다.

⚠ **오프라인 유예(`core/auth.GRACE_DAYS=7`)는 게이트가 전사 단일 장애점이 되지 않게 하는 장치이고, 그 전제는 "실패의 종류 구분"이다.** 서버가 **명시적으로 거부**하면(refresh 400/401/403·`terminated_at`·employees 미등록) 세션을 폐기하고 재로그인을 강제하지만, **네트워크/서버 오류**(status 0·5xx·타임아웃)는 마지막 성공 검증(`verified_at`)이 7일 이내면 통과시킨다. 예전 `restore()`처럼 *모든* 실패에 세션을 비우는 코드로 되돌리면 유예가 원리적으로 불가능해진다 — `_fetch_profile`이 `(status, prof)`를 돌려주는 것도, `_apply_token_response`가 프로필 조회보다 **토큰 반영을 먼저** 하는 것도(회전된 refresh_token 유실 방지) 같은 이유다. offline 세션은 유효한 access_token이 없어 동기화·큐레이션이 자동 no-op이고, 교정은 로컬 사전만 쓰므로 정상 동작한다. 개발 우회 `KS_SKIP_LOGIN=1`은 **frozen이 아닐 때만** 통한다.

### UI flow (v5) — 단일 워크스페이스 셸

[ui/main_window.py](ui/main_window.py) is a **persistent single-workspace shell**, not a wizard. The root layout is **horizontal**: a full-height left `Sidebar` ([ui/widgets/sidebar.py](ui/widgets/sidebar.py) — brand wordmark on top + embedded `StepperRail` nav + `© kim daekyung`/version footer at the bottom) and, to its right, a **main column** holding `AppHeader` (top — a **custom title bar**: theme-toggle + new-file on the left, window minimize + close on the right; the logo lives in the sidebar) / center row (`stage` + `ActivityPanel`) / `StatusFooter` (bottom). The window is **frameless** (`Qt.FramelessWindowHint`, no native title bar); `MainWindow.nativeEvent` handles Win32 `WM_NCHITTEST` to give edge-resize on all sides and turns the top `_DRAG_ZONE_H` strip (minus interactive buttons) into the move/snap region via `HTCAPTION`. The header and footer are therefore confined to the main column (separated from the sidebar). `StepperRail` exposes the 4 macro steps 설정/분석/검토/완료 with per-step result subtitles; built with `embedded=True` it drops its own width/chrome so the sidebar owns the background+border. `MainWindow.rail` is an alias for `sidebar.rail` so existing call sites are unchanged. Regions are built once and never destroyed; only the center `QStackedWidget` (`stage`) swaps among four panels in `ui/widgets/`: `SetupPanel` (upload+options merged) / `RunningPanel` / `ReviewPanel` / `ResultPanel`. `_show_phase()` keeps rail/footer/stage in sync; review is skipped when `options["auto_apply"]` is true (confidence=="low" auto-rejected). Two QThread workers (`ProofreadingWorker`, `ApplyWorker`) are owned by the window; their signals fan out to the persistent components. `_cleanup_worker` requests stop and waits up to 5s before discarding — keep that pattern when adding new workers.

⚠ 설정 화면의 결과물 카드는 값이 다섯이 되어 **2칸 × 3줄**이다(홀수라 마지막 줄 빈 칸은 stretch로 채운다 — 안 채우면 남은 카드가 줄 폭 전체로 늘어난다). 줄이 하나 늘어난 만큼 `setup_panel`의 세로 여백 상수 6개를 한 번 더 조였다(`_CARD_PAD_V` 9 · `_ROW_PAD_V` 8 · `_SEC_GAP` 9 · `_SEC_SPACING` 16 · `_MAIN_PAD_V` 14 · `_ROW_GAP` 10) — 기본 창(1500×900)에서 세로 스크롤이 사라지는 것을 실측했다(내용 666px / 뷰포트 758px). ⚠ 가로 여백은 여전히 건드리지 말 것.

**설정 화면의 우측 칸은 첨부 2단이다** (`AttachPanel`, 2026-09-03): 위 `FilePanel`(한글 원고) : 아래 `DictPanel`(사용자 사전 엑셀) = **2 : 1 높이**. `MainWindow.file_panel`은 `attach_panel`의 별칭이라 `set_file`/`has_file` 호출부는 그대로다. ⚠ 세로 2:1은 `stretch(2,1)`만으로 정해지지 않는다 — QVBoxLayout은 stretch를 나누기 전에 각 칸의 최소 높이를 먼저 확보하므로, 좌우 1:1에서 겪은 것과 **같은 함정**이다(memory `setup-panel-equal-grid-qt-traps`). 두 칸 모두 세로 정책 `Ignored`로 최소 높이를 0 취급시켜 비율이 오직 stretch로 정해지게 한다. ⚠ 그래서 `DictPanel`은 `FilePanel`의 축소판이 아니라 **여백·아이콘을 따로 잡은 낮은 칸**이다(1/3 높이에 드롭존 기본값을 그대로 쓰면 내용이 잘린다). 첨부 직후 파일명 옆의 '등록 용어 N건'은 `DictPanel._peek`이 같은 로더로 한 번 읽어 보여 주는 **표시용**이다 — 실제 교정에 쓰는 값은 언제나 워커가 분석 시작 시점에 다시 읽는다(그 사이에 사용자가 엑셀을 고칠 수 있다).

**Activity log** ([ui/widgets/activity_panel.py](ui/widgets/activity_panel.py)): the right-hand log **does not print worker messages verbatim**. Pipeline logs are written as evidence — long sentences carrying the *reason* for each decision, interleaved with COM-bridge plumbing, per-chunk progress and boilerplate — which in a ~300px column reads as a wall of text (user report 2026-07-23). A display layer therefore ① hides low-value rows (`_DROP`, `_ITEM_RE`), ② rewrites each line to keywords via an ordered regex table (`_RULES` — reason clauses dropped, **counts always preserved**), and ③ collapses repeated progress lines onto one self-updating row via a coalesce key (`AI 분석 n/m 청크`). `err`-level lines bypass all three (tracebacks must survive intact). ⚠ **Screen-log convention, binding on every log line you add (user directive 2026-07-31)**: a displayed line carries a `[태그]` prefix and an `n건` count — **never a concrete example** ('원문' → '교정' word lists). Per-item detail belongs in the raw log only, emitted as an indented `      · …` bullet: `_ITEM_RE` drops *any* bullet-led line by shape, so no per-phrase `_DROP` entry is needed (the previous per-phrase list is what let `· 상호 무효화 쌍 → 사용자 결정 '…' ↔ '…'` leak onto the screen — an unregistered phrase is one `log()` call away from becoming a visible row). Corollary: **summary lines must not start with `·`** — use `→` or `[태그]`, or the count disappears. The sweep that proves it is `_condense`-over-every-`log()`-literal; both invariants (every displayed line tagged / no manuscript examples) currently hold at 154 literals. ⚠ `self._entries` keeps the **raw** messages — `get_proofreading_log()` and post-hoc debugging depend on them, and the result dashboard runs its own separate curation; condensing only ever happens on screen. Rendering is a **2-column `QTextTable`** (time | content) built incrementally: a wrapped message stays inside its own cell instead of flowing under the timestamp, which is what the old single-block `시각&nbsp;&nbsp;내용` layout did. `_write_row` rewrites a row's cells in place (used by both append and coalesce); `refresh_theme()` rebuilds the table from `_rows` (already-condensed), never from `_entries`. The panel has **no summary chips** — they duplicated the footer/rail counters and were removed 2026-07-23 along with `set_detected`/`set_summary`.

**Design system**: [ui/styles/theme.py](ui/styles/theme.py) holds `LIGHT`/`DARK` token palettes, scales (`SPACE`/`RADIUS`/`FONT`), and `build_qss(palette)`. Style **only** via global QSS objectName/property selectors (e.g. `variant="primary"`, `role="card"`, `state="active"`) + `restyle(widget)` after a property change — avoid per-instance `setStyleSheet` in persistent widgets so dark-mode toggle reskins everything via `apply_theme(app, mode)`. Directly-painted/HTML widgets (`ToggleSwitch`, review `QTextBrowser`, icons, activity log) implement `refresh_theme()`; `MainWindow._refresh_all_themes()` walks the tree and calls it on every descendant after a toggle. Reuse primitives from [ui/widgets/components.py](ui/widgets/components.py) (`make_button`, `card`, `section_card`, `badge`, `chip`, `label`). Theme mode persists via `ConfigLoader.get_theme()/set_theme()` ([APP] section). ⚠ **Tooltips are a theme-independent dark chip** (`tooltip_bg`/`tooltip_fg`/`tooltip_border`, identical in both palettes — the same "theme-independent surface" idiom as `LightConfirmDialog` and the toast). Keep the text light and do **not** split those tokens per theme; `apply_theme` also mirrors them into `QPalette.ToolTipBase/ToolTipText` (tooltip-only roles — widening that palette write would repaint native widgets the QSS doesn't cover). The rule body lives once in `_TOOLTIP_RULE`, used by both the global QSS and `tooltip_qss()`.
★**A selector-less instance stylesheet cascades into the tooltip and beats the global `QToolTip` rule** — Qt wraps `w.setStyleSheet("background: transparent;")` in `* { … }`, and QTipLabel counts as part of that subtree. Every tooltip bug seen here is that one cause wearing different faces (measured 2026-08-12 by real screen capture): review cards (`_inner_card` = `background:#FFFFFF`) rendered **white-on-white in light mode**; the result panel (`_twidget`/`_Riser` = `background:transparent`) rendered **pure black** — which is what the earlier "this environment's Qt paints tooltips black no matter what the stylesheet says" note actually measured. That note was wrong: with no selector-less ancestor, forcing `background-color:#FF0000` renders **red**. Dark mode hides the bug because the ancestor's surface color is already near-black. The fix is `theme.local_qss(decls)`: it states the `*` selector explicitly (identical to what Qt does — verified pixel-for-pixel, 0 differing pixels in both themes) and re-declares the `QToolTip` chip after it, so the type selector out-specifies `*`. **Use it for any new declaration-only stylesheet on a container**, and never mix declarations and rules in one string (Qt fails to parse and re-wraps the whole thing in `*{…}`). ⚠ Verify tooltips by **real screen capture** (`QScreen.grabWindow(0)` cropped to the QTipLabel's geometry × devicePixelRatio) — `widget.grab()` returns the stylesheet's intent and shows nothing wrong.

**Bundled assets** (under `assets/`, resolved by [ui/styles/assets.py](ui/styles/assets.py) for dev + frozen): `assets/fonts/` Pretendard **TTF** (the `static/alternative` TrueType-hinted build — OTF/CFF rendered blurry & vertically clipped on Windows/Qt; loaded by [ui/styles/fonts.py](ui/styles/fonts.py) `load_fonts()` in `main.py`; primary UI font, set via single-family `font-family: "Pretendard"` since Qt QSS ignores comma fallback lists; the app font uses `QFont.PreferNoHinting` because Windows' default hinting grid-snaps and drops thin top strokes e.g. ㅎ), `assets/icons/` Lucide SVGs (ISC) rendered/recolored to QIcon/QPixmap by [ui/styles/icons.py](ui/styles/icons.py) — use `IconButton`/`IconLabel` or `make_button(..., icon="name")`, never emoji glyphs. **Build note**: Nuitka/PyInstaller must bundle `assets/` and the `PySide6.QtSvg` + `qsvg` image-format plugin. ⚠ **`assets.base_dir()` must resolve to `sys._MEIPASS`, not the EXE folder** — PyInstaller onedir puts `--add-data assets;assets` inside `_internal/`, and the old EXE-folder-only rule made every icon, the brand logo, and **Pretendard itself** vanish from the released build with no error at all (a missing SVG becomes an empty pixmap; a missing font silently falls back). This is the *opposite* of the data rule in `datapaths.py` — dictionaries live beside the EXE precisely so they can be replaced independently, while assets are code-coupled and belong in the bundle. `build_dist.verify()` now fails the build if `_internal/assets/{icons,fonts,logo}` is missing or empty.

**Review panel** ([ui/widgets/review_panel.py](ui/widgets/review_panel.py)): cards are **per-occurrence** — a word repeated N times in the manuscript yields N cards (each tagged `반복 k/N`), ordered by document position; clicking a card scrolls the preview to that occurrence (`<a name>` anchors + `scrollToAnchor`). Cards default to **pending** (white); each occurrence has its own accept/reject (split ✓/✕ solid icon buttons, card tinted green/red by `status` property). **반복 일괄 처리**: a user's accept/reject on any card auto-propagates to the group's other untouched repeat cards (`occ["auto"]`); flipping an auto-set card to the opposite raises a confirm popup and, if confirmed, flips **only that card** (`occ["by_user"]` — never overwritten by later propagation). **용어 일관성 통일** (`_unify_dialog`): 띄어쓰기 일관성 카드(marked `Correction.consistency_flip` — set **only** by worker [7] `find_compound_spacing_consistency` consumption; `consistency_pass` variants explicitly unset it; never enable for norm corrections) is **not** a per-item verdict but a document-wide 표기 choice, so `_set_status` routes it to a confirm popup **before** the repeat/auto branch (accept → "문서 전체를 '{corrected}' 표기로 통일", reject → "…'{original}'…"). Confirm ⇒ the whole group moves together **and** the opposite direction is settled in the same step: reject runs `_apply_flip` (reject A→B group + synthesize/accept reverse B→A), accept runs `_apply_unify_forward` (accept A→B group + reject an existing reverse so the two can't cancel out). Symmetric — selecting on the reverse card returns to the original direction; no reverse card is ever synthesized for non-`consistency_flip` cards (that would de-standardize norm corrections). Consequence: consistency cards have **no per-occurrence partial** accept/reject. The old "반대 표기로 통일" link button was removed 2026-07-21 (users rejected without noticing it, leaving both 표기 mixed). Both paths preserve other cards' per-occurrence states by re-running only sort/`_mark_stem_boundary_skips`/`_resolve_overlaps`/`_derive_all` (**never** rebuild occurrences — that wipes partial decisions), and both are dispatched via `QTimer.singleShot(0, …)` after the popup closes ⚠ **and neither rebuilds the card list** (2026-07-27 perf fix): the old code called `_rebuild_cards()` and then synchronously re-created every card from index 0 up to the acted-on one, so the delay scaled with the card's position in the list (measured 0.8s at card #20 → **6.2s at #690**). Unify only changes ① two groups' statuses and ② — on the reject direction, and only when the reverse correction is synthesized fresh — a few new occurrences. So status-only paths just call `_restyle_dirty()` (repaints solely the cards whose `(status, is_active)` actually changed, tracked in `card._styled`), and `_apply_flip` returns `grew=True` only when occurrences were added, which is the sole case that runs `_sync_cards()` (remove-then-insert diff against the live card list) plus the anchor restore. What makes this possible is that **occurrence identity is a stable `uid`, not a list index** (`_new_uid`/`_occ_pos`/`_reindex_occ`): card `occ_id`, preview anchors `c{uid}` and `_active_occ_id` all key off it, so re-sorting `_occ` when reverse occurrences join no longer desynchronizes every card — which is exactly why a full rebuild used to be the only option. Same release: `_mark_stem_boundary_skips` memoizes per occurrence (`_stem_done`, invalidated by `_on_corrected_edited`), `_resolve_overlaps`/`_render_with_text` use the `_Occupancy` bytemap instead of an O(occurrences²) interval scan, `_derive_all` groups in one pass, and `_refresh_preview(defer=True)` coalesces re-renders on an 80ms timer — 96% of preview cost is Qt's `setHtml`, not the Python render (455ms of 475ms at 3,830 occurrences), so rapid accept/reject clicks now cost one re-typeset instead of N. `load()` and `refresh_theme()` stay synchronous (dialog teardown first, else a ghost white window; `_set_status` must `return` immediately since `_rebuild_cards` deletes the card widget it was passed). The popup is `LightConfirmDialog` — a frameless **always-light** modal built on `build_light_card()`/`LIGHT_CARD_QSS`, the same surface the **toast** (`_toast`, 반복 일괄 처리 알림) uses, so both read as one system: head title + divider + body, drawn in-widget so the OS dark title bar can't leak in, every visual property re-declared under `#lcd*` objectName selectors to beat the global dark QSS, and wordWrap labels given a measured `setMinimumWidth` (their sizeHint collapses to ~230px and folds a one-liner into 3 lines). Both are theme-independent — do **not** add `refresh_theme()` to them. **Card list loading is measured-tuned** (constants at the top of `ReviewPanel`): a 50-card batch cost ~433ms of frozen UI, and since each batch carries a ~30ms whole-list layout pass, smaller batches only multiply the total — so the fix isn't batch size. Instead: first batch `_INITIAL_CARDS` (screen-filling only), the rest by an **idle prefetch timer** that runs only after `_IDLE_QUIET_MS` of no interaction (`_note_interaction()` is called from scroll/accept-reject/`_scroll_to`) and **parks itself once `_PREFETCH_AHEAD` viewports of cards are buffered below the fold** — never preload everything, because insert cost scales with how many cards are already alive. `_on_scroll` keeps an 80% safety net (`_SCROLL_CHUNK`). `_rebuild_cards` swaps the whole scroll content (`_new_scroll_content`) instead of detaching cards one by one (309ms → 64ms for 200 cards, and no widget ever becomes a top-level window, which also retires the old ghost-window workaround) — ⚠ `QScrollArea.setWidget()` destroys the old widget **synchronously**, so clear `self._cards` first. Never call `_emit_counts()` from `_load_more_cards`: counts derive from `_occ`, not from loaded cards. ⚠ **A freshly created card's `pos()` is not final for several layout passes** (measured y: 0 → 877 → 2953); reading it after a single `singleShot(0)` lands mid-settle and scrolls to the wrong place, and forcing `activate()`/`adjustSize()` does not fix it. Both `_scroll_to` and `_restore_card_anchor` therefore go through `_place_card(occ, offset, smooth)`, which re-measures until the position stops changing. Any rebuild-triggering action must bracket itself with `_capture_card_anchor(occ)` / `_restore_card_anchor(..., on_done=)` to keep the acted-on card at the same viewport offset, and must hide the rebuild: `_do_unify` loads cards **up to the anchor synchronously** (deferring that leaks a frame showing only the initial batch) and wraps the whole sequence in `_card_scroll.setUpdatesEnabled(False)`, re-enabled from `on_done` plus a time-based backstop so the panel can never stay frozen. Likewise `_refresh_preview(keep_scroll=True)` is the default because `setHtml` resets QTextBrowser scroll to 0 — accepting one card used to fling the 원문/교정문 panes back to the top; only `load()` passes `keep_scroll=False`. It suspends `_scroll_sync` around the swap and restores each scrollbar twice (immediately + next tick, since the document's scroll range isn't final until it has laid out). To make the previews *follow* an action instead, call `_scroll_previews_to(cid)` (previews only — leaves the card list where it is) from a `QTimer.singleShot(0)` so it runs **after** that restore; `_do_unify` does this to match what `_scroll_to` gives normal cards, and passes `active_occ=` into `_apply_flip`/`_apply_unify_forward` so `_mark_active_occ` can re-resolve the occurrence index after the re-sort without a second render. ⚠ the panel's correction list is a sorted **copy**, so `main_window._start_apply` re-syncs `self._corrections = review_panel.get_corrections()` before applying — without it panel-added reverse corrections never reach ApplyWorker/errata. **Partial reject is real**: `_derive()` sets the unique `Correction.status` (accepted if any occurrence accepted) and `skip_occurrences` = occurrence indices (document order, 0-based) NOT accepted; this flows `apply_worker` → `HwpEditor.apply_corrections` → bridge `apply()`, whose `RepeatFind` loop skips those `count` indices (and disables the AllReplace fallback when a skip set is present). `counts_changed`/`get_counts()` report **occurrence-level** counts. **Card width is fixed to the column** (no h-scrollbar): the 원본 label gets ZWSP soft-break points (`_soft_breakable`, default size policy — a custom `Ignored` policy broke heightForWidth), the 교정 field is a `GrowingTextEdit` (wrap-anywhere QTextEdit that grows vertically, `QLineEdit`-compatible `text()`/`editingFinished`; height = doc height + measured chrome, **never** `frameWidth()` which lies under QSS borders), and cards are vertically `Maximum` so leftover list space goes to the trailing stretch, not into the cards.

**Result = completion dashboard**: [ui/widgets/result_panel.py](ui/widgets/result_panel.py) renders a report-style dashboard — header (파일명+완료 시각+수작업 대비 절약 시간 시계) / pipeline hero (01 분석 N자 → 02 교정 제안 사전·규칙/AI 분해 → 03 적용 N건·본문 M곳·적용률, terms: 건=항목·곳=등장) / 상세 분석 (제안 소스 도넛·적용률 게이지·오류 유형 바) / 산출물 카드 / 실패항목(인라인 사유, no dialog) / 교정 진행 로그, all inside a vertical QScrollArea. Numbers are the heroes: `AnimatedNumberLabel` count-up (OutExpo + 착지 팝, final-width reserved so layout doesn't shift; font set via per-instance stylesheet because global QSS `QWidget{font-size:13px}` overrides `setFont`). `show_result(result, log, corrections=, char_count=, file_name=)` — main_window passes the extras at apply-done; a later change to the same run (추가 산출물 완료 등) goes through `update_result(result)`, a **static** re-render that reuses the stored extras and keeps the completion timestamp (result-dict identity), because replaying the whole count-up/chart animation reads as a new run. `refresh_theme()` re-renders statically (no re-animation). Chart widgets read `current_palette()` at paint time; only bundled Lucide icons exist (no pie-chart/clock/file-spreadsheet — use table/circle-check/list-checks etc.). The progress log there is **the same log the activity panel shows** — `ActivityPanel.get_proofreading_log()` returns its already-condensed display rows (`[태그] 내용`), minus HWP-bridge plumbing (`_PLUMBING_KW`, which also catches `err`-level lines that bypass `_DROP`). `result_panel` renders them as-is and only owns the two-column time/text alignment. ⚠ It used to receive raw messages and re-curate them with its own `_curate_result_log`/`_LOG_DROP`/`_LOG_LEAD` rules; two rule sets meant the same run read differently on the two screens and every wording change had to be made twice — that second pass was deleted 2026-07-23. **Change log wording in exactly one place: `activity_panel._RULES`.** There is no settings dialog — the header has only theme-toggle + new-file (the HWP-version-registration `settings_dialog.py` and its header button were removed 2026-06-17; the Gemini API key comes from env/config.ini/embedded org key).

## Conventions

- Korean docstrings/comments are the norm. Keep new code consistent.
- `core/` is GUI-agnostic — never import `PySide6` from `core/`. UI threading lives in `ui/workers/`.
- Long-running checkers accept a `threading.Event` named `stop_event` and a `logger` callable; honor both.
- There is no automated test suite. Verify changes by running the app (`.\.venv64\Scripts\python.exe main.py`) against a real `.hwp`/`.hwpx`; `core/` modules are GUI-agnostic and can be exercised directly from a Python REPL.
